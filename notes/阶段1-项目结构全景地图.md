## 一、顶层布局（按职责归类）


**记忆锚点**：`prog/`（通用引擎，与 OS 无关）↔ `sys/`（某 OS 描述数据）是阶段 0"可移植性分界线"的两侧，是读懂整个结构的钥匙。

## 三、构建系统：`make` 产出什么（阶段 1 重点）

Makefile 顶层三行（`Makefile:114-116`）：

```makefile
all:    host target
host:   manager repro mutate prog2c db upgrade      # 跑在 HOST 上的 Go 二进制
target: execprog executor check_syzos               # 跑在 目标机 上的二进制
```

**`host` vs `target` 的划分 = 阶段 0 "manager 在 host / executor 在目标机" 的构建体现**：

| 组 | 编译给谁 | 输出路径 | 代表二进制 |
|---|---|---|---|
| **host** | Go，宿主机（`GOOS=HOSTOS`） | `bin/syz-*` | `syz-manager`(大脑)、`syz-repro`(复现)、`syz-mutate`、`syz-prog2c`、`syz-db`、`syz-upgrade` |
| **target** | 交叉编译，目标机（`GOOS=TARGETGOOS`） | `bin/{OS}_{ARCH}/syz-*` | `syz-executor`(C++,唯一非Go)、`syz-execprog` |

两个细节：
1. 输出路径不同：host 直接进 `bin/`；target 进 `bin/linux_amd64/` 架构子目录（为目标机交叉编译）。
2. executor 是唯一 C++（`Makefile:136`）：`$(CXX) -o bin/.../syz-executor executor/executor.cc ...`，静态、极简。

### 常用单目标（`Makefile`）
- `manager`(:161) `repro`(:180) `mutate`(:183) `prog2c`(:189) `db`(:198) → host Go 工具
- `execprog`(:164) → target Go 工具；`executor`(:118) → target C++
- `extract`(:238) → syz-extract（从内核头抽常量）；`generate`(:246) → 重跑代码生成

## 四、隐藏关键环：`descriptions` / syz-sysgen（syzlang→代码）

几乎每个目标都挂 `descriptions` 依赖（`Makefile:118,161,164...`）。这一步（`Makefile:143-153`）是阶段 0 那条"syzlang→代码"编译链的真身：

```
sys/*/*.txt + sys/*/*.const ──(syz-sysgen)──► ① sys/*/gen/*.go        (给 Go 侧 prog 用)
                                              ② executor/defs.h
                                              ③ executor/syscalls.h    (给 C++ 侧 executor 用)
```

**关键洞察**：同一份 syzlang 描述被 `syz-sysgen` 编译成**两边都用**的代码——Go 侧（`sys/*/gen/`，供 `prog/` 加载）+ C++ 侧（`executor/defs.h`、`syscalls.h`，供 `executor.cc` 编译）。这解释了"结构感知"如何同时贯穿生成端(Go)与执行端(C++)：它们读同一份描述的两种产物。因此 `descriptions` 是所有构建的前置——不先 codegen，两边都编不了。

（`.descriptions` 是个 stub 文件，代表 syz-sysgen 一次性生成的所有文件，见 `Makefile:143-145` 注释。）

## 五、动手：`make` 结果（本环境实测）

工具链：go 1.26.0 + gcc 13.3.0。分别跑了 `make host` 和 `make target`，产物如下：

```
bin/                          ← host 组(Go, 宿主机, 直接放 bin/)
├── syz-manager   (66M)   顶层编排大脑
├── syz-repro     (56M)   崩溃复现/最小化
├── syz-mutate    (41M)   变异一个程序(命令行)
├── syz-prog2c    (42M)   syz程序→C(理解程序模型利器,阶段2/3用)
├── syz-db        (19M)   corpus 数据库工具
├── syz-upgrade   (19M)   corpus 格式升级
└── syz-sysgen    (12M)   ★codegen工具(descriptions前置,把 syzlang 编成代码)

bin/linux_amd64/              ← target 组(交叉编译, 目标机, 进 {OS}_{ARCH}/ 子目录)
├── syz-executor          ★C++执行器(跑在目标机里)
└── syz-execprog             在目标上执行程序看覆盖率(需VM/内核)
```

**三点实测印证**：
1. **host 直接进 `bin/`，target 进 `bin/linux_amd64/`** —— 架构子目录只在编 target 时出现，坐实了"为目标机交叉编译"。
2. **executor 确实是静态二进制**：`file bin/linux_amd64/syz-executor` → `ELF 64-bit ... static-pie linked` —— 正好印证阶段 0 `internals.md` 说的"C++、compiled as static binary"（静态是为了不依赖目标机的动态库，随时 scp 过去就能跑）。
3. **编译命令**：executor 用 `g++ ... -static-pie -std=c++17 executor/executor.cc`（单文件 C++）；host 工具用 `go build`。

> 注：`make` 顶部会提示 "run command via tools/syz-env for best compatibility" —— 官方推荐用 `syz-env`(容器) 保证工具链一致，本机直接 make 也能成功。

## 五之二、目录落到实体：VM vs 物理 DUT 两张图

> 事实核对：这版**无 `syz-fuzzer`**，fuzzing 逻辑全在 host 的 syz-manager 进程内（`pkg/fuzzer`）；`pkg/rpcserver/runner.go` 也是 host 侧（每 executor 一个 `Runner`）。目标机上**只有 syz-executor + 内核**。

### 图一：VM 情形（vm/qemu 后端）

```
┌─ HOST（宿主机·稳定内核）= 运行 syz-manager 这一个 Go 进程 ───────────
│  编排大脑    syz-manager/            启停/监控VM、主循环
│  决策闭环    pkg/fuzzer/             genFuzz(生成vs变异)、triage
│              pkg/signal/            signal Diff/Merge(什么叫新信号)
│              pkg/corpus/            语料库入库
│  程序引擎    prog/                  Generate/Mutate/Serialize/Minimize  ← 与OS无关
│  描述数据    sys/*/gen/*.go         syzlang 编译出的Go, 被 prog 加载
│  通信服务端  pkg/rpcserver/         rpcserver.go + runner.go(每executor一个Runner)
│  崩溃/覆盖   pkg/report/ pkg/repro/  console→崩溃描述、复现
│              pkg/cover/             PC→源码行(给人看的报告, 不在热路径)
│  【差异点】  vm/qemu/               ★用内核镜像启动/销毁 QEMU VM
│  持久化      workdir/               corpus.db、crashes/
└───────────────────────────────┬──────────────────────────────────────
                                 │  线格式: pkg/flatrpc (FlatBuffers)
                                 │  传输:   内部网络 / ssh
                                 ▼
┌─ TARGET = QEMU 虚拟机（manager 用 vmlinux 镜像现拉起）──────────────
│  syz-executor（常驻）   ← executor/executor.cc + 编入的 defs.h/syscalls.h(syzlang产物)
│       │ fork
│       ▼ 短命子进程 × N   每个只跑一个输入
│       │  syscalls ↓        ↑ KCOV 覆盖率
│  本VM内核 + Modules（vmlinux 镜像，编译时开 CONFIG_KCOV）
└──────────────────────────────────────────────────────────────────────
```

### 图二：物理 DUT 情形（vm/isolated 后端）——host 侧几乎相同，只差外圈一行 + 通信方式

```
┌─ HOST（宿主机·稳定内核）= 运行 syz-manager 这一个 Go 进程 ───────────
│  编排/决策/引擎/描述/RPC服务端/崩溃覆盖/持久化 …全部同图一…
│   (syz-manager/ + pkg/fuzzer/ + prog/ + sys/gen + pkg/rpcserver/
│    + pkg/signal/ + pkg/corpus/ + pkg/cover/ + pkg/report/ + pkg/repro/ + workdir/)
│  【差异点】  vm/isolated/           ★不建机器、不部署镜像, 只 ssh/scp
│                  ├─ scp   : 把 bin/linux_amd64/syz-executor 推到 DUT 的 target_dir
│                  ├─ ssh   : 启动 executor、读内核 console(dmesg)
│                  └─ ssh -R: 反向隧道, 让 executor 的 RPC 回连 manager
└───────────────────────────────┬──────────────────────────────────────
                                 │  线格式: pkg/flatrpc (FlatBuffers)
                                 │  传输:   ssh / 反向 ssh 隧道(唯一通道)
                                 ▼
┌─ TARGET = 已存在的真实物理机 DUT（内核它自己装好, manager 不碰镜像）──
│  sshd ──► syz-executor（scp推来、ssh启动、常驻）
│       │                   ← 同样是 executor/ + syzlang头文件 编成的静态二进制
│       │ fork
│       ▼ 短命子进程 × N   每个只跑一个输入
│       │  syscalls ↓        ↑ KCOV 覆盖率
│  DUT 本机内核（自带, 需 CONFIG_KCOV=y / KASAN / DEBUG_INFO）
└──────────────────────────────────────────────────────────────────────
```

### 落位对照表

| 代码/产物 | 实体 | VM 情形 | 物理 DUT 情形 |
|---|---|---|---|
| `syz-manager/`、`pkg/fuzzer`、`prog/`、`sys/*/gen`、`pkg/signal`、`pkg/corpus`、`pkg/rpcserver`、`pkg/cover`、`pkg/report`、`pkg/repro`、`workdir/` | **HOST** | 相同 | 相同 |
| `vm/`（后端） | HOST | `vm/qemu/` 建/销毁VM+部署镜像 | `vm/isolated/` 只 ssh/scp |
| `pkg/flatrpc`（线格式） | 两端共用 | 内部网络/ssh | ssh **反向隧道** |
| `syz-executor`（源自 `executor/`+syzlang头文件） | **TARGET** | VM 内运行 | scp 到物理机运行 |
| 内核 + KCOV | **TARGET** | vmlinux 镜像启动 | DUT 自带 KCOV 内核 |
| 短命子进程 | **TARGET** | executor fork | executor fork |

**三个落位判断（要记牢）**：
1. **生成/变异全在 HOST**（`prog/`+`pkg/fuzzer/`）；目标机只"执行+采集"，不做决策。
2. **`sys/` 一份描述编到两端**：Go 产物(`sys/*/gen`)链进 host manager；C 头(`executor/defs.h`/`syscalls.h`)编进 target executor。
3. **VM 与物理机差异只在外圈一行**（`vm/qemu`↔`vm/isolated`）+ 通信方式；HOST 大脑与 TARGET 的 executor/内核/子进程结构两种情形完全一致。
