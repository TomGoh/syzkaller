## 三、构建系统：`make` 产出什么

Makefile 顶层三行（`Makefile:114-116`）：

```makefile
all:    host target
host:   manager repro mutate prog2c db upgrade      # 跑在 HOST 上的 Go 二进制
target: execprog executor check_syzos               # 跑在目标机上的二进制
```

要分清两个维度：`host` / `target` 回答「二进制在哪台机器跑」；「给什么架构编」另有三组 OS/arch。

### 维度一：`host` / `target` = 在哪跑

对应阶段 0：「manager 在 host / executor 在目标机」。

| 组 | 在哪跑 | 输出路径 | 代表二进制 |
|---|---|---|---|
| **host** | 宿主机（Go） | `bin/syz-*` | `syz-manager`、`syz-repro`、`syz-mutate`、`syz-prog2c`、`syz-db`、`syz-upgrade` |
| **target** | 被测机（常需交叉编译） | `bin/{OS}_{ARCH}/syz-*` | `syz-executor`（C++，见 `Makefile:136`）、`syz-execprog` |

### 维度二：三组 OS/arch = 给什么架构编

见 `Makefile:4-17`。

| 对 | 含义 | 决定谁的 arch | 产物去哪 |
|---|---|---|---|
| **HOSTOS / HOSTARCH** | syz-manager 所在机器 | host 工具 | `bin/` |
| **TARGETOS / TARGETVMARCH** | 被测 OS / 内核的 arch | `syz-execprog` | `bin/{OS}_{TARGETVMARCH}/`（`Makefile:165`） |
| **TARGETOS / TARGETARCH** | 发起 syscall 的测试进程的 arch | `syz-executor` | `bin/{OS}_{TARGETARCH}/`（`Makefile:135-136`） |

后两组分开，是为了测 compat（兼容层）syscall。例如在 amd64 内核上跑 386 测试进程，走 32 位 compat 路径：

```bash
make TARGETVMARCH=amd64 TARGETARCH=386
```

此时：

- `syz-executor`（真正发 syscall）是 386 → `bin/linux_386/syz-executor`
- `syz-execprog` 是 amd64 → `bin/linux_amd64/syz-execprog`

也就是说，executor 和 execprog 可以落在不同 arch 子目录。不做 compat 时（例如只设 `TARGETARCH=arm64`），`TARGETVMARCH` 会归一成 arm64，两者一起进 `bin/linux_arm64/`。

`bin/` 是累加的：换 target arch 不会清掉旧目录，多试几次会看到多个 `linux_*/` 并存。想干净重来：`make clean`（`Makefile:409`）或 `rm -rf bin`。

### FAQ：为物理 DUT 编译，要改编译指令吗？

不用。只看 arch。

「用 VM 还是连物理机（qemu vs isolated）」是**运行时 config**，和编译正交：

1. 各后端以空导入编进同一个 `syz-manager`（`vm/vm.go:37-41`：`_ ".../vm/isolated"`、qemu、gce …）。
2. 各自在 `init()` 里 `vmimpl.Register("isolated", ...)` 注册进一张表。
3. 启动时 manager 读 config 的 `"type"`，按名字查表选后端。一个二进制含全部后端。

为物理 DUT 编译，命令与测 VM 相同，只按 DUT 的 arch 编。例如 arm64 DUT：

```bash
make HOSTOS=linux HOSTARCH=amd64 TARGETOS=linux TARGETARCH=arm64
```

区别只在 config：

| | VM（qemu） | 物理 DUT（isolated） |
|---|---|---|
| `"type"` | `"qemu"` | `"isolated"` |
| `vm` 段 | `count` / `cpu` / `mem` / `kernel` … | `targets` / `target_dir` / `target_reboot` … |

和 DUT 相关的编译约束主要仍是 arch：`TARGETARCH` 必须等于 DUT 的 arch，scp 过去的 executor 才能跑。DUT 内核还需开 `CONFIG_KCOV=y` 等，那是目标机侧配置，不是 syzkaller 编译本身。

**小结**：编译只回答「给什么架构造二进制」；「连 VM 还是物理机」由 config 的 `type` 在运行时回答。二者正交。

### 常用单目标

- host Go：`manager`（:161）、`repro`（:180）、`mutate`（:183）、`prog2c`（:189）、`db`（:198）

## 四、隐藏关键环：`descriptions` / syz-sysgen

几乎每个目标都依赖 `descriptions`（`Makefile:118,161,164…`）。这一步（`Makefile:143-153`）就是阶段 0 那条「syzlang → 代码」链在构建里的落点：

```
sys/*/*.txt + sys/*/*.const
        │ syz-sysgen
        ▼
  ① sys/gen/*.gob.flate   （每个 OS/arch 一份，序列化并压缩的描述）
     + sys/register.go    （//go:embed gen/*.gob.flate，嵌进 Go 二进制）
  ② executor/defs.h       （每个 call 的属性等，约 194KB）
  ③ executor/syscalls.h   （syscall 名 → 号大表，约 4.2MB）
```

同一份 syzlang 描述被编成**两侧都用**的产物：

- Go 侧：`sys/gen/*.gob.flate`，经 `sys/register.go` 的 `//go:embed` 嵌进每个 Go 二进制。
- C++ 侧：`executor/defs.h`、`syscalls.h`，被 `executor.cc`（约 25、498 行）`#include`。

因此「结构感知」能同时贯穿生成端（Go）与执行端（C++）：两边读的是同一份描述的两种产物。不先做 codegen，两边都编不过。

`.descriptions` 是 stub 文件，代表 syz-sysgen 一次生成的全部文件（见 `Makefile:143-145` 注释）。

### 为什么这么多目标都依赖 descriptions？

#### 1. 产物是源码级依赖

文件头都写着 `Automatically generated by syz-sysgen; DO NOT EDIT`。

| 侧 | 产物 | 如何进入二进制 |
|---|---|---|
| Host / Go | `sys/gen/*.gob.flate` + `sys/register.go` | `//go:embed` 嵌进 Go 二进制 |
| DUT / C++ | `executor/defs.h` + `executor/syscalls.h` | `executor.cc` `#include` |

这些文件不存在或过期，两边都编不过。所以 Makefile 把 `descriptions` 挂成几乎所有目标的前置。

#### 2. 没有描述，二进制用不上 syscall 元信息

凡是要操作程序的东西都依赖这份元信息：

- Go 侧：manager（生成 / 变异）、prog2c、mutate、execprog、repro、db …… 不知道 `open` 有几个参数、`fd` 是 resource，就做不了事。
- C++ 侧：executor 要把字节流解码成真实 syscall，必须有名 → 号表和参数布局。

#### 3. 两侧角色：同一真相源上的编码 / 解码

```
        同一份 sys/*.txt（syzlang）
                 │ syz-sysgen 一次生成
      ┌──────────┴──────────┐
      ▼                     ▼
 Host / Go 产物          DUT / C++ 产物
 sys/gen/*.gob.flate     executor/syscalls.h + defs.h
      │                     │
   编码端                  解码端
 生成 / 变异程序           解码字节流
 + 序列化成字节流  ──RPC──► + 发起真实 syscall
```

| 侧 | 用描述做什么 | 角色 |
|---|---|---|
| Host（Go） | 用元信息生成 / 变异，再序列化成执行器字节流 | 编码器 |
| DUT（executor） | 用表和布局解码字节流，还原成真实系统调用 | 解码器 |

两边必须对「第 2 个参数是 fd、占几字节、怎么排布」逐位一致。若 host 按 A 版描述序列化、executor 按 B 版解码，参数会错位，轻则乱执行，重则假崩溃。

syz-sysgen 从同一份 `.txt` 一次生成两套产物，保证编码与解码对齐。改了 `.txt` 必须两侧一起重编；只重编一边会协议错位。

#### 4. 为什么用 `.descriptions` stub

syz-sysgen 一次生成所有文件（多个 OS/arch 的 `.gob.flate` + 两个 C 头），没法把每个文件做成独立 make 目标。于是用 stub 表示「全部生成物已最新」。`.txt` / `.const` 一改，就触发整体重新 codegen（`Makefile:143-153`）。

#### 5. 和阶段 2 的衔接

这对编解码器对应阶段 2 数据流上的两棒：`prog.SerializeForExec`（host 编码）↔ executor 里的解码执行。改一处 `.txt` 会牵动两侧，根源在这里。

## 五、动手：`make` 结果（本环境实测）

工具链：go 1.26.0 + gcc 13.3.0。分别跑过 `make host` 和 `make target`，产物大致如下：

```
bin/                          ← host（Go，宿主机，直接放 bin/）
├── syz-manager   (66M)   顶层编排
├── syz-repro     (56M)   崩溃复现 / 最小化
├── syz-mutate    (41M)   命令行变异
├── syz-prog2c    (42M)   syz 程序 → C（阶段 2 / 3 常用）
├── syz-db        (19M)   corpus 数据库工具
├── syz-upgrade   (19M)   corpus 格式升级
└── syz-sysgen    (12M)   codegen：把 syzlang 编成代码（descriptions 前置）

bin/linux_amd64/              ← target（目标机，进 {OS}_{ARCH}/）
├── syz-executor              C++ 执行器
└── syz-execprog              在目标上执行程序并看覆盖率（需内核 / 目标机）
```

实测可核对三点：

1. host 进 `bin/`，target 进 `bin/linux_amd64/`。架构子目录只在编 target 时出现。
2. `file bin/linux_amd64/syz-executor` → `ELF 64-bit ... static-pie linked`。静态是为了少依赖目标机动态库，scp 过去就能跑（与 `docs/internals.md` 一致）。
3. executor 用 `g++ ... -static-pie -std=c++17 executor/executor.cc`；host 工具用 `go build`。

> `make` 顶部可能提示用 `tools/syz-env` 以获得更一致的工具链。本机直接 `make` 通常也能成功。

交叉编译 arm64 target 时，对应目录是 `bin/linux_arm64/`，里面同样只有 `syz-executor` 与 `syz-execprog`。这是设计如此，不是编少了。

## 六、目录落到实体：VM 与物理 DUT

> 核对：当前树**没有** `syz-fuzzer`。fuzzing 决策全在 host 的 `syz-manager` 进程内（`pkg/fuzzer`）。`pkg/rpcserver/runner.go` 也在 host（每个 executor 一个 `Runner`）。目标机上主要是 **syz-executor + 内核**。

图风格与阶段 0 拓扑 A / B 一致：左对齐流向。

### 图一：VM（`vm/qemu`）

```
[Host · 稳定机器，syz-manager 跑这儿]
  syz-manager/            启停 / 监控 VM、主循环
  pkg/fuzzer/             生成 vs 变异、triage
  pkg/signal/             signal Diff / Merge
  pkg/corpus/             语料库入库
  prog/                   Generate / Mutate / Serialize / Minimize（与 OS 无关）
  sys/gen/*.gob.flate     syzlang 产物，被 prog 加载
  pkg/rpcserver/          rpcserver.go + runner.go（每个 executor 一个 Runner）
  pkg/report/ pkg/repro/  console → 崩溃描述、复现
  pkg/cover/              PC → 源码行（给人看的报告，不在热路径）
  vm/qemu/                ★ 用内核镜像启动 / 销毁 QEMU VM
  workdir/                corpus.db、crashes/
      │
      │  线格式：pkg/flatrpc（FlatBuffers）
      │  传输：内部网络 / ssh
      ▼
[VM · manager 用 vmlinux 镜像拉起]
  sshd/adbd ──invoke──► syz-executor（常驻；编入 defs.h / syscalls.h）
                           │  ▲
                    fork   │  │ 共享内存（结果 / 覆盖率）
                           ▼  │
                      瞬态子进程（每个只跑一个输入）
                           │  ▲
                 syscalls  │  │ kcov
                           ▼  │
                      Kernel + Modules（vmlinux，含 CONFIG_KCOV）
```

### 图二：物理 DUT（`vm/isolated`）

```
[Host · 稳定机器，syz-manager 跑这儿]
  （与图一相同：manager / fuzzer / signal / corpus / prog / sys/gen /
   rpcserver / report / repro / cover / workdir）
  vm/isolated/            ★ 不建机器、不部署镜像，只 ssh / scp
      ├─ scp    ：把 bin/linux_<arch>/syz-executor 推到 DUT 的 target_dir
      ├─ ssh    ：启动 executor、读内核 console（dmesg）
      └─ ssh -R ：反向隧道，让 executor 的 RPC 回连 manager
      │
      │  线格式：pkg/flatrpc（FlatBuffers）
      │  传输：ssh / 反向 ssh 隧道（唯一通道）
      ▼
[DUT · 已存在的真实物理机；内核本机自带，manager 不碰镜像]
  sshd ──► syz-executor（scp 推来、ssh 启动、常驻）
             │  ▲
      fork   │  │ 共享内存
             ▼  │
        瞬态子进程（每个只跑一个输入）
             │  ▲
   syscalls  │  │ kcov
             ▼  │
        DUT 本机内核（需 CONFIG_KCOV=y；建议 KASAN / DEBUG_INFO）
```

与图一相比，Host 侧实质差异主要是：

1. 监控对象：VM → DUT。
2. 后端：`vm/qemu/`（建 / 销毁 VM + 部署镜像）→ `vm/isolated/`（只 scp / ssh / ssh -R）。
3. 传输：内部网络 / ssh → ssh 反向隧道。`pkg/flatrpc` 线格式不变。

Target 侧：QEMU 虚拟机 → 真实物理机；内核由镜像启动 → DUT 自带；executor 在 VM 内就绪 → 需 scp 推过去。executor 源码、fork 瞬态子进程、KCOV 采集两边一致。

### 落位对照表

| 代码 / 产物 | 实体 | VM | 物理 DUT |
|---|---|---|---|
| `syz-manager/`、`pkg/fuzzer`、`prog/`、`sys/gen`、`pkg/signal`、`pkg/corpus`、`pkg/rpcserver`、`pkg/cover`、`pkg/report`、`pkg/repro`、`workdir/` | Host | 相同 | 相同 |
| `vm/` 后端 | Host | `vm/qemu/` | `vm/isolated/` |
| `pkg/flatrpc`（线格式） | 两端共用 | 内部网络 / ssh | ssh 反向隧道 |
| `syz-executor`（`executor/` + syzlang 头） | Target | VM 内运行 | scp 到物理机运行 |
| 内核 + KCOV | Target | vmlinux 镜像 | DUT 自带 |
| 瞬态子进程 | Target | executor fork | executor fork |

要记牢的三点：

1. **生成 / 变异全在 Host**（`prog/` + `pkg/fuzzer/`）。目标机只执行并采集，不做决策。
2. **`sys/` 一份描述编到两端**：Go 产物进 host；C 头编进 target executor。
3. **VM 与物理机差异主要在外圈**：`vm/qemu` ↔ `vm/isolated`，以及通信方式。Host 大脑与 Target 的 executor / 内核 / 子进程结构两边一致。

### FAQ：是不是「除执行外，逻辑都在 Host」？

方向对，但分界线是「决策 vs 执行」，不是「复杂 vs 简单」。

**精确说法**：决策（往哪走）在 Host；执行机制（照着做 + 采集原始数据）在 DUT。executor 其实做了不少事，但都是执行机制，没有 fuzzing 决策。

**Host（决策 + 持久化 + 管理）**

| 职责 | 目录 |
|---|---|
| 生成 / 变异 / 最小化 | `prog/` + `pkg/fuzzer/` |
| 「什么算新信号」 | `pkg/signal/`（Diff / Merge）、`maxSignal` |
| triage、入库、syscall 组合优先级 | `pkg/fuzzer/`、`prog/prio.go`（ChoiceTable） |
| 语料保存（corpus.db / workdir） | `pkg/corpus/`、`syz-manager/` |
| 崩溃解析 / 存储 / 复现 | `pkg/report/`、`pkg/repro/` |
| 覆盖率符号化（PC → 源码行） | `pkg/cover/` |
| VM / DUT 管理、RPC 服务端 | `vm/`、`pkg/rpcserver/` |

**DUT / executor（执行机制，无 fuzzing 决策）**

从 `executor/executor.cc` 核对，这些也确实没法搬到 host：

| executor 做的事 | 代表函数 | 属于 |
|---|---|---|
| 与 manager 握手、收程序、回状态 | `receive_handshake` / `receive_execute` / `reply_execute` | 协议 |
| 解码序列化程序 | `read_input` / `read_arg` / … | 解码 |
| 把参数摆进内存 | `copyin` / `copyout` / `swap` | 执行准备 |
| fork 瞬态子进程；threaded 执行（应对阻塞 syscall） | `schedule_call` / `worker_thread` / `execute_call` | 执行 |
| 采集 KCOV；本地少量去重 | `dedup` / `coverage_filter` / `convert` | 采集 |
| 经共享内存 / flatrpc 回传 | `write_call_output` / `finish_output` | 回传 |
| 沙箱、超时 / 挂起处理 | sandbox_*、timeout 逻辑（阶段 6） | 隔离 |

它不做：生成、变异、最小化、corpus、符号化、「全局是否新覆盖」的判定、crash 解析。

> 唯一容易误会的点：executor 里的 `dedup` 只是本地少传一点数据。「这条覆盖对整个 fuzzing 是不是新的」仍在 host（`pkg/signal` Diff + `maxSignal`）。

为什么这么切：

1. 目标内核会崩。有价值的状态（corpus、crash、决策逻辑）必须放在不会一起崩的 host。
2. executor 需要尽量简单，才少干扰 fuzzing。`docs/internals.md`：*designed to be as simple as possible (to not interfere with fuzzing process)*。
3. 早期曾有 `syz-fuzzer` 跑在 VM 里做生成 / 变异，后来移除，逻辑收回 host。方向是 guest 更薄、host 更厚。

关于「构建」：`make` 是在开发机 / CI 上一次编好二进制，再把 executor 部署到目标机。这和运行时 host（manager）/ guest（executor）分工是两个维度：一个是「在哪编」，一个是「在哪跑」。

**小结**：executor 只跑被告知的程序并回传原始结果，不决定下一步跑什么。决策都在 host 的 `syz-manager` 进程里。
