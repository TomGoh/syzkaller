## 一、先从主线看仓库

阶段 0 已经从运行角度介绍了 `syz-manager`、`syz-executor` 和被测内核。本阶段要做的是把这些职责放回源码目录中。

先看一条简化后的主线：

```text
sys/ 中的 syzlang 描述
          │ syz-sysgen
          ▼
prog/ 中的类型化程序表示
          │
          ├── pkg/fuzzer/ 生成、变异和筛选程序
          │
          ▼
pkg/rpcserver/ + pkg/flatrpc/
          │ 下发程序，回收执行结果与覆盖率
          ▼
executor/ 在目标机上执行系统调用
          │
          ▼
被测内核

辅助路径：
vm/ 管理目标机生命周期
pkg/signal/ + pkg/corpus/ 维护反馈和语料
pkg/report/ + pkg/repro/ 处理崩溃与复现
pkg/cover/ 生成面向人的覆盖率报告
```

沿着这条主线，再看顶层目录会容易很多：

```text
syzkaller/
├── prog/          程序表示，以及生成、变异、最小化等通用算法
├── sys/           syzlang 描述、架构常量和描述代码生成工具
├── executor/      在目标机运行的 C++ 执行器
├── pkg/           fuzzer、signal、corpus、RPC、覆盖率、崩溃处理等 Go 包
├── vm/            目标机后端，包括 qemu、gce、isolated、adb 等
├── syz-manager/   syz-manager 的入口和顶层编排
├── tools/         syz-execprog、syz-prog2c、syz-mutate 等命令行工具
├── dashboard/     syzbot 使用的 Web 服务和数据处理代码
├── docs/          项目文档
└── syz-ci/、syz-hub/、syz-cluster/、syz-verifier/、syz-agent/ 等扩展组件
```

学习前几个阶段时，不必立即阅读所有顶层目录。先围绕 `syz-manager/`、`pkg/fuzzer/`、`prog/`、`sys/`、`pkg/rpcserver/`、`executor/` 和 `vm/` 建立主线，其余部分在用到时再展开。

## 二、主要目录及其职责

| 目录 | 主要职责 | 对应学习阶段 |
|---|---|---|
| `prog/` | 定义 `Prog`、`Call`、`Arg` 等程序表示，并实现生成、变异、序列化和最小化 | 3、4 |
| `sys/` | 保存各操作系统的 syzlang 描述和架构常量；提供 `syz-extract`、`syz-sysgen` 等生成工具 | 3 |
| `pkg/fuzzer/` | 组织生成、变异和 triage（复查新信号并决定是否入库）等反馈驱动的 fuzzing 流程 | 5 |
| `pkg/signal/` | 表示和计算覆盖率信号，例如 `Diff`、`Merge` | 5 |
| `pkg/corpus/` | 管理内存中的语料及其元数据；持久化入口仍由 manager 负责 | 5、8 |
| `pkg/rpcserver/` | 实现 Host 侧 RPC 服务，并为各 executor 连接维护 `Runner` | 8 |
| `pkg/flatrpc/` | 定义 manager 与 executor 之间的 FlatBuffers 二进制消息及其编解码代码 | 8 |
| `executor/` | 解释低层执行指令、准备参数、发起系统调用并采集 KCOV 数据 | 6 |
| `vm/` | 抽象并实现测试机后端；这里的“VM”也包括 `isolated` 物理机 | 8 |
| `syz-manager/` | 读取配置并把 fuzzer、RPC、VM、语料和崩溃处理等模块组织起来 | 8 |
| `pkg/cover/` | 处理覆盖率地址、符号和源码位置，生成覆盖率报告 | 7 |
| `pkg/report/`、`pkg/repro/` | 解析内核崩溃、生成报告并尝试复现和最小化 | 8 |

这里有三个边界需要先说明。

第一，`prog/` 的实现是跨操作系统复用的，但不能简单理解为“完全与 OS 无关”。每个 `Prog` 都属于一个具体的 `prog.Target`，而 `Target` 中的系统调用、类型、资源和常量来自 `sys/` 生成的目标描述。更准确的说法是：**程序表示和算法是通用的，算法处理的数据由具体 OS/arch 的描述决定。**

第二，`syz-manager/` 主要是可执行程序入口和顶层组装层。许多实际功能并不直接写在这个目录中，而是放在 `pkg/fuzzer/`、`pkg/corpus/`、`pkg/rpcserver/`、`pkg/report/` 等可复用包里。因此，阅读 manager 时需要顺着它调用的包继续追踪。

第三，`pkg/cover/` 主要负责把覆盖率地址整理成符号和源码位置，面向报告和分析；“某个覆盖率信号对本轮 fuzzing 是否是新的”主要由 `pkg/signal/` 和 `pkg/fuzzer/` 判断。二者都处理覆盖率，但职责不同。

## 三、构建系统：`make` 生成哪些程序

`Makefile` 的三个顶层目标如下：

```makefile
all:    host target
host:   manager repro mutate prog2c db upgrade
target: execprog executor check_syzos
```

`host` 和 `target` 表示程序将在哪里运行，不表示它们使用哪种语言，也不等同于“当前执行编译命令的机器”。例如，`syz-execprog` 是 Go 程序，但因为它在目标机上运行，所以属于 `target`。

### 1. host 与 target

| 目标组 | 运行位置 | 主要输出 | 默认输出目录 |
|---|---|---|---|
| `host` | 运行 `syz-manager` 的稳定机器 | `syz-manager`、`syz-repro`、`syz-mutate`、`syz-prog2c`、`syz-db`、`syz-upgrade` | `bin/` |
| `target` | VM 或物理 DUT | `syz-execprog`、`syz-executor` | `bin/<OS>_<ARCH>/` |

`syz-executor` 是 C++ 程序；`syz-execprog` 是一个面向手动执行、复现和调试的 Go 工具。持续 fuzzing 的主要执行链是 manager 直接与 executor 通信，并不要求在两者之间再启动一个 `syz-execprog`。

### 2. 三组 OS/arch

`Makefile` 开头定义了三组 OS/arch。它们回答的是三个不同问题：

| 变量 | 表示什么 | 影响的主要产物 |
|---|---|---|
| `HOSTOS/HOSTARCH` | `syz-manager` 等 Host 工具将在哪个平台运行 | `bin/syz-manager` 等 Host 工具 |
| `TARGETOS/TARGETVMARCH` | 被测系统及测试机的机器架构 | `bin/<OS>_<TARGETVMARCH>/syz-execprog` |
| `TARGETOS/TARGETARCH` | executor 进程使用的用户态应用二进制接口（ABI），也就是从哪个架构的测试进程发起系统调用 | `bin/<OS>_<TARGETARCH>/syz-executor` |

通常 `TARGETVMARCH` 与 `TARGETARCH` 相同。例如，从 linux/amd64 Host 为 linux/arm64 目标机编译时，可以明确写成：

```bash
make HOSTOS=linux HOSTARCH=amd64 \
     TARGETOS=linux TARGETVMARCH=arm64 TARGETARCH=arm64
```

如果未设置 `TARGETVMARCH`，`tools/syz-make/make.go` 会让它默认等于 `TARGETARCH`，所以上面的常见情况也可简写为：

```bash
make TARGETOS=linux TARGETARCH=arm64
```

只有测试兼容层时，两者才会有意不同。例如，在 amd64 内核上用 32 位进程测试 compat syscall：

```bash
make TARGETOS=linux TARGETVMARCH=amd64 TARGETARCH=386
```

此时会得到：

- `bin/linux_amd64/syz-execprog`：在 amd64 测试机上运行；
- `bin/linux_386/syz-executor`：以 386 用户态 ABI 发起系统调用。

`bin/` 不会因为切换目标架构而自动清空。因此，先后构建 amd64 和 arm64 后，两个架构目录可以同时存在。需要清理时可使用 `make clean`。

### 3. VM 和物理 DUT 是否使用不同的编译方式

不需要因为目标是物理机就换一套构建目标。QEMU、GCE 或 `isolated` 描述的是**运行时如何获得和管理测试机**；OS/arch 变量描述的是**为哪个平台和 ABI 生成二进制**。两者是不同的问题。

`vm/vm.go` 会导入各个后端，各后端再通过 `vmimpl.Register()` 注册名称。manager 启动后读取配置中的 `"type"`，选择 `qemu`、`isolated` 等后端。因此，同一个 `syz-manager` 二进制可以按配置使用不同后端。

为 arm64 物理 DUT 编译时，仍然使用前面的 arm64 命令。需要额外确认的是：

- 本机具备可用的 arm64 C++ 交叉编译器，否则 Makefile 会提示 executor 未构建；
- DUT 能运行所选 ABI 的二进制；
- DUT 内核已启用 KCOV 等 fuzzing 所需配置。

这些要求来自目标架构和被测内核，不是 `isolated` 后端特有的另一套编译规则。

### 4. 常用构建目标

| 命令 | 作用 |
|---|---|
| `make` | 构建默认的 Host 与 Target 程序 |
| `make host` | 只构建 Host 工具 |
| `make target` | 只构建 `syz-execprog`、`syz-executor` 等 Target 项目 |
| `make manager` | 只构建 `syz-manager` |
| `make executor` | 只构建 `syz-executor` |
| `make execprog` | 只构建 `syz-execprog` |
| `make extract TARGETOS=... SOURCEDIR=...` | 从目标内核源码中提取系统调用常量，更新 `.const` 文件 |
| `make generate` | 运行项目的整套生成流程，不只生成系统调用描述 |

## 四、系统调用描述如何进入二进制

许多构建目标依赖 `descriptions`。这一步把阶段 0 中提到的 syzlang 模型转换成 Go 端和 C++ 端可以直接使用的文件。

当前代码的生成关系如下：

```text
sys/<os>/*.txt       syzlang 接口与类型描述
sys/<os>/*.const     各架构的常量值
          │
          │ bin/syz-sysgen
          ▼
┌──────────────────────────────┬─────────────────────────────┐
│ Go 端                        │ executor 端                │
│ sys/gen/<os>_<arch>.gob.flate│ executor/defs.h            │
│ sys/register.go              │ executor/syscalls.h        │
└──────────────────────────────┴─────────────────────────────┘
```

这些文件都由 `syz-sysgen` 生成，文件头带有 `Automatically generated ... DO NOT EDIT`。修改源描述后，应重新运行生成流程，而不是直接编辑生成文件。

### 1. Go 端保存完整的类型化描述

`sys/gen/<os>_<arch>.gob.flate` 是序列化并压缩后的目标描述，主要包含：

- 系统调用及其属性；
- resource 定义；
- 参数和结构体等类型；
- 架构常量与 flags。

`sys/register.go` 使用 `//go:embed gen/*.gob.flate` 把这些文件嵌入需要目标描述的 Go 程序，并按 OS/arch 注册。manager 取得具体的 `prog.Target` 后，`prog/` 才能按照对应目标的 syscall、类型和 resource 规则生成或变异程序。

### 2. executor 端保存执行所需的表和常量

`executor/executor.cc` 会包含两个生成的头文件：

- `executor/defs.h`：保存 OS/arch、描述版本、数据区布局、fork server 开关、调用属性结构以及必要的 syscall 常量等；
- `executor/syscalls.h`：生成 `call_t` 表，记录调用名称、系统调用号、调用属性和必要的伪调用函数入口。

这里要避免一个常见误解：**executor 不会重新读取完整的 syzlang 类型，也不会在执行时重新判断某个参数是不是 `fd` resource。**

类型和资源关系主要由 Go 端使用。`prog.SerializeForExec()` 会先根据 `Prog` 和 `Target`，把类型化的 `Call/Arg` 降为简单的二进制指令，包括：

- `copyin`：把常量、缓冲区和资源引用写入目标地址；
- 系统调用编号（call ID）、参数数量和低层参数值；
- `copyout`：从返回值或内存中取出结果，供后续调用引用；
- 运行时校验和以及调用属性等辅助指令。

executor 中的 `read_input()`、`read_arg()` 和执行循环只需解释这些低层指令，再通过生成的 `call_t` 表找到实际系统调用号或伪调用函数。这样可以把复杂的类型处理留在 Go 端，使目标机上的 executor 保持相对简单。

对应的数据流是：

```text
syzlang 描述
      ▼
Go 端的 prog.Target + Prog/Call/Arg
      │ prog.SerializeForExec()
      ▼
copyin / call / copyout 等低层执行指令
      │ FlatRPC
      ▼
executor 解释指令并发起真实系统调用
```

### 3. 两端如何防止描述版本不一致

Go 端目标描述带有 `Target.Revision`；同一版本值会作为 `SYZ_REVISION` 编入 executor。executor 与 manager 建立连接时会上报架构、Git 版本和描述版本，`pkg/rpcserver.checkRevisions()` 会逐项比较。如果描述版本或架构不一致，连接会被拒绝。

因此，修改 `.txt` 或 `.const` 后，Host 工具和 executor 都应重新构建。这里需要保持一致的不是“executor 中的一份完整参数类型树”，而是 Go 端生成的执行指令与 executor 端使用的调用编号、属性和目标常量。

### 4. `.descriptions` 文件的作用

`syz-sysgen` 一次会生成多个 OS/arch 的描述文件和两个 executor 头文件，Makefile 很难把每个输出分别写成独立目标。因此，仓库使用 `.descriptions` 作为这一组生成结果的时间戳标记：

1. `descriptions` 先保证 `syz-sysgen` 工具本身是最新的；
2. `.descriptions` 依赖 `sys/*/*.txt`、`sys/*/*.const` 和 `bin/syz-sysgen`；
3. 任何输入较新时，Makefile 重新运行 `bin/syz-sysgen`，随后更新 `.descriptions`。

`.descriptions` 本身不保存系统调用信息，只表示这一组生成文件已经更新。

## 五、本机已有构建结果

当前环境中，`go.mod` 声明 Go 1.26.0；实际可用的 `/usr/local/go/bin/go` 为 Go 1.26.5，`g++` 为 15.2.0。当前 `bin/` 已有以下主要产物：

```text
bin/
├── syz-manager
├── syz-repro
├── syz-mutate
├── syz-prog2c
├── syz-db
├── syz-upgrade
├── syz-sysgen
├── linux_amd64/
│   ├── syz-execprog
│   └── syz-executor
└── linux_arm64/
    ├── syz-execprog
    └── syz-executor
```

用 `file` 检查可见：

- `syz-manager` 和两个架构的 `syz-execprog` 都是静态链接的 Go 可执行文件；
- `linux_amd64/syz-executor` 与 `linux_arm64/syz-executor` 分别是对应架构的静态位置无关（`static-pie`）可执行文件；
- amd64 与 arm64 目录同时存在，说明 `bin/` 会保留先前构建的其他架构产物。

静态链接可以减少目标机对用户态动态库和动态加载器的依赖，但不表示二进制与目标内核 ABI 无关。部署前仍要确认目标架构、用户态 ABI 和内核配置正确。

Makefile 会提示优先通过 `tools/syz-env` 使用项目建议的工具链。直接构建也可能成功，但学习过程中应检查完整构建输出，尤其不能只看到 `syz-execprog` 生成，就假定交叉编译的 executor 也已经生成。

## 六、目录如何映射到 VM 和物理 DUT

阶段 0 已经介绍了 VM 和物理机两种部署方式。这里不再重复进程职责，而是标出各目录实际位于哪一侧。

### 1. QEMU 后端

```text
[Host]
  syz-manager/
  pkg/fuzzer/、pkg/signal/、pkg/corpus/
  prog/ + sys/gen/
  pkg/rpcserver/、pkg/flatrpc/
  pkg/report/、pkg/repro/、pkg/cover/
  vm/qemu/                 启动、监控和销毁 QEMU 实例
  workdir/                 corpus.db、crashes/ 等持久化数据
      │
      │  QEMU 启动测试机
      │  SCP 部署 executor，SSH 启动进程
      │  FlatRPC 通过 TCP 连接传输；当前 qemu 后端用 SSH 反向端口转发建立可达路径
      ▼
[QEMU VM / Target]
  syz-executor
      │ fork
      ▼
  瞬态子进程 ──syscall──► 被测内核
      ▲                         │
      └──────── KCOV ──────────┘
```

QEMU 配置中的几个路径不要混淆：

- 顶层 `image` 通常是虚拟机磁盘或根文件系统镜像；
- `vm.kernel` 是可选的可启动内核文件，例如 `bzImage` 或 `Image`，由 QEMU 的 `-kernel` 参数使用；
- `kernel_obj` 是 Host 侧的内核构建目录，用于符号化、覆盖率报告等工作，其中通常包含 `vmlinux`。它不等同于 QEMU 直接启动的内核文件。

### 2. `isolated` 物理机后端

```text
[Host]
  manager、fuzzer、prog、sys/gen、RPC、语料和报告相关目录
  vm/isolated/             管理已经存在的物理 DUT
  workdir/                 corpus.db、crashes/ 等持久化数据
      │
      │  SCP 把 executor 复制到 target_dir
      │  SSH 启动 executor，并读取远端内核日志
      │  SSH -R 建立反向端口转发，承载 FlatRPC 连接
      ▼
[物理 DUT / Target]
  syz-executor
      │ fork
      ▼
  瞬态子进程 ──syscall──► DUT 本机内核
      ▲                         │
      └──────── KCOV ──────────┘
```

`vm/isolated/` 不创建物理机，也不替换 DUT 的内核镜像。它主要负责：

- 通过 SSH 检查和准备目标机；
- 通过 SCP 部署目标端程序；
- 启动 executor 并建立反向端口转发；
- 读取远端 console/dmesg，并可选读取 pstore；
- 在配置允许时尝试重启或修复目标机。

因此，QEMU 与物理 DUT 的主要差别位于 `vm/` 后端和目标机生命周期管理。程序生成、反馈判断、语料管理、RPC 消息以及 executor 的执行机制并不会因为后端不同而另写一套。

### 3. Host 与 Target 的职责边界

可以把整体分工概括为：**Host 负责选择接下来做什么，Target 负责执行并返回原始结果。** 但这不表示 executor 只调用一个 `syscall()` 就结束。它还承担了大量执行机制。

| Host 侧职责 | 主要目录 |
|---|---|
| 生成、变异、最小化程序 | `prog/`、`pkg/fuzzer/` |
| 判断覆盖率信号是否为全局新增 | `pkg/signal/`、`pkg/fuzzer/` |
| 管理语料并持久化 `corpus.db` | `pkg/corpus/`、`syz-manager/` |
| 管理 VM 或 DUT，提供 RPC 服务 | `vm/`、`pkg/rpcserver/` |
| 解析、保存和复现崩溃 | `pkg/report/`、`pkg/repro/`、`syz-manager/` |
| 把覆盖率 PC（程序计数器地址）转为符号和源码位置 | `pkg/cover/` |

| Target 侧 executor 的职责 | 代表代码 |
|---|---|
| 与 manager 握手并接收执行请求 | `executor/executor_runner.h` |
| 解释 `copyin`、call、`copyout` 等低层指令 | `executor/executor.cc` 的执行循环、`read_input()`、`read_arg()` |
| 准备内存、资源引用和系统调用参数 | `copyin()`、`copyout()` |
| 调度系统调用，并按选项使用线程执行 | `schedule_call()`、`execute_call()` |
| 采集并整理 KCOV 数据 | executor 的 coverage 相关代码 |
| 执行沙箱、超时和子进程管理 | `executor/common*.h` |

executor 可以过滤或整理本次执行产生的数据，但它不维护全局 corpus，也不决定某条覆盖率是否足以影响下一轮 fuzzing。全局判断仍在 Host 侧完成。

本阶段需要形成的最终认识是：

1. `sys/` 提供目标知识，`prog/` 用这些知识表示和操作程序；
2. `pkg/fuzzer/`、`pkg/signal/` 和 `pkg/corpus/` 在 Host 侧组成反馈闭环；
3. `pkg/rpcserver/` 与 `pkg/flatrpc/` 连接 Host 和 Target；
4. `executor/` 负责低层执行，`vm/` 负责目标机生命周期；
5. QEMU 与物理 DUT 的差异主要在 `vm/` 后端，不在 fuzzing 核心算法。
