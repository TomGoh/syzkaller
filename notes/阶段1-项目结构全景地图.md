## 三、构建系统：`make` 产出什么（阶段 1 重点）

Makefile 顶层三行（`Makefile:114-116`）：

```makefile
all:    host target
host:   manager repro mutate prog2c db upgrade      # 跑在 HOST 上的 Go 二进制
target: execprog executor check_syzos               # 跑在 目标机 上的二进制
```

**`host` vs `target` 的划分 = 阶段 0 "manager 在 host / executor 在目标机" 的构建体现**：

| 组 | 编译给谁 | 输出路径 | 代表二进制 |
|---|---|---|---|
| **host** | Go，宿主机（`GOOS=HOSTOS`） | `bin/syz-*` | `syz-manager`(大脑)、`syz-repro`(复现)、`syz-mutate`、`syz-prog2c`、`syz-db`、`syz-upgrade` |
| **target** | 交叉编译，目标机（`GOOS=TARGETGOOS`） | `bin/{OS}_{ARCH}/syz-*` | `syz-executor`(C++,唯一非Go)、`syz-execprog` |

两个细节：
1. 输出路径不同：host 直接进 `bin/`；target 进 `bin/linux_amd64/` 架构子目录（为目标机交叉编译）。
2. executor 是唯一 C++（`Makefile:136`）：`$(CXX) -o bin/.../syz-executor executor/executor.cc ...`，静态、极简。

### 补正：其实是**三个 OS/arch 对**，不是两个（`Makefile:4-17`）

上面 host/target 是简化版。精确说，syzkaller 有 **3 个 OS/arch 对**：

| 对 | 含义 | 决定谁 | 产物去哪 |
|---|---|---|---|
| **HOSTOS/HOSTARCH** | syz-manager 运行的机器 | host 工具 | `bin/`（syz-manager 等） |
| **TARGETOS/TARGETVMARCH** | **被测 OS/内核**的 arch | `syz-execprog` | `bin/{OS}_{TARGETVMARCH}/`（`Makefile:165`） |
| **TARGETOS/TARGETARCH** | **发起 syscall 的测试进程**的 arch | `syz-executor` | `bin/{OS}_{TARGETARCH}/`（`Makefile:135-136`） |

**为什么后两个要分开——测 compat（兼容层）syscall**：amd64 内核（`TARGETVMARCH=amd64`）上跑 386 测试进程（`TARGETARCH=386`）去打 32 位 compat 路径。此时：
- `syz-executor`（真正发 syscall 的进程）是 386 → `bin/linux_386/syz-executor`
- `syz-execprog` 是 amd64 → `bin/linux_amd64/syz-execprog`
→ **executor 和 execprog 会落在不同 arch 子目录**！这正是 executor 用 `TARGETARCH`、execprog 用 `TARGETVMARCH` 的由来。官方例子：`make TARGETVMARCH=amd64 TARGETARCH=386`。
不做 compat 时（如只设 `TARGETARCH=arm64`），syz-make 把 `TARGETVMARCH` 也归一成 arm64，两者一起进 `bin/linux_arm64/`。

**`bin/` 是累加的**：换 target arch 不清旧的，多试几次会看到多个 `linux_*/` 子目录并存。想清爽重来：`make clean`（`Makefile:409`）或 `rm -rf bin`。

### 常用单目标（`Makefile`）
- `manager`(:161) `repro`(:180) `mutate`(:183) `prog2c`(:189) `db`(:198) → host Go 工具
- `execprog`(:164) → target Go 工具；`executor`(:118) → target C++
- `extract`(:238) → syz-extract（从内核头抽常量）；`generate`(:246) → 重跑代码生成

## 四、隐藏关键环：`descriptions` / syz-sysgen（syzlang→代码）

几乎每个目标都挂 `descriptions` 依赖（`Makefile:118,161,164...`）。这一步（`Makefile:143-153`）是阶段 0 那条"syzlang→代码"编译链的真身：

```
sys/*/*.txt + sys/*/*.const ──(syz-sysgen)──► ① sys/gen/*.gob.flate  (每OS/arch一个,序列化+压缩的描述)
                                              + sys/register.go        (//go:embed gen/*.gob.flate → 嵌进Go二进制)
                                              ② executor/defs.h        (每call属性结构 call_attrs_t 等, 194KB)
                                              ③ executor/syscalls.h    (syscall 名→号大表 {"accept",30}..., 4.2MB)
```

**关键洞察**：同一份 syzlang 描述被 `syz-sysgen` 编译成**两边都用**的产物——Go 侧（`sys/gen/*.gob.flate`，经 `sys/register.go` 的 `//go:embed` 嵌进每个 Go 二进制）+ C++ 侧（`executor/defs.h`、`syscalls.h`，被 `executor.cc:25,498` `#include`）。这解释了"结构感知"如何同时贯穿生成端(Go)与执行端(C++)：它们读同一份描述的两种产物。因此 `descriptions` 是所有构建的前置——不先 codegen，两边都编不了。

（`.descriptions` 是个 stub 文件，代表 syz-sysgen 一次性生成的所有文件，见 `Makefile:143-145` 注释。）

### 深化 FAQ：为什么这么多目标都依赖 descriptions？两侧依赖它各为了干啥？

#### 一、descriptions 是"编译期代码生成"，产物是两侧**必须 include / embed 的源文件**

syz-sysgen 把 syzlang `.txt` **一次性**编译成两套产物（文件头都写着 `Automatically generated by syz-sysgen; DO NOT EDIT`）：

| 侧 | 产物 | 怎么被吃进二进制 |
|---|---|---|
| **Host / Go** | `sys/gen/*.gob.flate`（每个 OS/arch 一个，序列化+压缩的完整 syscall 描述）+ `sys/register.go` | `sys/register.go` 用 **`//go:embed gen/*.gob.flate`** 把描述**嵌进每个 Go 二进制** |
| **DUT / C++** | `executor/defs.h`(194KB, 每个 call 的属性结构 `call_attrs_t` 等) + `executor/syscalls.h`(4.2MB, syscall 名→号大表) | `executor.cc` 第 **25、498 行 `#include`** 它们 |

关键在于：这些都是**源码级依赖**。Go 代码要 embed 那些 `.gob.flate` 才能编译，`executor.cc` 要 include 那两个头才能编译。**文件不存在或过期 → 两边都编不过**。所以 Makefile 只能把 `descriptions` 挂成几乎所有目标的前置。

#### 二、为什么是"这么多"目标 —— 没有描述，每个二进制都是空壳

依赖它的不是某几个，而是**几乎全部**：凡是要**操作程序**的东西都离不开这份 syscall 元信息——

- Go 侧：manager(生成/变异)、prog2c(翻译)、mutate、execprog、repro、db …… 不知道 `open` 有几个参数、`fd` 是 resource，就什么都做不了；
- C++ 侧：executor 要把字节流**解码成真实 syscall**，必须有 syscall 表（`{"accept", 30}` 这种名→号）和参数布局。

它是两种语言**共同编译所依赖的地基**，所以"到处都依赖"。

#### 三、两侧都依赖它，分别"为了干啥"（核心：一对编码器/解码器）

**同一份描述 = 单一真相源；但两侧拿它做的是一对互补的活**：

```
        同一份 sys/*.txt (syzlang)
                 │ syz-sysgen 一次生成
      ┌──────────┴──────────┐
      ▼                     ▼
 Host/Go 产物            DUT/C++ 产物
 sys/gen/*.gob.flate     executor/syscalls.h + defs.h
      │                     │
   【编码端】              【解码端】
 生成/变异程序           解码那串字节流
 + 序列化成字节流  ──RPC──► + 发起真实 syscall
```

| 侧 | 用描述干的活 | 角色 |
|---|---|---|
| **Host（Go）** | 用 syscall 元信息**生成/变异**程序，再**序列化**成执行器字节流 | **编码器**：决定跑什么、编成字节 |
| **DUT（executor）** | 用 syscall 表 + 布局把字节流**解码**，还原成真正的系统调用去 execute | **解码器**：把字节变回真 syscall |

**最关键的洞察 —— 为什么两侧必须来自同一次生成**：

Host 用描述**编码**、DUT 用描述**解码**，这是一对严丝合缝的编码器/解码器。两边必须对"第 2 个参数是 fd resource、占几字节、怎么排布"达成**逐位一致**。如果 host 按 A 版描述序列化、executor 按 B 版解码 → executor 会把参数读错位 → 乱执行 / 假崩溃。

syz-sysgen **从同一份 `.txt` 一次同时生成两套**，从根上保证"host 说的字节序 = executor 读的字节序"。这也是为什么**改了 `.txt` 必须两侧一起重编**——只重编一边就会协议错位。

#### 四、`.descriptions` 这个 stub 为什么这么写

syz-sysgen 一次生成**所有**文件（十几个 OS/arch 的 `.gob.flate` + 两个 C 头），没法把每个文件做成独立 make 目标，于是用一个 stub 文件 `.descriptions` 代表"全部生成物已最新"。所有构建都依赖这个 stub → `.txt`/`.const` 一改就触发整体重新 codegen（`Makefile:143-153` 注释说的正是此事）。

#### 五、和阶段 2 脊柱的衔接（预告）

这对编解码器正是阶段 2 数据流上的两棒：`prog.SerializeForExec`（host 编码）↔ executor 里的解码执行。改一处 `.txt` 之所以牵动两侧，根源就在这里。

> 注：`make` 顶部会提示 "run command via tools/syz-env for best compatibility" —— 官方推荐用 `syz-env`(容器) 保证工具链一致，本机直接 make 也能成功。

1. **生成/变异全在 HOST**（`prog/`+`pkg/fuzzer/`）；目标机只"执行+采集"，不做决策。
2. **`sys/` 一份描述编到两端**：Go 产物(`sys/*/gen`)链进 host manager；C 头(`executor/defs.h`/`syscalls.h`)编进 target executor。
3. **VM 与物理机差异只在外圈一行**（`vm/qemu`↔`vm/isolated`）+ 通信方式；HOST 大脑与 TARGET 的 executor/内核/子进程结构两种情形完全一致。

### 深化 FAQ：是不是"除执行相关外，全部逻辑（语料保存/构建/管理）都在 Host，Guest 只留最简单的执行部分"？

**结论：方向对，但分界线是「决策 vs 执行」，不是「复杂 vs 简单」。**

> 精确说法：**决策逻辑（往哪走）在 Host；执行机制（照着做 + 采集原始数据）在 DUT。** "简单"是相对的——executor 其实做了不少事，只是这些事**全是执行机制，没有一丝 fuzzing 决策**。

**Host（大脑）：所有决策 + 持久化 + 管理**

| 职责 | 目录 |
|---|---|
| 生成 / 变异 / 最小化 | `prog/` + `pkg/fuzzer/` |
| "什么算新信号"的判定 | `pkg/signal/`（Diff/Merge）、`maxSignal` |
| triage、入库决策、syscall 组合优先级 | `pkg/fuzzer/`、`prog/prio.go`(ChoiceTable) |
| 语料**保存**（corpus.db / workdir） | `pkg/corpus/`、`syz-manager/` |
| 崩溃解析 / 存储 / 复现 | `pkg/report/`、`pkg/repro/` |
| 覆盖率符号化（PC→源码行） | `pkg/cover/` |
| VM/DUT 管理、RPC 服务端 | `vm/`、`pkg/rpcserver/` |

**DUT / executor（手脚）：只有执行机制，无任何 fuzzing 决策**

（从 `executor/executor.cc` 函数清单核对，这些也确实没法搬到 host）

| executor 做的事 | 函数 | 属于 |
|---|---|---|
| 与 manager 握手、收程序、回状态 | `receive_handshake`/`receive_execute`/`reply_execute` | 协议 |
| **解码**序列化程序（编解码器的解码端） | `read_input`/`read_arg`/`read_const_arg`/`read_result` | 解码 |
| 把参数摆进内存 | `copyin`/`copyout`/`swap` | 执行准备 |
| fork 短命子进程 + **threaded 执行**（应对阻塞 syscall） | `schedule_call`/`worker_thread`/`execute_call`/`thread_create` | 执行 |
| 采集 KCOV 原始覆盖率 + **本地少量 dedup** | `dedup`/`coverage_filter`/`convert` | 采集 |
| 经共享内存/flatrpc 回传结果 | `write_call_output`/`finish_output`/`mmap_output` | 回传 |
| 沙箱、超时/挂起处理 | sandbox_*、timeout 逻辑（阶段 6 细看） | 隔离 |

它**不做**：生成、变异、最小化、corpus、符号化、"全局是否新覆盖"的判定、crash 解析——一件都不碰。

> 唯一"疑似逻辑"：executor 里有 `dedup` 会对 signal 做**本地**去重，但那只是为了**少传点数据**；"这条覆盖对整个 fuzzing 是不是新的"这个全局判定仍在 host（`pkg/signal` Diff + `maxSignal`）。所以它依然是执行支持，不是决策。

**为什么这么切（三条理由）**：
1. **目标内核会崩** → 有价值的状态（corpus、crash、fuzzing 大脑）必须放在崩不着的 host 才能存活。
2. **executor 必须极简才不干扰 fuzzing**：`internals.md` 原话 *"designed to be as simple as possible (to not interfere with fuzzing process)"*。越简单，引入的覆盖噪声/自身 bug/资源占用越少 → 结果越保真。
3. **历史佐证**：早期有 `syz-fuzzer` 跑在 VM 里做生成/变异，后被**移除**、逻辑收回 host（即我们核对到的"这版无 syz-fuzzer"）。演进方向 = 让 guest 更薄、host 更厚。

**关于"构建"的小修正**：`make` 是 **build-time** 在开发机/CI 上一次性编好所有二进制，再把 executor **部署**（scp/镜像）到目标机。这与 runtime 的 host(manager)/guest(executor) 分工是两个维度：一个是"在哪编"，一个是"在哪跑"。

**一句话记牢**：executor 名副其实——一个忠实的"执行器"：只跑被告知的程序、回传原始结果，不做任何"下一步跑什么"的智能。所有智能都在 host 的 syz-manager 进程里。
