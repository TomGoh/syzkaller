# 阶段 4：生成与变异——程序怎么来的

> 本阶段的目标：理解 syzkaller 如何从一份 `Target` 描述出一段可执行的 `prog.Prog`，以及它怎样在保留尽量多有效结构的前提下修改已有程序。
>
> 示例目标：Linux/arm64 的 KVM 接口。示例使用的调用链是 `openat$kvm → KVM_CREATE_VM → KVM_CREATE_VCPU → KVM_ARM_VCPU_INIT → KVM_RUN`。它用于观察结构，不表示这就是唯一正确的 KVM 使用顺序。

---

## 一、这一阶段位于整体流程的什么位置

前面几个阶段已经建立了两件事：

1. syzlang 为每个目标定义系统调用、参数类型、资源和常量；
2. `prog.Prog` 是 Go 端保存的一份**结构化测试程序**。其中每一个 `prog.Call` 指向一种调用描述，每个 `prog.Arg` 是该调用参数在本次程序里的具体值，`ResultArg` 还可以引用前面调用产生的资源。

阶段 4 要回答的是：这份结构化程序最初如何产生，又如何变成新的候选程序？

```text
syzlang / Target 描述
        │
        ▼
Target.Generate ──► 一份新的 prog.Prog
        │
        ▼
Prog.Mutate ──────► 从已有 prog.Prog 得到变体
        │
        ▼
manager / queue ─► executor 执行，返回 signal、覆盖率或崩溃结果
```

最后一行属于前面的执行链路和后面的反馈链路。本阶段只聚焦前两步。这里的“有效”也要先限定含义：生成器主要保证类型、资源引用、地址分配等**结构约束**尽量成立；它并不理解 KVM 的完整状态机，不能保证每段程序一定具有业务语义、一定成功或一定触发新路径。

---

## 二、开始前先区分四个对象

后文会同时出现几个相近的名字，先把它们分开。

| 名称 | 它是什么 | 在本阶段的作用 |
| --- | --- | --- |
| `Target` | 一个目标平台的知识库，例如 `linux/arm64`；包含调用、类型、资源、常量和内存布局 | 告诉生成器“可以生成什么” |
| `prog.Prog` | 一次待测程序的 Go 端结构化表示 | 生成与变异的输入、输出 |
| `state` | 生成某个位置时的临时上下文；记录此前已出现的资源、文件名、字符串和已分配的内存/VMA | 告诉生成器“前面已经有什么可以用” |
| `ChoiceTable` | 调用选择表；保存“某个调用后面更适合接什么调用”的权重 | 决定下一次优先选哪类调用 |

`state` 不是要发送给 executor 的数据。它只在 Go 端生成过程中存在。生成结束后，真正留下的是 `prog.Prog`；再由阶段 2、阶段 3 中的序列化过程把它变为 executor 可读取的指令。

## 三、从空程序到 `prog.Prog`：`Target.Generate`

主入口在 `prog/generation.go`：

```go
func (target *Target) Generate(rs rand.Source, ncalls int, ct *ChoiceTable) *Prog {
	p := &Prog{Target: target}
	r := newRand(target, rs)
	s := newState(target, ct, nil)
	for len(p.Calls) < ncalls {
		calls := r.generateCall(s, p, len(p.Calls))
		for _, c := range calls {
			s.analyze(c)
			p.Calls = append(p.Calls, c)
		}
	}
	// 超出目标长度时裁掉尾部，随后修正并校验。
	return p
}
```

可以把它读成一个循环：

1. 新建空的 `Prog`、随机数发生器 `randGen` 和空 `state`；
2. 选择一种下一个调用；
3. 为该调用递归生成所有参数；
4. 如果参数需要某种尚未拥有的资源，先生成产生该资源的前置调用；
5. 将这批调用逐个分析并加入程序，让后续调用看见刚产生的资源；
6. 调整到目标调用数，执行 `sanitizeFix` 和一致性检查。

因此，`ncalls` 不是严格的“循环次数”。一次挑中 `KVM_CREATE_VCPU`，可能会因为它需要 VM 资源而顺带加入一个创建 VM 的调用；最后再根据上限裁剪尾部。

### 3.1 `state` 为什么必须随程序推进

`state` 的定义在 `prog/analysis.go`。它会保存：

- 已产生、按资源类型分类的返回值；
- 已用过的文件名与字符串；
- 用户内存分配器 `memAlloc`；
- 虚拟内存区域分配器 `vmaAlloc`；
- 当前的 `ChoiceTable`，以及可选的语料上下文。

每加入一条调用，`s.analyze(c)` 就更新这些记录。例如 `KVM_CREATE_VM` 返回一个 `fd_kvm_vm`，分析后该返回值会放入对应资源集合；接下来生成 `KVM_CREATE_VCPU` 的第一个参数时，就有一个可用的 VM fd 可引用。

这里的“分析”不是运行系统调用，也不是猜测内核结果。它依据 syzlang 中 `KVM_CREATE_VM` 的返回类型，预先把这条调用视为能提供这种资源。实际执行是否成功，要到 executor 运行时才能知道。

### 3.2 先选调用，再生成参数

`randGen.generateCall` 在 `prog/rand.go` 中完成调用选择。若程序前面已有调用，它通常随机选其中一条作为 **bias call（偏置调用）**，再让 `ChoiceTable` 给出一个更适合跟在它后面的候选调用；偶尔会完全随机选择，避免长期只在高权重组合附近活动。

选中调用后，`generateParticularCallUnsafe` 递归生成各个参数，并在最后：

- 处理条件字段；
- 根据已经生成的缓冲区、数组等内容填充长度字段；
- 返回“前置调用链 + 本次调用”。

所以“选择 `KVM_CREATE_VCPU`”只决定了中心目标，真正加入 `Prog` 的可能是一串调用。

## 四、KVM 例子：资源如何自动补出前置调用

先看关键的 syzlang 关系：

```text
openat$kvm(...)                         fd_kvm
ioctl$KVM_CREATE_VM(fd fd_kvm, ...)     fd_kvm_vm
ioctl$KVM_CREATE_VCPU(fd fd_kvm_vm, ...) fd_kvm_vcpu
ioctl$KVM_RUN(fd fd_kvm_vcpu, ...)
```

右侧的 `fd_kvm`、`fd_kvm_vm`、`fd_kvm_vcpu` 是资源类型，而不是普通整数。生成 `KVM_RUN` 的第一个参数时，`ResourceType.generate` 大致按下面的顺序工作：

```text
需要 fd_kvm_vcpu
  │
  ├─ state 中已有兼容的 vcpu fd？有：引用一个已有结果
  │
  └─ 没有：寻找能返回 fd_kvm_vcpu 的构造调用
               │
               ▼
        KVM_CREATE_VCPU 还需要 fd_kvm_vm
               │
               ▼
        再递归寻找 KVM_CREATE_VM
               │
               ▼
        KVM_CREATE_VM 需要 fd_kvm，于是生成 openat$kvm
```

这会形成类似下面的结构：

```syz
r0 = openat$kvm(AT_FDCWD, &AUTO="/dev/kvm\x00", O_RDWR, 0)
r1 = ioctl$KVM_CREATE_VM(r0, AUTO, 0)
r2 = ioctl$KVM_CREATE_VCPU(r1, AUTO, 0)
ioctl$KVM_RUN(r2, AUTO, 0)
```

`r0`、`r1`、`r2` 分别是前面调用的 `ResultArg`，后面的参数用这些结果建立依赖。也就是说，生成器不是先随机填一个整数再希望它刚好是 fd；它知道“这里需要 VM fd”，因而优先寻找能产生它的调用。

### 4.1 资源机制保证了什么，又没有保证什么

它通常能保证：

- `KVM_CREATE_VCPU` 不会凭空引用一个从未在结构中产生的 VM 资源；
- 同类资源会尽量复用已产生的结果；
- 若没有结果，生成器可以递归补入 syzlang 宣称的构造调用。

它不能保证：

- `/dev/kvm` 打开一定成功；
- 创建 VM、创建 vCPU 的 ioctl 一定成功；
- 调用顺序满足 KVM 的全部状态要求；
- 参数取值一定在内核允许的语义范围内。

例如，生成器可能生成了 VM 和 vCPU，却把 `KVM_RUN` 放在 `KVM_ARM_VCPU_INIT` 之前。资源链在类型上没有问题，但其执行结果可能是失败。这正是 fuzzer 有意保留的探索空间；若模型把所有内核状态规则硬编码进去，覆盖面反而会被过早限制。

## 五、`ChoiceTable`：为什么调用排列不是完全随机

资源解决的是“参数需要什么值”。但在还未决定下一条调用之前，生成器还要回答“这次选哪一种调用”。`ChoiceTable` 处理的是这个问题。

它的每一行可理解为：给定前一个调用 A，候选调用 B 的相对权重是多少。实际选择时以加权随机方式抽样，不是永远选最大值；还有一小部分概率直接随机选调用。

### 5.1 权重的两个来源

`prog/prio.go` 中的总权重来自静态优先级与动态优先级。

- **静态优先级**从 Target 的类型关系推导。例如 A 产生某资源，而 B 消费该资源，则 A → B 的权重提高；文件名、VMA、指针指向的结构等关系也可贡献权重。
- **动态优先级**从已有语料统计。若历史上的一份程序里 A 出现在 B 之前，A → B 的计数会上升；它统计的是“前后出现过”的组合，不只限于相邻两条调用。

两者再经过归一化合并。静态关系给生成器一个没有语料时也能工作的起点；动态关系让它逐渐学习当前语料中实际常见、可能有效的组合。

### 5.2 在受限 KVM 调用集上的一次观测

为了避免其他调用干扰，我只启用了 `openat$kvm`、创建 VM/vCPU、设置内存区、初始化和运行 vCPU 等 KVM 调用，并用空语料构建 `ChoiceTable`。观测到的静态权重包括：

| 前一调用 | 候选后续调用 | 观测到的权重 |
| --- | --- | ---: |
| `openat$kvm` | `KVM_CREATE_VM` | 31 |
| `KVM_CREATE_VM` | `KVM_CREATE_VCPU` | 18 |
| `KVM_CREATE_VM` | `KVM_SET_USER_MEMORY_REGION` | 18 |
| `KVM_CREATE_VCPU` | `KVM_RUN` | 14 |

这些数值是这次受限调用集、归一化方式和代码版本下的结果，不是 KVM 接口的固定分数。它们说明的是方向：打开 KVM 之后更值得尝试创建 VM；有了 VM 后更值得尝试设置内存或创建 vCPU；有了 vCPU 后更值得尝试运行它。

`ChoiceTable` 与资源递归是互补关系：前者把程序朝更有联系的调用组合引导，后者在某个参数真的需要资源时补出具体生产者。仅有前者，仍可能选到一个暂时无法使用的资源调用；仅有后者，则调用序列的总体组合更接近盲选。

## 六、已有程序如何改变：`Prog.Mutate`

生成负责从空白处开始；变异负责从一个已有 `Prog` 附近继续探索。入口在 `prog/mutation.go` 的 `Prog.Mutate` / `MutateWithOpts`。

一次变异不是必然只做一个动作。默认配置为多次尝试：从若干操作中按权重选一个，操作因条件不满足而失败时可以继续尝试。这样既能做很小的参数扰动，也能加入新的调用或语料片段。

| 操作 | 它如何修改程序 | KVM 例子 |
| --- | --- | --- |
| 插入调用 | 在某个位置生成一条调用；必要时同时插入资源前置链 | 在程序中插入 `KVM_CREATE_VCPU`，并补出所需的 VM 创建链 |
| 删除调用 | 删除一条调用，并修复引用它的后续资源参数 | 删除 `KVM_CREATE_VM` 后，使用其 VM fd 的参数改成默认资源值 |
| 变异参数 | 选一个可变参数，按其类型重新生成或扰动 | 改 `KVM_ARM_VCPU_INIT` 的 feature 字段 |
| 拼接语料 | 把另一份语料程序的克隆插入当前程序，再按上限裁尾 | 将已知有价值的调用片段带入当前程序 |
| 压扁复杂内存 | 将适合的复杂指针对象表示为通用字节内存 | 对较复杂的嵌套用户内存结构做更粗粒度探索 |

### 6.1 参数变异不是“随机改一个字节”

`mutateArg` 会从程序的参数树收集候选项，并按类型给不同优先级。常量参数不能任意变；资源参数需要保持资源类型；指针、VMA、长度、标志位和普通整数各有自己的变异方式。修改后会重新处理条件字段和相关长度。

在一份 KVM 程序上的一次实际观测如下：

```diff
- ioctl$KVM_ARM_VCPU_INIT(r2, 0x4020aeae, &(0x7f00000000c0)={0x5})
+ ioctl$KVM_ARM_VCPU_INIT(r2, 0x4020aeae, &(0x7f00000000c0)={0x5, 0x43})
```

这里第三个参数是 `kvm_vcpu_init` 结构。`{0x5}` 表示 target 值为 5，后面为零的字段和固定填充可省略打印；变异后 `{0x5, 0x43}` 表示 feature 字段被填为 `0x43`。这次变化仍保持“该参数是指向这个结构的指针”以及结构字段布局，远比随意破坏一段 executor 字节流更容易抵达内核的深层分支。

长度字段是一个容易误解的例外。程序生成完成后，syzkaller 会通常根据缓冲区或数组的实际内容推导长度；但有意变异长度字段时，变异器会保留这个不一致值，才能测试内核对错误长度的处理。

### 6.2 删除调用后为什么还有“坏程序”

删除并不是简单地把一行文本擦掉。`Prog.RemoveCall` 会遍历后续参数：若它们引用被删除调用产生的 `ResultArg`，则把引用替换为该资源类型的默认值。

对阶段 3 的 KVM 示例删除 `KVM_CREATE_VM` 后，观察到的结果是：

```syz
r0 = openat$kvm(AT_FDCWD, &AUTO="/dev/kvm\x00", O_RDWR, 0)
ioctl$KVM_SET_USER_MEMORY_REGION(0xffffffffffffffff, AUTO, &AUTO={...})
r1 = ioctl$KVM_CREATE_VCPU(0xffffffffffffffff, AUTO, 0)
ioctl$KVM_ARM_VCPU_INIT(r1, AUTO, &AUTO={0x5})
ioctl$KVM_RUN(r1, AUTO, 0)
```

原先 VM fd 的引用没有悬空，而是变成 `0xffffffffffffffff`，即该资源的默认无效值。这使 `Prog` 的内部引用结构仍可序列化、可执行，但不承诺这些 ioctl 会成功。这样的变体仍有价值：错误句柄、错误顺序和失败路径也可能触及内核代码；而真正发现价值要由执行后的反馈决定。

### 6.3 插入调用与拼接语料

插入调用时，变异器会先在插入位置重建当时的 `state`，再调用与生成阶段相同的资源感知生成逻辑。因此插入一个资源消费者时，也可能插入其所需的构造链。

拼接语料的当前实现会把另一份语料程序的完整克隆插入当前程序的随机位置，再从末尾删除调用以满足最大调用数。拼接并不等于安全地“合并两段可执行业务流程”：两段程序之间的资源和顺序可能并不协调。它的目的，是把语料中已经证明有某些执行价值的调用组合带入新的上下文。

### 6.4 何时会出现 `ANY`

“压扁复杂内存”操作涉及 `ANY`，所以只在这里引入它。某些指针指向的对象层次深、内容复杂，syzkaller 可以把它改写为一段通用的字节级内存表示；这称为 squash，结果类型常显示为 `ANY`。它会保留尺寸和其中需要保留的资源元素，但不再强制维持原有复杂结构的每个高层字段关系。

这是一种有意放宽结构的探索方法，不是普通参数变异的默认结果。阶段 3 的 `kvm_vcpu_init` 一类小型固定结构通常不是理解 squash 的好例子；理解它时应想到复杂的嵌套缓冲区、数组或结构图。

## 七、最小化：不是反向变异，而是借助外部判定删减

`prog.Minimize` 在 `prog/minimization.go`。它接受一份程序、关注的调用位置、模式和一个 `pred`（predicate，判定函数）。判定函数会实际执行候选程序并回答：“我关心的性质还在吗？”

```text
候选程序 P
   │ 尝试删除一个调用或简化一个参数
   ▼
外部 pred 执行候选程序
   │
   ├─ 性质仍在：接受这个更小的候选
   └─ 性质消失：撤销这次简化，尝试别处
```

这里的“性质”取决于调用者：可以是仍然触发同一崩溃、仍然覆盖目标 signal，或保留某个快照/调用相关条件。最小化器本身不懂“什么是崩溃”或“什么是好覆盖率”；它只根据 `pred` 给出的真或假做删减。

因此它和 `Mutate` 的方向相反，但机制不同：

- `Mutate` 主动制造附近的新候选，等待执行反馈判断价值；
- `Minimize` 已经有一个被证明有价值的程序，反复请求外部反馈以移除不必要部分。

阶段 5 会把这里的 `pred` 与执行、signal、triage 等反馈流程接起来。本阶段只需记住：没有外部执行反馈，最小化无法判断某次删除是否可以保留。

## 八、一次小型实验说明了什么

本阶段用临时 Go 程序加载 `linux/arm64` Target，只启用少量 KVM 调用，做了三类只读式观察：

1. 计算空语料下的静态 `ChoiceTable` 权重，得到前文的 KVM 依赖方向；
2. 调用 `Target.Generate`，观察它能产生资源相连的 fd 链；生成结果也可能在 KVM 状态顺序上不理想；
3. 对阶段 3 的示例执行删除调用和参数变异，得到前文的无效默认 fd 与 feature 字段变化。

它们支持以下结论：

- 生成器知道类型、资源、地址和调用间的统计关联；
- 变异器会维护 `Prog` 的内部结构，但保留错误参数、失败 fd、错误顺序等探索空间；
- “能被序列化并交给 executor”与“该 ioctl 在当前内核状态下一定成功”是不同层次的性质。

## 九、本阶段应带走的模型

```text
Target
  ├─ 调用和参数类型 ──► 递归生成参数
  ├─ 资源生产/消费关系 ─► 补出前置调用、引用已有结果
  └─ 静态关系 ────────► ChoiceTable 的初始倾向

语料历史 ────────────► ChoiceTable 的动态倾向、拼接来源

已有 Prog ───────────► Mutate：插入、删除、改参数、拼接、压扁
                                  │
                                  ▼
                            新的结构化 Prog
                                  │
                                  ▼
                     执行反馈决定是否保留、是否最小化
```

一句话概括：syzkaller 不把测试程序当作无结构的字节串来随机修改。它先用 Target 的类型和资源知识生成结构，再用调用关联和语料经验引导选择；但它不会替内核验证所有语义前提，最终仍由实际执行的反馈来筛选程序。

## 十、源码导航与下一阶段
