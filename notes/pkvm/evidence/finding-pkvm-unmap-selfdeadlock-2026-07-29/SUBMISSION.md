## 2. Provenance of the two cherry-picks — and the search trap

The two `ANDROID:` commits were **already in the local object store** but on no
branch we would have thought to search. Cherry-pick sources:

- `ed14b491ec76` → `ANDROID: KVM: arm64: Fix accounting of pinned THPs with pKVM`
- `63a99c1fb8e5` → `ANDROID: KVM: arm64: Fix THPs reclaim with ballooning`

**Verified** — they are reachable only from a *tag*:

```
$ git log --all --source --oneline --grep="Fix accounting of pinned THPs with pKVM"
ed14b491ec76  refs/tags/android15-6.6-2024-12_r1  ANDROID: KVM: arm64: Fix accounting ...
```

Searching the four plausible branches for the same subject returned **zero hits
each** (**verified**):

```
gerrit/android15-6.6-pkvm_experimental -> 0
gerrit/android-mainline                -> 0
gerrit/2030/pkvm                       -> 0
gerrit/2030/stable                     -> 0
```

This is the trap worth remembering. A branch-scoped search here yields
"no upstream fix exists" and sends you off to hand-roll patches that Google had
already written and reviewed. `git log --all --source --grep=` is the query that
finds them; `--all` reaches `refs/tags/`, `--source` tells you which ref it came
from. Note also that `git branch --contains` is unusably slow on this repo and, if
it hits a `timeout`, prints nothing — indistinguishable from a genuine "not
found". Use `git merge-base --is-ancestor` for "is it already applied?".

Cherry-picks preserved original authorship, `Signed-off-by`, and `Change-Id`
(**verified**), so Gerrit links them to the upstream changes and the reviewer sees
Perret's and Donnefort's names on their own work.

**checkpatch** (**verified**), run from inside `/home/jose/futlab-fixes`:

```
./scripts/checkpatch.pl --no-signoff --terse -g HEAD
total: 1 errors, 1 warnings
```

Both are expected and correct to leave alone:

- the "error" is `Remove Gerrit Change-Id's before submitting upstream` —
  checkpatch encodes the *upstream Linux* rule, but Gerrit **requires** the
  trailer. Deleting it to satisfy checkpatch breaks the submission.
- the warning is on the intentional ASCII call-trace diagram in the commit body.

Note `-g HEAD` resolves against the shell's cwd, not the script's location — an
earlier run from the wrong directory silently checked a different repository's
commit. Confirm the subject checkpatch prints is yours.

**Working tree isolation** (**verified**). All work happened in a
`git worktree add --detach` checkout. `/home/jose/common-stage2mvp` still shows

across the whole exercise. This matters because syz-manager pins that tree as

## 6. Open items

Labelled honestly — none of these are blocking the submission, but none should be
quietly forgotten either.

1. **THP undercount in `pkvm_unmap_range()` — candidate 4th change, unverified.**
   The loop increments `cnt++` per pinned page rather than `1 << order`, so a
   huge page is under-counted when un-accounting. Neither upstream commit covers
   this (`ed14b491ec76` fixes accounting *at pin time*, `63a99c1fb8e5` fixes the
   *reclaim/ballooning* path). This is a **code-reading hypothesis**, not a
   confirmed defect: no reproducer, no instrumented count. Confirm empirically
   before proposing it.

2. **D3000's PASS does not cover the exact submitted patch.** The board currently
   runs `6.6.30-pkvmfix`, built from hand-rolled variants during development, not
   from the three worktree commits as submitted. The reproducer result on it is
   real, but if the D3000 PASS is going to be cited as verifying *the submitted
   change*, rebuild from `d7c317637aa2` first.

3. **No independent confirmation of the Gerrit state** from this workstation. The
   landing is operator-reported (§1).
