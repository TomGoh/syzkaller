## 一、一句话定义

syzkaller 是一个 **无监督的、覆盖率引导的内核 fuzzer**（unsupervised coverage-guided kernel fuzzer）。

- **无监督**：不需要人工写测试用例，自己生成、自己变异、自己判断哪些输入"有价值"。
- **覆盖率引导**：用内核执行时的覆盖率反馈来决定"往哪个方向探索"。
- **内核 fuzzer**：被测对象是操作系统内核（通过系统调用这个入口去打）。
- 支持多种内核：Linux、FreeBSD、NetBSD、OpenBSD、Windows、Fuchsia、gVisor 等，但主战场和文档最全的是 Linux。

来源：`README.md` 第 10 行 "unsupervised coverage-guided kernel fuzzer"。

## 二、两根支柱（核心中的核心）

syzkaller 之所以比"随机往内核灌字节"强得多，靠的是两根互补的支柱，**缺一不可**：

### 支柱① 结构化 / 系统调用感知（structure-aware）

syzkaller **懂系统调用的参数结构**，不是瞎填字节。它知道：
- `open(path, flags, mode)` 的三个参数各是什么类型、合法取值范围；
- 参数之间的依赖关系，尤其是**资源（resource）在调用间的流转**——比如 `open` 返回一个 fd，后续 `read`/`write`/`close` 要复用这个 fd。

这靠的是 `sys/` 目录下的 **系统调用描述（syzlang，`.txt` 文件）**。

> 为什么关键：如果不懂结构，随机生成的系统调用参数几乎都会在内核最外层的参数校验（`copy_from_user` 后的合法性检查、`-EINVAL` 那一层）就被打回，根本进不了内核深处的逻辑。结构感知让 fuzzer 能构造出"合法到能往里走"的调用序列。

### 支柱② 覆盖率引导（coverage-guided）

每执行一个程序，都从内核收集**覆盖率反馈**（走过了哪些代码），据此判断这个输入"是否触达了以前没走过的路径"。有新路径 → 有价值 → 留下来作为后续变异的素材；没有 → 丢弃。

这就是"coverage-guided"的正反馈循环：**新覆盖 → 入库 → 变异素材 → 更多新覆盖**。

> 为什么关键：如果只有结构感知、没有覆盖率反馈，fuzzer 就没有"探索方向感"，只能盲目地生成合法程序，无法系统性地把内核代码一块块啃下来。

### 一句话总结两根支柱的互补关系

> 只有①（结构感知）会像随机 fuzzing 一样浅——生成得合法，但不知道往哪儿走；
> 只有②（覆盖率引导）不懂系统调用结构，会卡在参数校验层，根本积累不出有意义的覆盖。
> **两者相乘**，才有了 syzkaller 的战斗力。

## 三、三层进程结构（出师标准：能徒手画出来）

对着 `docs/process_structure.png` 和 `docs/internals.md` 的 Overview，整个系统是清晰的三层：

```
        用户 (http: url 访问 web 界面)
           │
   ┌───────▼─────────┐        ┌──────────────────────────┐
   │   syz-manager   │◄──────►│  workdir                 │
   │   (跑在稳定的     │  读写   │   crashes/crashN-T        │
   │    host 上)      │        │   corpus.db / corpus/*    │
   └───┬─────────▲───┘        └──────────────────────────┘
       │ RPC     │ RPC (回传结果 / 覆盖率)
       │ 下发程序 │
   ┌───▼─────────┴────────────────────────────────────┐
   │  VM (N 个，manager 负责启动/重启/监控)              │
   │                                                    │
   │   sshd/adbd ──invoke──►  syz-executor              │
   │                              │  ▲                  │
   │                    syscalls  │  │ coverage info    │
   │                              ▼  │ (kcov)           │
   │   ┌────────────────────────────────────────────┐  │
   │   │  Kernel + Modules  (vmlinux/kernel 镜像)     │  │
   │   └────────────────────────────────────────────┘  │
   │                                                    │
   │   syz-executor 内部：fork 出短命子进程，            │
   │   每个子进程执行"一个输入"(一段系统调用序列)         │
   └────────────────────────────────────────────────────┘
```

### 三层各自的职责

| 层 | 在哪 | 干什么 |
|---|---|---|
| **syz-manager** | host（稳定内核，不承受 fuzzer 的白噪声负载） | ① 启动/重启/监控 VM 实例；② 真正的 fuzzing 逻辑：输入生成、变异、最小化；③ 持久化：corpus 语料库 + crash 崩溃存储 |
| **syz-executor** | 每个 VM 内一个 | 通过 RPC 从 manager 收程序、执行、把结果（错误状态、覆盖率）回传。本身是常驻进程 |
| **短命子进程 (transient subprocess)** | executor `fork` 出来 | 每个子进程只执行**一个输入**（一段系统调用序列）。设计得尽量简单（C++、静态编译、共享内存通信），以免自身干扰 fuzzing |

### 三个关键设计点

1. **为什么 manager 在 host、executor 在 VM？**
   VM 里的内核是被 fuzz 的目标，随时可能崩。manager 必须活在一个**稳定的**环境里，才能在 VM 崩掉后重启它、收集崩溃、继续调度。

2. **为什么每个输入要在 fork 出的短命子进程里跑？**
   隔离。一个输入可能把子进程自己搞坏（内存破坏、卡死），用完即弃的子进程能把这种污染挡在外面，不影响 executor 常驻进程和后续输入。

3. **通信方式**：manager ↔ executor 走 **RPC**；executor ↔ 子进程走**共享内存**（快，且适合传大块覆盖率数据）。

来源：`docs/internals.md` 第 14–29 行。

## 四、覆盖率到底是什么（为阶段 5/7 打底）

`docs/coverage.md` 的要点：

- syzkaller 用 **sanitizer coverage（tracing 模式）** + **KCOV** 收集覆盖率。
- 覆盖率基于编译器插入到目标代码里的**覆盖点（coverage points）**。一个覆盖点通常对应一个**基本块（basic block）**或一条 **CFG 边（control-flow edge）**：
  - Linux + clang 默认是 **CFG 边**；
  - gcc 默认是**基本块**。
- ⚠️ 重要的直觉修正：覆盖点是编译器在**中端优化之后**插入的，所以覆盖率**和源代码不是严格对应**的——可能出现"未覆盖行的下一行反而被标记为已覆盖"这种反直觉现象。覆盖率是**趋势性**指标，用来看整体进展很有用，但别把它当成逐行精确的真值。

> 这段是你已经吃透的 KCOV 反馈在 syzkaller 里的定位。web 界面里的颜色（黑=全覆盖 / 橙=部分 / 红=未覆盖但函数被执行 / 灰=函数没执行或不可插桩）就是这套数据渲染出来的，细节留到阶段 7。

## 五、崩溃是怎么存的（为阶段 8 打底）

`docs/internals.md` 第 39–81 行：

- 找到崩溃后，信息存进 `workdir/crashes/`，**每种唯一崩溃一个子目录**。
- 每个子目录里：
  - `description`：一个唯一字符串，用于 bug 识别和去重；
  - 最多 100 对 `logN` / `reportN`：
    - `logN` = 原始 syzkaller 日志（含内核 console 输出 + 崩溃前执行的程序），可喂给 `syz-repro`（复现+最小化）或 `syz-execprog`（手动定位）；
    - `reportN` = 后处理并符号化后的崩溃报告（如 KASAN 报告）。
- `description` 靠 `pkg/report/` 里的一组正则从内核输出里提取。
- 三种特殊崩溃：`no output from test machine` / `lost connection to test machine` / `test machine is not executing programs`——这类通常没有 `reportN`，有时是 syzkaller 自身的 bug，但更多时候意味着内核 lockup 之类的严重问题。
