## 一、一句话定义

syzkaller 是一个 **无监督的、覆盖率引导的内核 fuzzer**（unsupervised coverage-guided kernel fuzzer）。

- **无监督**：不需要人工写测试用例，自己生成、自己变异、自己判断哪些输入"有价值"。
- **覆盖率引导**：用内核执行时的覆盖率反馈来决定"往哪个方向探索"。
- **内核 fuzzer**：被测对象是操作系统内核（通过系统调用这个入口去打）。
- 支持多种内核：Linux、FreeBSD、NetBSD、OpenBSD、Windows、Fuchsia、gVisor 等，但主战场和文档最全的是 Linux。

来源：`README.md` 第 10 行 "unsupervised coverage-guided kernel fuzzer"。

## 二、两根支柱（核心中的核心）

syzkaller 之所以比"随机往内核灌字节"强得多，靠的是两根互补的支柱，**缺一不可**：

### 支柱① 结构化 / 系统调用感知（structure-aware）

syzkaller **懂系统调用的参数结构**，不是瞎填字节。它知道：
- `open(path, flags, mode)` 的三个参数各是什么类型、合法取值范围；
- 参数之间的依赖关系，尤其是**资源（resource）在调用间的流转**——比如 `open` 返回一个 fd，后续 `read`/`write`/`close` 要复用这个 fd。

**准确的机制（别说成"存在文件里"）**：这套知识是用一门叫 **syzlang** 的**声明式描述语言**，按 syzlang 的类型体系把每个系统调用的接口**建模**出来的。`sys/$OS/*.txt` 文件就是用 syzlang 写成的这些模型，不是静态的常量表。

`docs/syscall_descriptions.md` 原文：*"syzkaller uses **declarative description** of syscall interfaces to manipulate programs."*

官方例子（就是 open/read/close 的模型）：

```
open(file filename, flags flags[open_flags], mode flags[open_mode]) fd
read(fd fd, buf buffer[out], count len[buf])
close(fd fd)
```

- `open(...) fd`：末尾 `fd` 是**返回值**，且是一种 **resource（资源）**。
- `read(fd fd, ...)`：第一个参数类型也是 `fd`，和 `open` 返回值**同一种 resource** → syzkaller 知道把 `open` 产出的 fd 喂进来，而不是瞎编。
- `count len[buf]`：`count` 被建模成 `buf` 的长度，变异 buf 时自动跟随，不会越界。
- 这就是"结构感知/资源流转"的本质：`fd` 这个 resource 类型像一根线，把 `open→read→close` 串成有意义的序列。

syzlang 的类型体系（建模用的基本积木，各带变异语义，详见 `docs/syscall_descriptions_syntax.md`）：
`const`/`intN`（整数）、`flags`（合法标志集合）、`ptr`（带 in/out/inout 方向的指针）、`array`/`string`/`buffer`（缓冲区）、`len`/`bytesize`/`bitsize`（跟随另一字段的长度）、**`resource`**（如 `fd`，调用间流转的句柄）。

从模型到能跑的东西这条链（细节留到阶段 3）：
```
sys/$OS/*.txt (syzlang 建模)
   │ syz-extract(抽常量) + syz-sysgen(编成 Go)
   ▼ sys/gen/*.go → prog 包加载 → 内存 AST: Call/Arg (prog/prog.go)
   ▼ generate/mutate/minimize 全程操作这个类型化 AST，而非文本
```
关键：syzlang 是"人写模型"的语言，最终编译成内存里的类型化 AST，fuzzer 的生成/变异全程都在这套模型约束下进行——这才是它"懂系统调用结构"的真正来源。

> 为什么关键：如果不懂结构，随机生成的系统调用参数几乎都会在内核最外层的参数校验（`copy_from_user` 后的合法性检查、`-EINVAL` 那一层）就被打回，根本进不了内核深处的逻辑。结构感知让 fuzzer 能构造出"合法到能往里走"的调用序列。

### 支柱② 覆盖率引导（coverage-guided）

每执行一个程序，都从内核收集**覆盖率反馈**（走过了哪些代码），据此判断这个输入"是否触达了以前没走过的路径"。有新路径 → 有价值 → 留下来作为后续变异的素材；没有 → 丢弃。

这就是"coverage-guided"的正反馈循环：**新覆盖 → 入库 → 变异素材 → 更多新覆盖**。

> 为什么关键：如果只有结构感知、没有覆盖率反馈，fuzzer 就没有"探索方向感"，只能盲目地生成合法程序，无法系统性地把内核代码一块块啃下来。

### 一句话总结两根支柱的互补关系

> 只有①（结构感知）会像随机 fuzzing 一样浅——生成得合法，但不知道往哪儿走；
> 只有②（覆盖率引导）不懂系统调用结构，会卡在参数校验层，根本积累不出有意义的覆盖。
> **两者相乘**，才有了 syzkaller 的战斗力。

## 三、三层进程结构（出师标准：能徒手画出来）

对着 `docs/process_structure.png` 和 `docs/internals.md` 的 Overview，整个系统是清晰的三层。
**注意**：三层职责在任何部署形态下都不变；下图（= png 画的）只是**拓扑 A：manager 自己拉起 VM**的情形。我实际关注的**拓扑 B：连真实物理机（isolated）**见本节末尾。

### 拓扑 A —— manager 自管 VM（qemu/gce，process_structure.png）

```
        用户 (http: url 访问 web 界面)
           │
   ┌───────▼─────────┐        ┌──────────────────────────┐
   │   syz-manager   │◄──────►│  workdir                 │
   │   (跑在稳定的     │  读写   │   crashes/crashN-T        │
   │    host 上)      │        │   corpus.db / corpus/*    │
   └───┬─────────▲───┘        └──────────────────────────┘
       │ RPC     │ RPC (回传结果 / 覆盖率)
       │ 下发程序 │
   ┌───▼─────────┴────────────────────────────────────┐
   │  VM (N 个，manager 负责启动/重启/监控)              │
   │                                                    │
   │   sshd/adbd ──invoke──►  syz-executor              │
   │                              │  ▲                  │
   │                    syscalls  │  │ coverage info    │
   │                              ▼  │ (kcov)           │
   │   ┌────────────────────────────────────────────┐  │
   │   │  Kernel + Modules  (vmlinux/kernel 镜像)     │  │
   │   └────────────────────────────────────────────┘  │
   │                                                    │
   │   syz-executor 内部：fork 出短命子进程，            │
   │   每个子进程执行"一个输入"(一段系统调用序列)         │
   └────────────────────────────────────────────────────┘
```

### 三层各自的职责

| 层 | 在哪 | 干什么 |
|---|---|---|
| **syz-manager** | host（稳定内核，不承受 fuzzer 的白噪声负载） | ① 启动/重启/监控 VM 实例；② 真正的 fuzzing 逻辑：输入生成、变异、最小化；③ 持久化：corpus 语料库 + crash 崩溃存储 |
| **syz-executor** | 每个 VM 内一个 | 通过 RPC 从 manager 收程序、执行、把结果（错误状态、覆盖率）回传。本身是常驻进程 |
| **短命子进程 (transient subprocess)** | executor `fork` 出来 | 每个子进程只执行**一个输入**（一段系统调用序列）。设计得尽量简单（C++、静态编译、共享内存通信），以免自身干扰 fuzzing |

### 三个关键设计点

1. **为什么 manager 在 host、executor 在 VM？**
   VM 里的内核是被 fuzz 的目标，随时可能崩。manager 必须活在一个**稳定的**环境里，才能在 VM 崩掉后重启它、收集崩溃、继续调度。

2. **为什么每个输入要在 fork 出的短命子进程里跑？**
   隔离。一个输入可能把子进程自己搞坏（内存破坏、卡死），用完即弃的子进程能把这种污染挡在外面，不影响 executor 常驻进程和后续输入。

3. **通信方式**：manager ↔ executor 走 **RPC**；executor ↔ 子进程走**共享内存**（快，且适合传大块覆盖率数据）。

来源：`docs/internals.md` 第 14–29 行。

### 拓扑 B —— 连真实物理机 / isolated（我的主要关注场景）

场景：syz-manager 通过 ssh 连到一台或若干台**已存在的真实物理机**（DUT），这些机器本机内核已开启 KCOV。manager **不创建机器、不部署内核镜像**，只用 ssh/scp 调度与监控。用左对齐流向画法（不画右边框，避免对齐问题）：

```
[Host · 稳定机器，syz-manager 跑这儿]
  syz-manager  ⇄  workdir/  (corpus.db, corpus/*, crashes/)
      │
      │  与 DUT 之间只有一条通道：ssh / scp
      │    ├─ scp ：把 syz-executor 二进制推到 DUT 的 target_dir
      │    ├─ ssh ：启动 executor、读内核 console(dmesg) 监控崩溃
      │    ├─ ssh -R 反向隧道：executor 的 RPC 回连 manager（故需 AllowTcpForwarding yes）
      │    └─ ssh（可选）：读 /sys/fs/pstore 抓崩溃日志
      ▼
[DUT · 真实物理机，本机内核已开 CONFIG_KCOV=y / KASAN / DEBUG_INFO]
  sshd ──► syz-executor（常驻）
             │  ▲
   syscalls  │  │ kcov 覆盖率
             ▼  │
        本机被测内核
             │
             └─ executor fork 出「短命子进程」，每个只跑一个输入
```

**A 与 B 的差异（就这几点变，三层职责不变）**：

| 维度 | 拓扑 A：VM（qemu/gce） | 拓扑 B：isolated（真实物理机） |
|---|---|---|
| 目标机哪来的 | manager 自己拉起/销毁 | 已存在的真实机，manager 不创建 |
| 内核镜像 | manager 部署 vmlinux 进 VM | 不部署，用 DUT 本机 KCOV 内核 |
| 生命周期 | manager 全权启停/重启 | 只能 ssh；重启尽力而为（`target_reboot`：ssh `reboot` 或对 `usb_device_num` 做 USB re-authorization 断电重连） |
| 连接通道 | 内部网络 + ssh | 只有 ssh/scp；RPC 走 **反向 ssh 隧道** `ssh -R` |
| 崩溃日志 | VM console | ssh 读 console（dmesg），可选 `/sys/fs/pstore` |
| 配几台 | VM 池数量 | `"targets": ["10.0.0.1", ...]`，一台或若干台 |

**isolated 配置要点**（`docs/linux/setup_linux-host_isolated.md`）：
- DUT 内核需 `CONFIG_KCOV=y`、`CONFIG_DEBUG_INFO=y`、`CONFIG_KASAN=y`（建议再关 KASLR：`# CONFIG_RANDOMIZE_BASE is not set`，覆盖率更好对齐）。
- DUT 的 sshd 需 `AllowTcpForwarding yes`（反向隧道要用）。
- config：`"type": "isolated"`，`vm` 段里 `targets` / `target_dir` / `target_reboot` / 可选 `pstore` / `startup_script`。

**源码依据**（`vm/isolated/isolated.go`）：
- `Copy()` `:285` —— `vmimpl.SCP(...)` 把 executor 推到 `target_dir`（推前先 `pkill -9` 旧的）。
- `Run()` `:304`、`SSHArgsForward` `:326` —— ssh 进 DUT `cd target_dir && exec <executor>`，并带反向端口转发；同时 `OpenRemoteConsole` 读 dmesg。
- `Forward()` `:140` —— 记录反向隧道端口（manager 的 RPC 端口）。
- `repair()` `:216` / reboot `:236` —— 修复时尝试重启（USB 授权或 ssh reboot），best-effort。
- `Diagnose()` `:383` + `readPstoreContents()` `:366` —— 崩溃诊断 / 从 pstore 取日志。

## 四、覆盖率到底是什么（为阶段 5/7 打底）

`docs/coverage.md` 的要点：

- syzkaller 用 **sanitizer coverage（tracing 模式）** + **KCOV** 收集覆盖率。
- 覆盖率基于编译器插入到目标代码里的**覆盖点（coverage points）**。一个覆盖点通常对应一个**基本块（basic block）**或一条 **CFG 边（control-flow edge）**：
  - Linux + clang 默认是 **CFG 边**；
  - gcc 默认是**基本块**。
- ⚠️ 重要的直觉修正：覆盖点是编译器在**中端优化之后**插入的，所以覆盖率**和源代码不是严格对应**的——可能出现"未覆盖行的下一行反而被标记为已覆盖"这种反直觉现象。覆盖率是**趋势性**指标，用来看整体进展很有用，但别把它当成逐行精确的真值。

> 这段是你已经吃透的 KCOV 反馈在 syzkaller 里的定位。web 界面里的颜色（黑=全覆盖 / 橙=部分 / 红=未覆盖但函数被执行 / 灰=函数没执行或不可插桩）就是这套数据渲染出来的，细节留到阶段 7。

## 五、崩溃是怎么存的（为阶段 8 打底）

`docs/internals.md` 第 39–81 行：

- 找到崩溃后，信息存进 `workdir/crashes/`，**每种唯一崩溃一个子目录**。
- 每个子目录里：
  - `description`：一个唯一字符串，用于 bug 识别和去重；
  - 最多 100 对 `logN` / `reportN`：
    - `logN` = 原始 syzkaller 日志（含内核 console 输出 + 崩溃前执行的程序），可喂给 `syz-repro`（复现+最小化）或 `syz-execprog`（手动定位）；
    - `reportN` = 后处理并符号化后的崩溃报告（如 KASAN 报告）。
- `description` 靠 `pkg/report/` 里的一组正则从内核输出里提取。
- 三种特殊崩溃：`no output from test machine` / `lost connection to test machine` / `test machine is not executing programs`——这类通常没有 `reportN`，有时是 syzkaller 自身的 bug，但更多时候意味着内核 lockup 之类的严重问题。

## 八、深化 FAQ

### Q1：fork 短命子进程也挡不住内核崩溃，那测试搞崩内核 / 污染整机状态怎么办？

**前提要纠正的直觉**：崩溃不是"要避免的意外"，而是 syzkaller **要达成的目标**（崩内核 = 找到 bug = 成功）。所以设计目标是"崩了之后怎么办（容错+恢复）"，不是"预防崩溃"。

- **fork 隔离的边界**：只隔离**用户态**——子进程自己内存被写坏 / 卡在阻塞 syscall / 泄漏 fd。丢弃子进程 → executor 常驻进程保持干净跑下一个。它**从不负责、也挡不住共享内核崩溃**。

- **内核真崩了，靠 host 上 manager 的四步容错闭环**：
  1. **检测**：`monitorExecution()`（`vm/vm.go:373`）盯 DUT 的 console，识别 oops/KASAN（`ContainsCrash` `:439`）、`lost connection`（`:568`）、`no output`（`:424`）、`timeout`（`:395`）。
  2. **抓证据**：`pkg/report/` 正则解析 console → 符号化报告 + `description`（去重）→ 存 `workdir/crashes/`，保留 `logN`（崩前执行过的程序）+ `reportN`。
  3. **恢复**：把 DUT 当一次性耗材。`Instance.Close()`（`:343`）清掉实例，dispatcher 拉起全新实例。VM→销毁重建；isolated 物理机→best-effort reboot（`vm/isolated/isolated.go` `repair()`：ssh reboot 或 USB re-authorization）。→ 这就是"manager 为什么在 host"的落地：目标会死，大脑必须活在崩不着的地方。
  4. **复现**：崩溃未必是最后一个程序触发（可能是"多个程序+累积状态"）→ 事后 `logN` 喂 `syz-repro`（`pkg/repro/`）二分+最小化，逼出稳定最小复现。

- **不崩但污染整机状态**（更微妙）：executor 沙箱（none/setuid/**namespace** 给较干净命名空间）+ per-call/per-prog 超时 + threaded 执行 + 定期重启目标机；并**坦承内核 fuzzing 可复现性天生不完美**（这正是 `pkg/repro` 是独立硬问题的原因）。

- **一句话**：fork 是最内层用户态隔离（保护 executor 自己）；兜底内核崩溃的是 host 上 manager 的「检测→解析去重存盘→重建目标→syz-repro 复现」闭环。哲学 = 不预防崩溃，把目标机当耗材，让不死的 manager 收尸、复活、验尸。
- 完整源码细节 → 阶段 8（manager/RPC/VM/崩溃）+ `pkg/repro`。

## 九、自检批改与精确化（出师留痕）

三题全过，以下是把答案钉得更准的三处：

1. **manager 在 host** = 崩溃隔离 + **稳定算力/存储**（生成/变异/最小化要可靠、corpus/crash 要持久） + **编排中枢**（启停/监控 N 个 VM、分发程序、收结果——就是 orchestrator）。三合一，别只记"崩不死"。

2. **短命子进程**两重价值：① 崩溃/错误隔离（保护 executor 常驻进程）；② **每个输入状态干净**（避免上个输入泄漏的 fd/内存/信号处理器污染下一个）。边界：挡用户态，不挡共享内核。

3. 结构感知 = **`sys/`（某 OS 的描述数据）+ `prog/`（与 OS 无关的结构引擎，真正使用/变异结构的地方）**——这就是"可移植性分界线"（附录 C 主心骨②）。覆盖率链里要分两条路：
   - **决策热路径**（驱动 fuzzer）：内核 KCOV → `executor/` 回传 → `pkg/signal`(Diff/Merge) → `pkg/fuzzer`(triage/genFuzz/maxSignal) → `pkg/corpus`(入库)。**全程用 raw PC/signal，不需符号化**。
   - **报告路径**（给人看）：`pkg/cover` 把 PC→file:line 渲染网页，**不在热路径上**。
