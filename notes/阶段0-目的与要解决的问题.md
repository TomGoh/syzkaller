## 一、syzkaller 是什么

syzkaller 是一个 **无监督的、覆盖率引导的内核 fuzzer**（unsupervised coverage-guided kernel fuzzer）。

分别解释这些定语：

- **无监督**：运行后可以持续生成、执行和筛选测试输入，不需要人工逐条编写测试用例。这里的“无监督”不表示完全不需要人工知识：系统调用描述、目标机配置和内核配置仍需要人来编写和维护。
- **覆盖率引导**：利用内核执行时返回的覆盖率信号，判断哪些输入值得保留，并调整后续生成和变异的重点。
- **内核 fuzzer**：被测对象是操作系统内核。用户态进入内核的主要接口是系统调用，因此 syzkaller 的输入通常不是任意字节流，而是一条 **syscall 程序**（`Prog`），也就是若干系统调用组成的有序序列。构造程序时需要决定调用种类和顺序、按类型生成参数，并处理调用之间的资源依赖，例如把 `open` 返回的 fd 交给后续 `read` 使用。
- syzkaller 支持 Linux、FreeBSD、Fuchsia、gVisor、NetBSD、OpenBSD、Windows 等目标；项目最初面向 Linux，目前大多数文档仍以 Linux 为主。

## 二、syzkaller 的两根支柱

与直接向系统调用参数填入随机字节相比，syzkaller 主要依靠两类信息提高探索效率：**系统调用结构**和**执行覆盖率**。二者作用不同，需要配合使用。

### 支柱一：结构化 / 系统调用感知（structure-aware）

syzkaller 了解系统调用接口的参数结构，不会把所有参数都当作没有含义的字节。以 `open`、`read`、`write`、`close` 为例，描述中可以表达：

- 参数的类型、方向、常见标志值和长度关系；
- 参数之间的依赖，尤其是 **resource（资源）在调用之间的流转**。

这套知识用 **syzlang** 声明式描述语言建模。`sys/<os>/*.txt` 保存接口和类型描述，`sys/<os>/*.const` 保存各架构的常量值。它们不是运行时读取的一张简单 syscall 常量表，而是生成目标描述的输入。

在 syzlang 中，resource 表示由某个调用产生、又可被其他调用使用的句柄或标识。典型例子是文件描述符 `fd`，此外还有 `sock`、`pid`、`uid` 等。这里的 resource 不是泛指硬件或内存资源，而是 syzlang 类型系统中的一种依赖关系：它描述谁能产生某类值、哪些调用能使用这类值。生成或变异程序时，syzkaller 可以复用已有 resource，也可以插入产生该 resource 的调用；它也会保留一部分特殊或无效值，用来测试错误处理路径。

官方文档中的 `open` / `read` / `close` 描述如下：

```text
open(file filename, flags flags[open_flags], mode flags[open_mode]) fd
read(fd fd, buf buffer[out], count len[buf])
close(fd fd)
```

- `open(...) fd`：末尾的 `fd` 是返回值，其类型是 resource。
- `read(fd fd, ...)`：第一个参数也要求 `fd` resource，因此 syzkaller 能建立 `open → read` 的资源依赖，而不只是填入一个无来源的普通整数。
- `count len[buf]`：`count` 与 `buf` 的长度建立关联。正常生成和程序修复会据此计算长度；变异器也可以故意把长度改成不一致或边界值，以测试内核的校验逻辑。因此，`len[buf]` 表达的是依赖关系，不是“永远不会越界”的保证。

syzlang 的常用类型包括：`const` / `intN`（整数）、`flags`（标志集合）、`ptr`（带 in/out/inout 方向的指针）、`array` / `string` / `buffer`（数组和缓冲区）、`len` / `bytesize` / `bitsize`（长度关系），以及 `resource`（调用间传递的句柄或标识）。详细语法见 `docs/syscall_descriptions_syntax.md`。

当前代码从 syzlang 到内存程序的关系如下，细节留到阶段 1 和阶段 3：

```text
内核头文件 ──syz-extract──► sys/<os>/*.const   （更新常量时运行）
sys/<os>/*.txt + sys/<os>/*.const
                 │ syz-sysgen
                 ▼
sys/gen/<os>_<arch>.gob.flate + sys/register.go
                 │ 加载为具体 OS/arch 的 prog.Target
                 ▼
内存中的 Prog / Call / Arg 表示
                 │
                 └─ generate / mutate / minimize 等算法
```

`Prog`、`Call` 和 `Arg` 是类似 AST 的类型化内存表示。生成、变异和最小化主要操作这套表示，而不是直接修改文本。执行前，`prog.SerializeForExec()` 还会把它转换成更简单、不可逆的 exec 二进制指令；executor 不会重新读取完整的 syzlang 类型。

> 为什么重要：如果完全不了解参数结构，许多输入会在系统调用入口附近因为 `-EINVAL`、`-EBADF`、`-EFAULT` 等错误提前返回，难以进入更深的状态和代码路径。结构描述提高了产生有意义调用序列的概率，但不会排除所有无效值；主动测试错误处理同样是 fuzzing 的一部分。

### 支柱二：覆盖率引导（coverage-guided）

每次执行程序后，syzkaller 从被测内核取得覆盖率 signal，并与已经见过的 signal 比较。如果首次执行出现潜在的新 signal，程序会进入 **triage**：重复执行以确认信号是否足够稳定，随后尝试最小化。只有仍能保留新增稳定 signal 的程序才会加入 corpus，成为后续变异的素材。没有带来新增 signal 的普通输入通常不会进入 corpus。

这形成了一个反馈循环：**发现潜在新 signal → triage 与最小化 → 加入 corpus → 继续变异 → 探索更多代码**。

> 为什么重要：只有结构描述而没有覆盖率反馈时，fuzzer 可以产生较合理的程序，却缺少判断“哪个方向带来了新行为”的依据，容易反复探索已经到达的代码。

### 两根支柱如何互补

- 结构化描述提高输入通过浅层检查、建立有效状态和资源依赖的概率；
- 覆盖率反馈负责评价执行结果，为后续探索提供方向。

只有覆盖率反馈而没有结构知识，输入往往难以越过接口的浅层检查；只有结构知识而没有反馈，生成的程序即使较合理，也难以持续向尚未覆盖的代码集中。

## 三、三层进程结构

`docs/process_structure.png` 和 `docs/internals.md` 把典型 syzkaller 部署分为三层：稳定 Host 上的 manager、目标机上的 executor，以及 executor 为单次输入启动的瞬态子进程。下面先以当前 Linux/QEMU 的普通 RPC 模式为例；其他后端的生命周期和传输细节可能不同，但三层的基本职责相同。

### 拓扑 A —— manager 管理 QEMU VM

场景：`syz-manager` 通过 `vm/qemu` 启动若干 QEMU 实例。QEMU 使用配置中的磁盘 `image`，也可以通过 `vm.kernel` 指定可启动内核；Host 侧的 `kernel_obj` 主要用于符号化和覆盖率报告，不能和 QEMU 的启动内核混为一谈。manager 通过 SCP 复制 executor，通过 SSH 启动它，并监控 QEMU 进程和 console。用户可以通过 manager 自带的 HTTP 状态页查看运行情况。

```text
[Host · 稳定机器，syz-manager 运行在这里]
  用户 ──HTTP──► syz-manager  ⇄  workdir/（corpus.db、crashes/）
                      │
                      ├─ vm/qemu：启动、监控、关闭 QEMU 实例
                      ├─ SCP / SSH：复制并启动 syz-executor
                      └─ SSH -R：让 VM 内的 executor 连接 Host 的 RPC 端口
                           │     RPC 使用 FlatRPC 消息，经 TCP 连接传输
                           ▼
[QEMU VM · 运行被测 Linux 内核]
  sshd ──► syz-executor（在当前实例中持续处理请求）
             │  ▲
        fork │  │ 共享内存中的执行结果和覆盖率
             ▼  │
        瞬态子进程（一个正常程序请求对应一个子进程）
             │  ▲
    syscalls │  │ KCOV
             ▼  │
        被测内核 + 内核模块
```

这里需要区分两层含义：manager 与 executor 在应用层使用 FlatRPC 交换程序和结果；至于这个 TCP 连接如何到达 Host，由具体 VM 后端解决。当前 `vm/qemu` 和 `vm/isolated` 都在启动 executor 的 SSH 连接中使用反向端口转发。FlatRPC 并不是 SSH 的替代品，SSH 隧道也不负责解释 fuzzing 消息。

### 三层各自的职责

| 层 | 位置 | 主要职责 |
|---|---|---|
| **syz-manager** | 稳定 Host | 管理测试机实例；执行生成、变异、triage、最小化等 fuzzing 决策；持久化 corpus 和 crash |
| **syz-executor** | VM 或物理 DUT | 接收低层执行指令，准备参数并执行；采集错误状态和覆盖率并回传。在一次目标机实例运行期间通常持续处理请求 |
| **瞬态子进程** | Linux executor `fork` 出的进程 | 执行一个正常程序请求。子进程退出后，其用户态地址空间、fd 和线程随之清理 |

“每个输入 fork 一个子进程”是当前 Linux executor 的常见 fork-server 路径，不是所有操作系统和执行模式都必须采用的统一规则；是否使用 fork server 由目标配置决定，并作为 `SYZ_EXECUTOR_USES_FORK_SERVER` 写入生成的 `executor/defs.h`。

### 三个关键设计点

1. **为什么 manager 放在 Host，executor 放在目标机？**
   被测内核可能报告错误、挂起或重启。manager 必须位于独立、稳定的环境中，才能保存状态、回收或重建测试实例，并继续调度。

2. **为什么 Linux executor 为程序 fork 瞬态子进程？**
   子进程可以隔离单次输入造成的用户态进程污染，例如损坏自身地址空间、泄漏 fd 或留下卡住的线程。它不能隔离共享内核中的状态，更不能阻止内核崩溃。

3. **各层如何通信？**
   manager 与 executor 使用基于 TCP 的 FlatRPC；具体网络可达性由 VM 后端提供。executor 父进程与瞬态子进程主要通过共享内存交换输入、结果和覆盖率。

### 拓扑 B —— 连接真实物理机 / `isolated`

场景：`syz-manager` 通过 SSH 连接一台或多台已经存在的物理 DUT。`isolated` 后端不创建物理机，也不部署或替换 DUT 的内核镜像；它使用 DUT 当前启动的内核。

```text
[Host · 稳定机器，syz-manager 运行在这里]
  syz-manager  ⇄  workdir/（corpus.db、crashes/）
      │
      ├─ SCP：把 syz-executor 复制到 DUT 的 target_dir
      ├─ SSH：启动 executor，并持续读取远端内核日志
      ├─ SSH -R：让 executor 的 FlatRPC 连接回到 manager
      └─ SSH（可选）：DUT 重启后读取 /sys/fs/pstore
      ▼
[DUT · 已存在的真实物理机]
  sshd ──► syz-executor
             │ fork
             ▼
        瞬态子进程 ──syscalls──► DUT 本机被测内核
             ▲                         │
             └──────── KCOV ──────────┘
```

**QEMU 与 `isolated` 的主要差异**：

| 维度 | QEMU | `isolated` 物理 DUT |
|---|---|---|
| 目标机来源 | manager 启动和关闭 QEMU 进程 | 目标机预先存在，manager 不创建 |
| 被测内核 | 来自磁盘镜像，或由 `vm.kernel` 指定启动文件 | DUT 当前启动的本机内核 |
| executor 部署 | 通过 SCP 复制到 VM，再用 SSH 启动 | 通过 SCP 复制到 `target_dir`，再用 SSH 启动 |
| RPC 可达性 | 当前 qemu 后端使用 SSH 反向端口转发 | 使用 SSH 反向端口转发 |
| 崩溃日志 | QEMU console 与 executor/SSH 输出 | SSH 读取的远端内核日志；可选 pstore |
| 恢复能力 | 可以关闭并重新创建干净 VM | 取决于 DUT 是否能自行恢复，以及 `target_reboot` 和外部 USB 控制是否可用 |

**`isolated` 配置要点**（`docs/linux/setup_linux-host_isolated.md`）：

- 使用覆盖率引导时，DUT 内核必须支持 KCOV。`CONFIG_DEBUG_INFO=y` 用于符号化和源码级报告；KASAN 是强烈推荐的内存错误检测器，但不是 KCOV 工作本身的必要条件。
- 关闭 KASLR（`# CONFIG_RANDOMIZE_BASE is not set`）通常能简化地址对应和复现，但这也是推荐项，不是 `isolated` 后端能连接 DUT 的前提。
- DUT 的 sshd 需要允许 TCP 转发，例如 `AllowTcpForwarding yes`。
- manager 配置使用 `"type": "isolated"`；`vm` 段至少提供 `targets` 和 `target_dir`，还可配置 `target_reboot`、`pstore`、`startup_script`、`system_ssh_cfg` 等。

**源码对应关系**（`vm/isolated/isolated.go`）：

- `Copy()` 使用 `vmimpl.SCP()` 把目标端程序复制到 `target_dir`，复制前会终止同名旧进程并删除旧文件。
- `Run()` 通过 SSH 在 `target_dir` 中启动 executor，使用 `SSHArgsForward()` 建立反向端口转发，并通过 `OpenRemoteConsole()` 读取远端日志。
- `Forward()` 记录需要反向转发的 manager RPC 端口。
- `repair()` 先等待 SSH；只有 SSH 已经可用且启用了 `target_reboot`，才会尝试 SSH `reboot`，或通过 `usb_device_num` 取消并恢复 USB 授权。USB 授权切换能否真正重启 DUT 取决于硬件连接方式。由于检查 SSH 在重启操作之前，当前实现不能依靠这条路径恢复一个始终无法重新建立 SSH 的 DUT。
- `Diagnose()` 在启用 `pstore` 时等待 DUT 重启并读取 pstore。它不能保证一个完全失联且没有外部恢复手段的物理 DUT 自动恢复。

## 四、syzkaller 与 KCOV 代码覆盖率

以下说明针对常见的 Linux 配置；gVisor 等目标使用不同的覆盖率机制。

- syzkaller 使用 **sanitizer coverage 的 tracing 模式**在目标代码中插入覆盖点，再通过 **KCOV** 把执行产生的 PC 反馈给用户态。
- 一个覆盖点通常对应一个基本块（basic block）或一条控制流图边（CFG edge），具体取决于编译器和插桩模式：
  - Linux + clang 的默认模式是 CFG edge；
  - gcc 的默认模式是 basic block。
- 覆盖点是在编译器中端已经完成多轮转换和优化后插入的，因此它们与源代码行不是严格一一对应。可能出现相邻源代码行的覆盖状态看似矛盾，或者预期位置没有覆盖点的情况。

覆盖率适合衡量整体探索进展，也适合作为 fuzzer 的反馈信号；它不应被理解成逐行执行情况的绝对真值。

## 五、崩溃信息的持久化

发现崩溃后，manager 会把信息保存到 `workdir/crashes/`。目录名是根据 crash title 计算出的哈希，同一 title 的多次报告放在同一个子目录中。这里的 title 是用于归类和去重的标识，并不保证不同 title 一定对应不同的根因。

每个 crash 子目录中的主要文件包括：

- `description`：保存用于归类的 crash title；
- `logN`：原始 syzkaller 执行记录和内核输出，可供 `syz-repro` 或 `syz-execprog` 使用；
- `reportN`：解析并符号化后的报告，例如 KASAN 报告。

默认每类 crash 最多保存 100 组日志，但该数量由 `max_crash_logs` 配置决定。达到上限后，当前实现会覆盖最旧的一组，而不是无限增长。根据运行情况，目录中还可能出现 `tagN`、`machineInfoN`、`vmcore`、`repro.prog`、`repro.cprog` 等文件。

`pkg/report/` 负责从内核输出中识别和解析崩溃。当前 `vm/vm.go` 还会为 `no output from test machine`、`lost connection to test machine`、`timed out` 等基础设施异常构造特殊 crash。这类记录通常没有正常的内核报告内容：有时表示 syzkaller 或环境故障，也可能来自内核 hang、异常重启等严重问题，需要结合原始日志判断。

## 六、Q&A

### Q1：fork 瞬态子进程挡不住内核崩溃，那么测试破坏内核或污染整机状态时怎么办？

触发内核错误是内核 fuzzing 希望发现的结果，但一次 crash 记录并不自动证明已经找到一个新的、可稳定复现的内核缺陷。syzkaller 仍需保存证据、归类并尝试复现。它的设计重点不是阻止目标机出错，而是让 Host 能在目标机出错后继续工作。

**fork 隔离的边界**（当前 Linux fork-server 路径）：

1. executor 收到一个正常程序请求后创建私有临时目录，再 `fork()` 出瞬态子进程。
2. 子进程运行 `execute_one()`，完成后调用 `doexit(0)`。
3. 父进程用 `waitpid()` 观察子进程。如果超过 `program_timeout_ms`，或者在最短等待时间后长期没有系统调用进展，就调用 `kill_and_wait()`。源码注释列出的典型情况包括阻塞 syscall、seccomp 禁止 `exit_group`、userfaultfd 导致退出路径挂起。
4. 输入、执行结果和覆盖率主要通过共享内存交换；一轮结束后，父进程删除本轮临时目录。
5. 这些措施能清理子进程的用户态地址空间、fd 和线程。正常情况下，常驻 executor 可以继续处理下一个请求。
6. fork 不会复制或回滚共享内核。一个程序留下的全局内核状态、触发的 oops/KASAN 报告、hang 或重启，都超出了进程隔离的范围。

**如果检测到内核 crash 或目标机异常，Host 侧会执行以下流程：**

1. **检测**：`vm/vm.go` 的 `monitorExecution()` 持续处理目标机 console 和 executor 输出。它使用 reporter 的 `ContainsCrash()` 识别内核报告，也处理连接丢失、执行超时和长时间没有程序进展等情况。
2. **保存证据**：`pkg/report/` 解析输出；manager 随后进行符号化，并通过 `pkg/manager.CrashStore` 写入 `workdir/crashes/`。
3. **回收实例**：dispatcher 在本次实例任务结束后调用 `Instance.Close()`，随后创建下一实例。QEMU 场景会关闭并重新启动 VM，因此能够得到新的虚拟机实例。
4. **尝试恢复物理 DUT**：`isolated` 的 `Close()` 本身不会重启物理机。下一次 `Create()` 会调用 `repair()`；只有 DUT 已经恢复 SSH 且 `target_reboot=true` 时，当前代码才尝试 SSH reboot 或 USB 授权切换。如果 DUT 一直无法恢复 SSH，这条 `repair()` 路径不会执行后续重启操作，仍需要独立的看门狗或外部电源控制。
5. **复现**：manager 可把保存的执行日志交给 `syz-repro`。复现器会尝试判断需要哪些程序和执行选项，并进行最小化，得到更短、更稳定的 syz 或 C reproducer。

**如果没有立即崩溃，但内核状态已经被污染：**

- executor 的 sandbox 限制测试进程的用户态权限和命名空间，但不能回滚内核全局状态；
- syscall/program timeout 可以终止卡住的用户态执行，但同样不能撤销已经完成的内核操作；
- 普通 RPC 模式会按照 `VMRunningTime` 定期结束并重建实例。其基础默认值是一小时，还会按目标的 slowdown 系数缩放。QEMU 因而可以获得干净的新 VM；`isolated` 是否真的重启物理机仍取决于 `target_reboot` 和 SSH 状态；
- 在受支持的 Linux/QEMU snapshot 模式中，可以在程序之间恢复 VM 快照，减少跨程序状态积累，但这不是所有后端都具备的通用能力。

**小结**：fork 只负责最内层的用户态进程隔离。内核报告的检测、证据保存和实例调度由稳定 Host 上的 manager 完成；能否把目标机恢复到干净状态，则取决于后端。QEMU 可以通过重建或快照恢复，物理 DUT 需要可用的重启或外部控制手段。
