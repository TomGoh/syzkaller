## 一、syzkaller 是什么

syzkaller 是一个 **无监督的、覆盖率引导的内核 fuzzer**（unsupervised coverage-guided kernel fuzzer）。

分别解释下这些定语： 

- **无监督**：无需人工编写测试用例，自行生成输入、变化调整输入、判断哪些输入"有价值"。
- **覆盖率引导**：用内核执行时的覆盖率反馈来决定"模糊测试的输入的变化方向"。
- **内核 fuzzer**：被测对象是操作系统内核；用户态进内核最常见的口是系统调用，所以 fuzz 的「输入」不是任意字节流，而是一条 **syscall 程序**（`Prog`：若干系统调用的有序序列）。构造这样一条程序时至少包括：选取哪些 syscall、按照什么顺序组织编排这些 syscall、按类型填入/改变 syscall 的参数、调用间如何传递资源（如 `open` 输出的 fd 作为之后的 `read` 的输入）。
- 支持多种内核：Linux、FreeBSD、NetBSD、OpenBSD、Windows、Fuchsia、gVisor 等，但代码和文档支持最全面的是 Linux。

## 二、syzkaller 的两根支柱（核心中的核心）

syzkaller 之所以比"向 syscall 输入随机生成的字节"的早期模糊测试方法高效，靠的是两根互补的支柱，**缺一不可**：

### 支柱一 结构化 / 系统调用感知（structure-aware）

syzkaller拥有 **系统调用的参数结构** 这一先验知识，不是黑盒地随机填充字节。比如，针对 `open`， `read`， `write`， `close` 等常见的文件描述符系统调用， syzkaller 拥有如下的先验知识：
- `open(path, flags, mode)` 的三个参数分别是什么类型、合法取值范围；
- 参数之间的依赖关系，尤其是**资源（resource）在调用间的流转**。

这套知识是用一门叫 **syzlang** 的**声明式描述语言**，按 syzlang 的类型体系把每个系统调用的接口建模出来的。`sys/$OS/*.txt` 文件就是用 syzlang 写成的这些模型，不是静态的常量表。可以参见 `docs/syscall_descriptions.md` 原文：*"syzkaller uses **declarative description** of syscall interfaces to manipulate programs."*

在 syzlang 里，resource 指某个 syscall **产出**、又可能被后续 syscall **消费**的内核侧句柄或标识——典型如文件描述符 `fd`，此外还有 `sock`、`pid`、`uid` 等。它不是“机器上的某种硬件资源”，而是描述语言里的一类类型，：用来把“谁创建、谁使用、谁释放”建模清楚，生成/变异时才能把调用串成有意义的序列，而不是给 `read` 随机一个整数当 fd。

官方 open/read/close 的模型实例：

```
open(file filename, flags flags[open_flags], mode flags[open_mode]) fd
read(fd fd, buf buffer[out], count len[buf])
close(fd fd)
```

- `open(...) fd`：末尾 `fd` 是**返回值**，且是一种 **resource（资源）**。
- `read(fd fd, ...)`：第一个参数类型也是 `fd`，是和 `open` 返回值同一种的 resource，因此 syzkaller 知道把 `open` 产出的 fd 喂进来，而不是随机填充整数。
- `count len[buf]`：`count` 被建模成 `buf` 的长度，变异 buf 时自动跟随，不会越界。

这就是"结构感知/资源流转"的本质：`fd` 等 resource 类型像一根线，把 `open→read→close` 等系统调用之间的参数依赖关系进行建模，将 syscall 调用链建模成有意义的序列。

syzlang 的类型体系（建模用的基本积木，各带变异语义，详见 `docs/syscall_descriptions_syntax.md`）：
`const`/`intN`（整数）、`flags`（合法标志集合）、`ptr`（带 in/out/inout 方向的指针）、`array`/`string`/`buffer`（缓冲区）、`len`/`bytesize`/`bitsize`（跟随另一字段的长度）、**`resource`**（如 `fd`，调用间流转的句柄）。

从模型建立的定义到 syzkaller 按照这个模型构建测试的调用链如下（细节留到阶段 3）：
```
sys/$OS/*.txt (syzlang 建模)
   │ syz-extract(抽常量) + syz-sysgen(编成 Go)
   ▼ sys/gen/*.go → prog 包加载 → 内存 AST: Call/Arg (prog/prog.go)
   ▼ generate/mutate/minimize 全程操作这个类型化 AST，而非文本
```
关键：syzlang 是模型建立的语言，最终编译成内存里的类型化 AST，fuzzer 的生成/变异全程都在这套模型约束下进行，这才是 syzkaller 系统调用结构先验知识的真正来源。

> 为什么关键：如果不懂结构，随机生成的系统调用参数几乎都会在内核最外层的参数校验（`copy_from_user` 后的合法性检查、`-EINVAL` 那一层）就被打回，根本进不了内核深处的逻辑。结构感知让 fuzzer 能构造出"合法到能往里走"的调用序列。

### 支柱二 覆盖率引导（coverage-guided）

每执行一个测试实例，syzkaller 都从内核收集**覆盖率反馈**（走过了哪些代码），据此判断这个输入"是否触达了以前没走过的路径"。如果这个测试输入走上了新的路径， syzkallr 会认为这个输入具有价值，将会保存下来到语料库中作为后续变异的素材，反之则丢弃。

这就是"coverage-guided"的正反馈循环：**新覆盖 → 入库 → 变异素材 → 更多新覆盖**。

> 为什么关键：如果只有结构感知、没有覆盖率反馈，fuzzer 就没有"探索方向感"，只能盲目地生成合法程序，无法系统性地把内核代码全部覆盖。

### 总结两根支柱的互补关系

> 只有结构感知会像随机 fuzzing 一样浅——生成的测试用例确实是合法，但缺少指引性，可能一直在测试重复的部分；
> 只有覆盖率引导不懂系统调用结构，会卡在参数校验层，较难积累出有意义的覆盖。

## 三、三层进程结构

参照 `docs/process_structure.png` 和 `docs/internals.md` 的 Overview，syzkaller 整个系统是清晰的三层。
**注意**：三层职责在任何部署形态下都不变；下图为**拓扑 A：manager 自己拉起 VM**的情形。而基于物理测试机（DUT）
的 **拓扑 B：连真实物理机（isolated）**见本节末尾。

### 拓扑 A —— manager 自管 VM（qemu/gce，process_structure.png）

场景：syz-manager 自己拉起 N 个 VM（qemu/gce），向 VM 部署内核镜像与 executor，并负责启停/重启/监控。用户经 http 看 dashboard。用左对齐流向画法（与拓扑 B 同风格）：

```
[Host · 稳定机器，syz-manager 跑这儿]
  用户 ──http──► syz-manager  ⇄  workdir/  (corpus.db, corpus/*, crashes/)
                      │
                      │  与 VM 之间有两条通道（别混）：
                      │    ├─ 控制面 ssh/scp：部署镜像与 executor、启停/监控 VM
                      │    └─ 数据面 RPC/FlatRPC：下发程序 ↔ 回传结果/覆盖率
                      │         （RPC 直连已启动的 executor，不经 sshd）
                      ▼
[VM × N · manager 创建/销毁，内含被测内核镜像]
  sshd/adbd ──invoke──► syz-executor（常驻）
                           │  ▲
                    fork   │  │ 共享内存（结果/覆盖率）
                           ▼  │
                      瞬态子进程（每个只跑一个输入）
                           │  ▲
                 syscalls  │  │ kcov 覆盖率
                           ▼  │
                      Kernel + Modules（vmlinux/kernel，含 kcov）
```

### 三层各自的职责

| 层 | 位置 | 职责|
|---|---|---|
| **syz-manager** | host（稳定内核，不承受 fuzzer 的白噪声负载） | ① 启动/重启/监控 VM 实例；② 真正的 fuzzing 逻辑：输入生成、变异、最小化；③ 持久化：corpus 语料库 + crash 崩溃存储 |
| **syz-executor** | 每个 VM 内一个 | 通过 RPC 从 manager 收程序、执行、把结果（错误状态、覆盖率）回传。本身是常驻进程 |
| **瞬态子进程 (transient subprocess)** | executor `fork` 出来 | 每个子进程只执行**一个输入**（一段系统调用序列）。设计得尽量简单（C++、静态编译、共享内存通信），以免自身干扰 fuzzing |

### 三个关键设计点

1. **为什么 manager 在 host、executor 在 VM？**
   VM 里的内核是被 fuzz 的目标，在 bug 被触发的时候会崩溃。manager 必须活在一个**稳定的**环境里，才能在 VM 崩掉后重启它、收集崩溃、继续调度。

2. **为什么每个输入要在 fork 出的瞬态子进程里跑？**
   隔离。一个输入可能破坏测试所在的进程自身的资源（内存破坏、卡死），用完即弃的子进程能把这种污染挡在外面，不影响 executor 常驻进程和后续输入。

3. **通信方式**：manager ↔ executor 走 **RPC**；executor ↔ 子进程走**共享内存**（快，且适合传大块覆盖率数据）。

来源：`docs/internals.md` 第 14–29 行。

### 拓扑 B —— 连真实物理机 / isolated

场景：syz-manager 通过 ssh 连到一台或若干台**已存在的真实物理机**（DUT），这些机器本机内核已开启 KCOV。manager **不创建机器、不部署内核镜像**，只用 ssh/scp 调度与监控。用左对齐流向画法（不画右边框，避免对齐问题）：

```
[Host · 稳定机器，syz-manager 跑这儿]
  syz-manager  ⇄  workdir/  (corpus.db, corpus/*, crashes/)
      │
      │  与 DUT 之间只有一条通道：ssh / scp
      │    ├─ scp ：把 syz-executor 二进制推到 DUT 的 target_dir
      │    ├─ ssh ：启动 executor、读内核 console(dmesg) 监控崩溃
      │    ├─ ssh -R 反向隧道：executor 的 RPC 回连 manager（故需 AllowTcpForwarding yes）
      │    └─ ssh（可选）：读 /sys/fs/pstore 抓崩溃日志
      ▼
[DUT · 真实物理机，本机内核已开 CONFIG_KCOV=y / KASAN / DEBUG_INFO]
  sshd ──► syz-executor（常驻）
             │  ▲
   syscalls  │  │ kcov 覆盖率
             ▼  │
        本机被测内核
             │
             └─ executor fork 出「瞬态子进程」，每个只跑一个输入
```

**拓扑A VM 与 拓扑B 物理DUT 的差异**：

| 维度 | 拓扑 A：VM（qemu/gce） | 拓扑 B：isolated（真实物理机） |
|---|---|---|
| 目标机哪来的 | manager 自己拉起/销毁 | 已存在的真实机，manager 不创建 |
| 内核镜像 | manager 部署 vmlinux 进 VM | 不部署，用 DUT 本机 KCOV 内核 |
| 生命周期 | manager 全权启停/重启 | 只能 ssh；重启尽力而为（`target_reboot`：ssh `reboot` 或对 `usb_device_num` 做 USB re-authorization 断电重连） |
| 连接通道 | 内部网络 + ssh | 只有 ssh/scp；RPC 走 **反向 ssh 隧道** `ssh -R` |
| 崩溃日志 | VM console | ssh 读 console（dmesg），可选 `/sys/fs/pstore` |
| 配几台 | VM 池数量 | `"targets": ["10.0.0.1", ...]`，一台或若干台 |

**isolated 配置要点**（`docs/linux/setup_linux-host_isolated.md`）：
- DUT 内核需 `CONFIG_KCOV=y`、`CONFIG_DEBUG_INFO=y`、`CONFIG_KASAN=y`（最好关闭 KASLR：`# CONFIG_RANDOMIZE_BASE is not set`，覆盖率更好对齐且更易复现）。
- DUT 的 sshd 需 `AllowTcpForwarding yes`（反向隧道要用）。
- config：`"type": "isolated"`，`vm` 段里 `targets` / `target_dir` / `target_reboot` / 可选 `pstore` / `startup_script`。

**源码依据**（`vm/isolated/isolated.go`）：
- `Copy()` `:285` —— `vmimpl.SCP(...)` 把 executor 推到 `target_dir`（推前先 `pkill -9` 旧的）。
- `Run()` `:304`、`SSHArgsForward` `:326` —— ssh 进 DUT `cd target_dir && exec <executor>`，并带反向端口转发；同时 `OpenRemoteConsole` 读 dmesg。
- `Forward()` `:140` —— 记录反向隧道端口（manager 的 RPC 端口）。
- `repair()` `:216` / reboot `:236` —— 修复时尝试重启（USB 授权或 ssh reboot），best-effort。
- `Diagnose()` `:383` + `readPstoreContents()` `:366` —— 崩溃诊断 / 从 pstore 取日志。

## 四、syzkaller 与 KCOV 代码覆盖率

`docs/coverage.md` 的要点：

- syzkaller 用 **sanitizer coverage（tracing 模式）** + **KCOV** 收集覆盖率。
- 覆盖率基于编译器插入到目标代码里的**覆盖点（coverage points）**。一个覆盖点通常对应一个**基本块（basic block）**或一条 **CFG 边（control-flow edge）**：
  - Linux + clang 默认是 **CFG 边**；
  - gcc 默认是**基本块**。
- ⚠️ 重要的直觉修正：覆盖点是编译器在**中端优化之后**插入的，所以覆盖率**和源代码不是严格对应**的——可能出现"未覆盖行的下一行反而被标记为已覆盖"这种反直觉现象。覆盖率是**趋势性**指标，用来看整体进展很有用，但别把它当成逐行精确的真值。

## 五、崩溃信息的持久化

`docs/internals.md` 第 39–81 行：

- 找到崩溃后，信息存进 `workdir/crashes/`，**每种唯一崩溃一个子目录**。
- 每个子目录里：
  - `description`：一个唯一字符串，用于 bug 识别和去重；
  - 最多 100 对 `logN` / `reportN`：
    - `logN` = 原始 syzkaller 日志（含内核 console 输出 + 崩溃前执行的程序），可喂给 `syz-repro`（复现+最小化）或 `syz-execprog`（手动定位）；
    - `reportN` = 后处理并符号化后的崩溃报告（如 KASAN 报告）。
- `description` 靠 `pkg/report/` 里的一组正则从内核输出里提取。
- 三种特殊崩溃：`no output from test machine` / `lost connection to test machine` / `test machine is not executing programs`——这类通常没有 `reportN`，有时是 syzkaller 自身的 bug，但更多时候意味着内核 lockup 之类的严重问题。

## 六、Q&A

### Q1：fork 瞬态子进程也挡不住内核崩溃，那测试搞崩内核 / 污染整机状态怎么办？

**前提要纠正的直觉**：崩溃不是"要避免的意外"，而是 syzkaller **要达成的目标**（崩内核 = 找到 bug = 成功）。所以设计目标是"崩了之后怎么办（容错+恢复）"，不是"预防崩溃"。

- **fork 隔离的边界**（对照 `executor/common.h` 的 `loop()`）：
  1. Linux 上 executor 开 fork server 后，每收到一个程序就 `fork` 出一个瞬态子进程。
  2. 子进程跑 `execute_one()`，结束后 `doexit(0)`。
  3. 父进程轮询 `waitpid`。若超过 `program_timeout_ms`、或长时间无进展，就用 `kill_and_wait` 杀掉子进程（典型卡点：阻塞 syscall、seccomp 禁了 `exit_group`、userfaultfd 挂死）。
  4. 结果和覆盖率经**共享内存**回传。本轮临时工作目录随后删掉。
  5. 以上只能清掉**用户态污染**（子进程地址空间被写坏、泄漏的 fd、卡死的线程）。常驻 executor 可以立刻接下一个输入。
  6. fork **不隔离、也挡不住共享内核**。oops / KASAN / lockup 一旦发生，整机状态已坏，要靠下一节 manager 的检测与重建。

- **如果内核真的崩溃了**，syzkaller 靠 host 上的 manager 走完下面四步：
  1. **检测**：`vm/vm.go` 的 `monitorExecution()` 持续读目标机 console。用 `ContainsCrash` 识别 oops / KASAN 等内核崩溃串；也识别 `lost connection`、`no output`、`timeout` 等异常。
  2. **保存证据**：`pkg/report/` 用正则解析 console，生成符号化报告和用于去重的 `description`，写入 `workdir/crashes/`。目录里保留 `logN`（崩溃前执行过的程序与原始日志）和 `reportN`（处理后的报告）。
  3. **恢复目标机**：`Instance.Close()` 关掉当前实例，再由 dispatcher 拉起新实例。VM 场景是销毁后重建；isolated 物理机则尽量重启（`vm/isolated/isolated.go` 的 `repair()`：ssh `reboot`，或对 USB 设备重新授权）。这正是 manager 必须跑在稳定 host 上的原因：目标机可以挂，调度端不能挂。
  4. **复现**：崩溃不一定由最后一个程序单独触发，也可能是多个程序叠加状态后才出现。事后把 `logN` 交给 `syz-repro`（`pkg/repro/`），做二分和最小化，得到尽量短、尽量稳定的复现程序。

- **内核没有崩溃，但整机状态被污染**时（更难处理）：依赖 executor 沙箱（none / setuid / namespace）、单次 syscall 与整段程序的超时、threaded 执行，以及定期重启目标机来缓解。内核 fuzzing 的可复现性本身就不完美，这也是为什么复现要单独做成 `pkg/repro`。

- **小结**：fork 只做最内层的用户态隔离，保护常驻 executor。内核崩溃的收尾靠 host 上 manager：检测 → 解析并去重存盘 → 重建目标机 → 用 `syz-repro` 复现。设计取向是接受目标机会崩，把恢复和验明原因放在不会一起崩的 manager 一侧。
- 更细的源码放到阶段 8（manager / RPC / VM / 崩溃）和 `pkg/repro`。
