## 一、进入主线前先认识这些对象

阶段 0 说明了 syzkaller 为什么需要结构化程序和覆盖率反馈，阶段 1 说明了相关代码分别位于哪些目录。阶段 2 要把这些模块连成一条实际运行的数据流。

本文把运行 `syz-manager`、Go fuzzer 和 RPC server 的一侧称为 **Host**，把运行待测内核与 `syz-executor` 的机器或 VM 称为 **目标端**。两侧使用 FlatRPC 交换 `ExecRequest`、`ExecResult` 等消息；在当前远程 runner 路径中，这些 FlatRPC 消息经过 FlatBuffers 编码并承载在 TCP 连接上。

这里要区分协议层次：FlatRPC 规定消息有哪些类型和字段，并用长度前缀划分消息边界；TCP 只负责可靠、有序地传输字节。两者不是互相替代的选择，而是“FlatRPC over TCP”的上下层关系。

这一阶段关注的是**模块之间如何交接**，暂时不深入每个模块内部的算法：

| 这里只需要掌握 | 后续深入阶段 |
|---|---|
| `Prog` 是 Host 端的类型化程序，执行前会被降为低层指令 | 阶段 3：`Prog`、`Call`、`Arg` 与 syzlang |
| 程序来自从零生成或 corpus 变异 | 阶段 4：生成、变异和 `ChoiceTable` |
| 新 signal 会触发稳定性验证、最小化和入库 | 阶段 5：signal、triage 与 corpus 算法 |
| executor 解释指令、执行调用并收集 KCOV | 阶段 6：线程、fork server、超时与输出布局 |
| manager、RPC server 和目标机 runner 负责跨机器接力 | 阶段 8：manager、RPC、VM 和崩溃处理 |

阶段划分只限制本阶段讲到多深，不能省略支撑当前主线所必需的概念。下面先介绍程序、请求、执行槽、反馈和 triage。后文再追函数时，这些名字就都有明确来处。

### 1. `*prog.Prog`：一条测试程序的类型化内存对象

先拆开这个名字：

- `prog` 是 Go 包名；
- `Prog` 是该包中的结构体类型；
- `*` 表示指向 `Prog` 的指针。

它的核心定义位于 `prog/prog.go:15-22`：

```go
type Prog struct {
    Target   *Target
    Calls    []*Call
    Comments []string
}
```

所以，一个 `*prog.Prog` 就是 **Host 内存中一条 syzkaller 测试程序的结构化表示**。它不是可读的 syz 文本，也不是 executor 能直接解释的字节流，而是 fuzzer 可以生成、克隆、变异和最小化的 Go 对象。

三个主要字段分别表示：

- `Target`：程序属于哪个 OS/arch，例如 `linux/amd64`；其中保存该目标的 syscall、类型、resource、常量和地址布局；
- `Calls`：按执行顺序保存程序中的调用；
- `Comments`：与程序一起保存的注释，不参与核心执行语义。

每个调用又是一个 `Call`，定义于 `prog/prog.go:79-85`：

```go
type Call struct {
    Meta  *Syscall
    Args  []Arg
    Ret   *ResultArg
    Props CallProps
}
```

- `Meta` 指向调用定义，提供调用名称、call ID、内核 syscall number、参数类型、返回类型和属性；
- `Args` 保存这一次调用实际使用的参数对象；
- `Ret` 表示该调用产生的 resource 返回值；
- `Props` 保存异步执行、故障注入和重复执行等附加属性。

`Arg` 是参数接口，实际对象包括：

| 参数对象 | 大致含义 |
|---|---|
| `ConstArg` | 整数、flags、长度等标量值 |
| `PointerArg` | 指针及其指向的参数对象 |
| `DataArg` | 字符串或字节缓冲区 |
| `GroupArg` | 结构体或数组中的一组字段 |
| `UnionArg` | union 中当前选中的分支 |
| `ResultArg` | resource 值，或对前面调用结果的引用 |

例如：

```text
r0 = openat(..., './file1', ...)
write(r0, 'data', 4)
close(r0)
```

在内存中可以先理解为：

```text
Prog
├── Target: linux/amd64
└── Calls
    ├── Call[0]: openat
    │   ├── Meta: openat 的接口定义
    │   ├── Args
    │   │   ├── ConstArg: AT_FDCWD
    │   │   ├── PointerArg
    │   │   │   └── DataArg: "./file1\0"
    │   │   ├── ConstArg: flags
    │   │   └── ConstArg: mode
    │   └── Ret: ResultArg r0
    ├── Call[1]: write
    │   ├── Args[0]: ResultArg ─────► Call[0].Ret
    │   └── Args[1]: PointerArg ────► DataArg "data"
    └── Call[2]: close
        └── Args[0]: ResultArg ─────► Call[0].Ret
```

这是一棵带调用顺序和跨调用引用的对象图。阶段 3 会继续研究 syzlang 怎样形成 `Target`、`Call` 和各类 `Arg`；阶段 4 会研究这棵对象图怎样被生成和变异。本阶段只需先知道：**`Prog` 是一条完整测试用例在 Host 端的高层表示。**

### 2. `queue.Request`：围绕程序建立的一张执行工单

`Prog` 只回答“执行什么”，还没有说明：

- 这次要不要收集 signal 或完整 cover；
- 使用什么沙箱和执行模式；
- 应该避开哪个 VM 或执行槽；
- VM 崩溃后要不要重试；
- 结果返回后交给谁处理。

因此 fuzzer 会把 `Prog` 包装进 `queue.Request`。其主要定义位于 `pkg/fuzzer/queue/queue.go:24-61`：

```go
type Request struct {
    Type     flatrpc.RequestType
    ExecOpts flatrpc.ExecOpts
    Prog     *prog.Prog

    ReturnAllSignal []int
    ReturnError     bool
    ReturnOutput    bool
    Stat            *stat.Val
    Important       bool
    Avoid           []ExecutorID

    // 另有完成回调、结果和等待通道等内部字段。
}
```

所以答案是明确的：**普通程序请求中的 `Request.Prog` 就是一个 `*prog.Prog`。**

可以把 `Request` 看成一张执行工单：

| 字段 | 回答的问题 |
|---|---|
| `Prog` | 执行什么程序 |
| `Type` | 这是普通 syz 程序、二进制测试，还是 glob 请求 |
| `ExecOpts.EnvFlags` | 使用什么沙箱和目标端执行环境 |
| `ExecOpts.ExecFlags` | 本次收集 signal、cover 还是 comparisons，是否 threaded |
| `ReturnAllSignal` | 哪些调用的 signal 不应被目标端“已见集合”省略 |
| `ReturnOutput` | 是否需要 executor 的 stdout/stderr |
| `ReturnError` | executor 内部失败是否作为普通结果返回 |
| `Avoid` | 尽量避开哪些 VM/proc |
| `Important` | VM 崩溃时是否仍应重试 |
| `Stat` | 完成后更新哪项执行统计 |
| 完成回调与等待通道 | 结果回来后由谁处理，谁在等待 |

这里需要把“同一个 `Prog` 被重复执行”说得更准确。普通 fuzz、triage、最小化和 comparison hints 不是 `Prog` 自身的四种状态，而是 **围绕一条程序开展的四类执行任务**。这些后续任务会建立各自的 `queue.Request`；前一次普通 fuzz 使用的 `Request` 不会一直改造后继续充当 triage 请求。candidate 重试等机制可以把同一张请求重新入队，但那属于同一执行意图的重试，不影响 `Prog` 与执行任务的职责划分。

程序对象也不一定始终是同一个 Go 指针：

- 内容不需要修改时，可以让多个新 `Request` 引用同一个 `*prog.Prog`；
- 需要与原对象隔离时，会先调用 `Prog.Clone()`，得到内容相同、内部资源关系等价但可以独立修改的副本；
- 最小化或 hints 需要修改程序时，会从该副本继续产生调用更少、参数更简单或参数值不同的 `Prog` 变体。

从一条普通 fuzz 程序开始，关系大致如下：

```text
新生成或变异的 p0
  │
  └── Request{Prog: p0, CollectSignal}
          │ 首次执行发现潜在新 signal
          ▼
      p1 := p0.Clone()                 交给 triageJob
          │
          ├── 多个 Request{Prog: p1}  原样重执行，验证 signal 是否稳定
          │
          └── p2、p3……                 尝试删除调用或简化参数
                └── 各自建立 Request  实际执行，验证是否仍保留目标 signal
                        │ 接受其中可行的修改，得到 p_min
                        │ 若启用 comparisons
                        ▼
                    p4 := p_min.Clone() 交给 comparison hints
                        ├── 原样执行 p4  收集稳定的比较操作数
                        └── 生成若干变体  把提示值代入参数后执行，寻找新 signal
```

各类任务建立 `Request` 时，想回答的问题不同：

| 执行任务 | `Request.Prog` 大致来自哪里 | 主要执行选项 | 这次执行要回答什么 |
|---|---|---|---|
| 普通 fuzz | 新生成的程序，或从 corpus 克隆后变异的程序 | `CollectSignal` | 是否出现了 Host 尚未见过的 signal |
| triage 的 deflake | 首次发现程序的克隆；多次执行期间内容保持不变 | `CollectSignal + CollectCover`，并对关注调用设置 `ReturnAllSignal` | 原 signal 能否稳定重现，同时收集该程序的 cover |
| 最小化验证 | `prog.Minimize()` 提出的更小 `Prog` 候选 | `CollectSignal`，并对关注调用设置 `ReturnAllSignal` | 删除调用或简化参数后，目标 signal 是否仍然存在 |
| comparison hints | 先执行有价值程序的克隆，再执行根据比较值生成的参数变体 | 原程序用 `CollectComps`；变体用 `CollectSignal` | 内核拿输入与什么值比较；把这些值代入参数后能否发现新 signal |

comparison hints 可以先理解为一种定向变异：如果 KCOV 观察到内核把某个输入与一个常量比较，fuzzer 就尝试把该常量写进匹配的 syscall 参数，而不是只做随机修改。`CollectComps` 与 `CollectSignal/CollectCover` 在一次请求中互斥，所以“先收集比较值”和“再执行参数变体判新”是两批不同请求。

对应源码分别位于 `pkg/fuzzer/fuzzer.go:168` 的 triage 克隆、`pkg/fuzzer/job.go:228` 的重复验证、`pkg/fuzzer/job.go:350` 的最小化验证，以及 `pkg/fuzzer/job.go:538-585` 的 comparison hints。

因此，真正保持稳定的是职责边界：`Prog` 描述调用序列、参数和资源引用，即“执行什么”；`Request` 描述某一次执行为何发生、收集什么反馈以及结果交给谁，即“这次怎样执行、为了验证什么”。这正是二者分开的原因。

这里的沙箱选项决定 executor 以哪种受限环境运行，例如 namespace 或 setuid；`threaded` 则允许程序中的调用由工作线程调度，使调用可能重叠。它们的具体执行语义属于阶段 6，本阶段只需知道这些策略属于“怎么执行”，因此放在 `Request` 而不是 `Prog` 中。

### 3. 两个 runner 与目标端 `Proc`

这条链上有两个都叫 runner 的对象，必须先分开：

| 名称 | 所在位置 | 职责 |
|---|---|---|
| Host 侧 `rpcserver.Runner` | `pkg/rpcserver/runner.go` | 代表一条目标机连接，从请求源取 `queue.Request`，发送 FlatRPC，并把结果交回原请求 |
| 目标侧 C++ `Runner` | `executor/executor_runner.h` | 运行在 `syz-executor runner` 进程中，接收 `ExecRequest` 并分派给本机执行槽 |

目标端 C++ `Runner` 会创建若干 `Proc`。`Proc` 不是 `prog.Prog`，也不能简单等同于一个 PID。它是 **目标端 runner 管理的一个执行槽**，定义于 `executor/executor_runner.h:109-247`。

每个 `Proc` 拥有：

- 一个 proc ID；
- 一个以 `syz-executor exec` 方式启动、必要时可重启的子进程；
- 独立的输入和输出共享内存；
- 请求、响应和日志管道；
- 当前 `ExecRequest`；
- `Started / Handshaking / Idle / Executing` 状态；
- 超时、重试次数，以及同一 `exec` 进程此前执行过多少程序（`freshness`）等运行状态。

关系如下：

```text
目标端 syz-executor runner
├── Proc 0：执行槽
│   ├── syz-executor exec / fork server
│   └── 当前请求的瞬态测试子进程
├── Proc 1：执行槽
│   ├── syz-executor exec / fork server
│   └── 当前请求的瞬态测试子进程
└── ...
```

一条网络连接可以服务多个 `Proc`。这样目标机可以并行执行多个程序，同时让每个执行槽拥有独立的共享内存、管道、超时和重启状态。

### 4. cover、signal 与 `maxSignal`

executor 从 KCOV 得到的基础材料是内核执行过程中经过的程序计数器地址，即 PC 序列。syzkaller 会把它整理为两种不同用途的反馈：

- **cover**：本次执行经过的内核 PC，信息较完整，但数据量也较大；
- **signal**：从 PC 进一步整理出的紧凑反馈，主要供 fuzzer 快速判断是否出现了新的执行行为。

Host 还维护 `maxSignal`，表示目前已经观察过的 signal 集合。普通 fuzz 的绝大多数输入没有新行为，因此没有必要每次都把完整 cover 从目标机传回 Host。普通请求主要收集 signal；只有发现潜在新 signal 后，triage 才为值得继续处理的程序请求更完整的反馈。

三个容易混淆的控制项先记住轮廓：

| 控制项 | 含义 |
|---|---|
| `CollectSignal` | 本次计算并返回 signal |
| `CollectCover` | 本次返回较完整的覆盖率 PC |
| `ReturnAllSignal` | 对指定调用，即使 signal 已经见过也要返回 |

它们为何这样组合，会在第九节结合首次执行和 triage 重执行具体解释。

### 5. corpus、candidate 与 triage

先定义 triage 的终点。**corpus（语料库）**是当前 fuzzer 保留的有价值程序集合；其中的程序已经在当前运行中提供了有用的稳定 signal，之后既是覆盖率成果，也是继续变异的素材。磁盘上的 `corpus.db` 是跨重启保存的程序数据库，而 fuzzer 运行时还会建立自己的内存 corpus。

manager 启动时不会不经检查地把 `corpus.db`、seed 或 hub 提供的程序直接当成当前内存 corpus。这里的 seed 是随目标描述或配置提供的初始测试程序；hub 是多个 manager 之间交换有价值程序的服务。内核版本、配置和可用调用都可能已经变化，因此这些待执行、待验证的已有程序先叫作 **candidate（候选程序）**。candidate 经过当前内核上的执行和 triage 后，仍然有价值的程序才进入本次运行的内存 corpus。

本文中的 **triage（复查筛选）**也不是默认读者已经掌握的术语。它指：首次执行发现潜在新 signal 后，对这个程序进行重复验证、最小化和入库判断的后台任务。

```text
首次发现潜在新 signal
        │
        ▼
deflake：重复执行，排除偶发 signal
        │
        ▼
minimize：尝试缩小程序，并实际重执行验证
        │
        ▼
Corpus.Save：保存稳定且尽量小的程序
```

不能在首次发现后立即入库，因为 signal 可能受并发和时序影响而偶发，原程序也可能包含许多与新行为无关的调用。直接保存会让 corpus 迅速积累不稳定或冗长的程序。

后文第一次进入这条分支时会再次说明 triage 的输入和输出；阶段 5 再深入它的集合运算和停止条件。

有了这些概念，看到 `read_input()`、`write_signal()` 或 `triageJob` 时，本阶段要理解的是它们在接力链中的作用。具体生成策略、signal 算法和 executor 调度细节会在后续阶段展开，但这些对象的基本轮廓不会再省略。

## 二、完整主线

### 1. 主线开始前，系统已经完成什么

正常 fuzzing 开始前，manager 已经创建 corpus 和 fuzzer，并把 fuzzer 接到 RPC server 的请求源；目标机上的 executor runner 也已连接，并按配置创建若干 `Proc`：

```text
syz-manager.MachineChecked()
├── 创建 corpus.Corpus
├── 创建 fuzzer.Fuzzer
├── 把已有 corpus 程序加入 candidate 队列
└── RPCServer.SetSource(fuzzer)

目标机连接 Host
└── syz-executor runner 完成握手
    └── 创建 N 个 Proc 执行槽
```

详细初始化代码在第四节继续定位。这里先把它看作端到端循环的起始状态。

### 2. 谁触发 `genFuzz()`

普通 fuzz 请求是由空闲执行能力向上拉取出来的，不是几个函数自行运行：

```text
目标机仍有空闲执行能力
        │
        ▼
Host rpcserver.Runner.ConnectionLoop()
        │ source.Next(vmID)
        ▼
queue.Distributor
        │
        ▼
fuzzer.Next()
        │
        ▼
依次检查 candidate / triage / smash 等队列
        │ 没有现成任务
        ▼
genFuzz()
        │
        ├── mutateProgRequest()
        └── genProgRequest()
                │
                ▼
          *queue.Request
```

这条调用背景解释了后文函数的来处：目标端有空闲执行槽，Host 侧连接循环需要下一张执行工单，于是一路从 fuzzer 的请求源取得或现场生成 `Request`。

图中的 candidate 是等待在当前内核上验证的已有程序，triage 是对潜在新 signal 的复查筛选，smash 是围绕有价值程序做的一批强化变异。第五节会具体区分这些队列以及它们的优先关系。

### 3. 完整数据流

下面画出正常执行并产生稳定新 signal 的完整路径：

```text

│                                           │ SerializeForExec()       │
│                                           ▼                          │
│                                FlatRPC ExecRequest{Data: 执行字节流}  │
└─────────────────────────────────────────────┬────────────────────────┘
                                              │ FlatRPC over TCP
                                              ▼
                                  Target：syz-executor
┌──────────────────────────────────────────────────────────────────────┐

│                                         │                            │
│                                         ▼                            │

┌──────────────────────────────────────────────────────────────────────┐

│                                     │                               │

│                                      │ 有                            │

│                    重复执行去除不稳定 signal ─► 最小化并验证             │
│                                      │                               │
│                                      ▼                               │
│                         Corpus.Save() ─► corpus.db                   │
│                               │                                      │
│                               └────────► 成为后续变异素材              │
└──────────────────────────────────────────────────────────────────────┘
```

这张图需要同时记住三个事实。

第一，持续 fuzzing 的起点不是固定的 `Target.Generate()`。当覆盖率可用时，`genFuzz()` 默认大约 95% 的机会从 corpus 选择程序并变异，约 5% 的机会从零生成；如果 corpus 为空，变异无法取得程序，也会退回从零生成。源码位置是 `pkg/fuzzer/fuzzer.go:285-308` 和 `pkg/fuzzer/job.go:53-80`。

第二，`queue.Request` 与 FlatRPC 的 `ExecRequest` 不是同一个对象。前者是 Host 端 Go 进程内的调度对象，后者才是发到目标机的网络消息。

第三，“发现新 signal”不等于“立即入库”。首次执行只标记一个潜在新输入；它必须经过 triage，确认存在足够稳定的新 signal，并在最小化后仍能保留该 signal，才会进入 corpus。这里特意不用 candidate 称呼它，因为 `Candidate` 在代码中专指从已有 corpus、seed 或 hub 等来源送来、尚待当前运行验证的程序。

## 三、接力过程中程序的几种形态

同一个逻辑程序在不同边界上会变成不同对象。分清这些形态，可以避免把程序表示、调度协议和网络协议混为一谈。

| 所在位置 | 主要形态 | 作用 |
|---|---|---|
| Host 的 `prog/` | `*prog.Prog` | 保存类型化的调用序列、参数和资源引用 |
| Host 的 fuzzer/queue | `*queue.Request` | 携带程序、执行选项、调度约束、统计和完成回调 |
| Host 到 executor 的执行负载 | `[]byte` | `SerializeForExec()` 生成的低层执行指令 |
| FlatRPC 请求 | `ExecRequest` | 携带请求 ID、执行字节流、执行标志和信号返回要求 |
| executor 内部 | 请求共享内存 + `execute_req` | 共享内存保存程序字节，控制管道传递请求 ID 和标志 |
| FlatRPC 响应 | `ExecResult` / `ProgInfo` / `CallInfo` | 携带每个调用的 errno、signal、cover、状态和执行元数据 |
| Host 的完成结果 | `*queue.Result` | 把网络结果交回原请求及其完成回调 |
| corpus 输入 | `corpus.NewInput` | 携带最小化程序、稳定 signal、cover 和产生 signal 的调用 |

还有两种名字相近但用途不同的序列化：

- `Prog.Serialize()` 生成可读的 syz 程序文本，可用于日志、哈希、corpus 数据和人工查看；
- `Prog.SerializeForExec()` 生成 executor 解释的二进制指令流，是低层、不可逆的执行格式。

## 四、运行前的连接：manager 如何把 fuzzer 接到 executor

完整 fuzzing 开始前，manager 已经完成目标机检查和 executor 握手。阶段 2 不展开启动 VM 和握手协议，只看与主线有关的结果。

`syz-manager/manager.go:1127-1216` 中的 `MachineChecked()` 会：

1. 加载已有 `corpus.db` 中的程序作为候选；
2. 创建带更新通道的 `corpus.Corpus`；
3. 创建 `fuzzer.Fuzzer`，并把 corpus、可用系统调用和功能开关交给它；
4. 把已有程序作为 candidate 交给 fuzzer 重新执行，发现 signal 后再进入 candidate triage；
5. 用 `queue.DefaultOpts()` 补充默认执行选项；
6. 调用 `mgr.serv.SetSource(source)`，把 fuzzer 接到 RPC server 的请求源。

RPC server 在 `pkg/rpcserver/rpcserver.go:212-241` 中用动态请求源和 `queue.Distributor` 组织请求；每个已连接目标机在 `CreateInstance()` 中得到一个 Host 侧 `rpcserver.Runner`。runner 之后可以不断从同一个请求源取程序。

executor 与 manager 的版本、架构和目标描述 revision 已在连接握手时检查。这样 Host 生成的 call ID 和目标端 `syscalls[]` 表才能保持一致。握手细节已经在阶段 1 说明，阶段 8 会再完整追踪。

## 五、第一棒：产生一个 `Prog`

### 1. fuzzer 有哪些执行队列

这里的“队列”不是目标端的网络收包队列，也不是 executor 内部的调用线程队列，而是 **Host 侧 fuzzer 保存待执行 `queue.Request` 的几类工作源**。目标机有空闲能力时，Host 会从这些工作源取出下一张执行工单。

先看各类工作的来路：

```text
已有 corpus.db / seed / hub 程序
        │
        └──► candidateQueue：先在当前内核上执行一次
                    │ 若发现当前运行尚未见过的 signal
                    ▼
             triageCandidateQueue：复查和最小化已有候选

普通生成或变异程序
        │ 首次执行发现潜在新 signal
        ▼
triageQueue：复查和最小化本轮 fuzz 新发现的程序
        │ 确认有价值
        ▼
smashQueue：围绕有价值程序做强化探索

以上暂时都没有可执行请求
        │
        └──► genFuzz()：现场生成一张普通 fuzz 请求
```

四个队列的职责是：

| 工作源 | 放进去的是什么 | 为什么单独存在 |
|---|---|---|
| `triageCandidateQueue` | candidate 首次执行发现 signal 后，`triageJob` 产生的重复验证、收集 cover 和最小化请求 | 优先完成启动或新接收候选的复查，尽快重建当前运行真正可用的 corpus |
| `candidateQueue` | 从本地 `corpus.db`、seed、hub 等来源取得的 candidate 的首次执行请求 | 旧程序在新的内核、配置或 syscall 集合上未必仍然有效，需要先重新执行 |
| `triageQueue` | 普通 fuzz 首次发现潜在新 signal 后，`triageJob` 产生的重执行和最小化请求 | 在继续大范围探索前，确认新发现是否稳定并保留有价值程序 |
| `smashQueue` | `smashJob`、comparison hints 和 fault injection 等强化任务产生的请求 | 它们都围绕已经证明有价值的程序继续深挖，但不应长期占满全部执行能力 |

其中，**smash** 指围绕一个刚确认有价值的程序做一批更集中的变异执行。当前 `smashJob` 会克隆该程序并变异执行 25 次。comparison hints 会利用内核比较操作数引导参数变异；fault injection 会尝试在调用路径上注入失败。这些算法留到阶段 5，本阶段只需知道它们会继续产生普通的 `queue.Request`。

严格说，`genFuzz()` 不是一个储存请求的队列，而是一个按需生产请求的回调。前四类暂时取不到工作时，它才现场选择“从 corpus 变异”或“从零生成”，保证执行能力不会闲置。

### 2. 队列优先级怎样工作

`pkg/fuzzer/fuzzer.go:92-115` 用 `queue.Order()` 按下面的次序查询：

```text
triageCandidateQueue
        ↓ 为空
candidateQueue
        ↓ 为空
triageQueue
        ↓ 为空
smashQueue（会定期主动让出一次机会）
        ↓ 本轮未取到
genFuzz()
```

`queue.Order()` 每次从前往后查询，返回第一个非空工作源给出的请求。因此，这不是给每个请求计算一个数值分数，而是工作源之间的固定优先顺序。

两个 triage 队列使用 `DynamicOrderer`：每个新 `triageJob` 会取得自己的子队列，较早创建的 job 产生的请求始终排在较晚 job 之前，避免同时启动大量复查却都只完成一部分。`candidateQueue` 和 `smashQueue` 则是普通的先进先出队列。

`smashQueue` 外面还有 `queue.Alternate()`。默认情况下，它每三次查询主动返回一次空，让排在后面的 `genFuzz()` 获得机会。也就是说，即使强化任务很多，fuzzer 仍会定期探索更广的程序空间。

这套顺序表达的是：先验证已有输入并重建当前 corpus，再及时确认新发现，然后在“围绕已知有价值输入深挖”和“继续广泛生成、变异”之间分配执行能力。

因此，executor 空闲时取得的下一项可能是 candidate 的首次执行，也可能是 triage、最小化或 smash 的重执行，还可能是现场生成的普通 fuzz。它们都沿用同一条序列化、RPC、executor 和回传路径，只是请求标志和完成后的处理不同。

本文选择一条普通 fuzz 请求作为主角。

### 3. 从零生成或选择语料变异

`genFuzz()` 位于 `pkg/fuzzer/fuzzer.go:285-308`。覆盖率可用时：

- 大约 95% 的机会调用 `mutateProgRequest()`；
- 其余情况调用 `genProgRequest()`；
- corpus 为空时，`ChooseProgram()` 返回 `nil`，同样会退回生成；
- 还可能把程序改成并发执行形式，制造调用之间的竞争。

从零生成的路径是：

```text
genProgRequest()
    │
    └─ Target.Generate(rnd, RecommendedCalls(), ChoiceTable())
           │
           └─► *prog.Prog
```

`Target.Generate()` 位于 `prog/generation.go:12-34`。它建立生成状态，反复调用 `generateCall()`，分析新调用对资源状态的影响，最后修整调用数量并校验程序。这里的 `ChoiceTable` 是根据已启用调用、资源依赖和 corpus 统计等信息建立的带权选择表，用来影响下一条调用的选择；具体生成和参数算法属于阶段 4。

变异路径是：

```text
Corpus.ChooseProgram()
    │ 选择已有程序
    ▼
Prog.Clone()
    │
    └─ Prog.Mutate(...)
           │
           └─► 新的 *prog.Prog
```

`mutateProgRequest()` 位于 `pkg/fuzzer/job.go:64-80`，`Corpus.ChooseProgram()` 位于 `pkg/corpus/prio.go:41-73`。先克隆再变异，可以避免直接改坏 corpus 中应视为只读的程序。

### 4. 包装为 `queue.Request`

生成和变异路径都会把 `*prog.Prog` 放进 `Request.Prog`。例如 `genProgRequest()` 的核心返回值是：

```go
return &queue.Request{
    Prog:     p,
    ExecOpts: setFlags(flatrpc.ExecFlagCollectSignal),
    Stat:     fuzzer.statExecGenerate,
}
```

因此，此时的关系就是：

```text
Request
├── Prog ─────────────► 刚生成或变异的 *prog.Prog
├── ExecOpts ─────────► 本次先收集 signal
├── Stat ─────────────► 记为 generate 或 fuzz 执行
└── callback/done ────► 随后由 fuzzer.prepare() 安装和使用
```

普通请求接下来的完整生命周期如下：

```text
genProgRequest() / mutateProgRequest()
        │ 创建 Request{Prog, ExecOpts, Stat}
        ▼
fuzzer.prepare(req)
        │ 安装 processResult() 完成回调
        ▼
queue.DefaultOpts
        │ 补充沙箱、threaded 等默认执行选项
        ▼
queue.Distributor
        │ 读取 Avoid，选择适合的 VM
        ▼
rpcserver.Runner.sendRequest(req)
        │
        ├── req.Prog.SerializeForExec()
        ├── req.ExecOpts        → ExecRequest.ExecOpts
        ├── req.ReturnAllSignal → ExecRequest.AllSignal
        ├── req.ReturnOutput    → RequestFlagReturnOutput
        ├── req.ReturnError     → RequestFlagReturnError
        └── req.Avoid           → 目标端 proc 避让位图
```

Host 不会把这个 Go 对象直接放上网络。它只从 `Request` 提取 FlatRPC 所需的信息，同时把原对象保存在 Host 内存中，等待结果回来。

其他字段也会在后续路径实际使用：

| 字段 | 后续使用位置和作用 |
|---|---|
| `Prog` | `sendRequest()` 生成执行字节；结果回来后又用于校准调用结果、输出可读程序和创建 triage |
| `ExecOpts` | 写入 `ExecRequest`；目标端据此选择沙箱、threaded 以及 signal/cover/comps 收集方式 |
| `ReturnAllSignal` | 写入 `ExecRequest.AllSignal`；目标端为指定调用绕过 `max_signal` 过滤 |
| `ReturnOutput` / `ReturnError` | 转换为协议 flags，控制是否回传进程输出和 executor 内部错误 |
| `Avoid` | Host 的 `Distributor` 先尝试避开 VM，目标端 runner 再尝试避开具体 `Proc` |
| `Important` | `queue.Retry` 在 VM 崩溃时决定是否重试一次该请求 |
| `Stat` | `Request.Done()` 最终完成时增加对应统计 |
| 完成回调 | `req.Done()` 时先进入 `processResult()`；重试包装层也通过回调截获结果 |
| `done/result` | triage、最小化等需要同步结果的代码通过 `req.Wait()` 等待 |

不是每个普通 fuzz 请求都会用到所有字段。例如 `ReturnAllSignal` 主要由 triage 使用，`ReturnError` 常用于机器能力检查。把它们集中在同一种执行工单中，可以让不同任务共用后面的调度和 RPC 路径。

## 六、第二棒：Host 端调度、降级和发送

### 1. runner 从请求源取下一项

Host 侧 `rpcserver.Runner.ConnectionLoop()` 位于 `pkg/rpcserver/runner.go:141-233`。只要连接仍然有效，它会：

1. 调用 `runner.source.Next(runner.id)` 取得适合该 VM 的请求；
2. 用 `sendRequest()` 发送；
3. 记录请求 ID 到原始 `queue.Request` 的映射；
4. 接收 `ExecutingMessage`、`ExecResult` 或状态响应。

`queue.Distributor` 会尽量遵守 triage 请求中的 `Avoid`，让重复验证分散到不同 VM 或 proc，减少某个 executor 局部状态造成的误判。这个约束是软约束：没有其他可用执行器时仍可在同一处执行。

### 2. `SerializeForExec()` 把高层程序降为执行指令

真正发送前，`sendRequest()` 在 `pkg/rpcserver/runner.go:306-380` 调用：

```go
progData, err := req.Prog.SerializeForExec()
```

`SerializeForExec()` 位于 `prog/encodingexec.go:69-91`。当前格式是一串变长编码的整数和原始数据，开头是调用总数，结尾是 `execInstrEOF`。每个调用会被展开成下列低层动作：

1. 生成必要的 `copyin`，把路径、缓冲区、结构体字段和已有资源值写入 executor 数据区；
2. 必要时生成运行时校验和指令；
3. 必要时生成 `setprops`；
4. 写入 call ID、调用返回值的保存槽、参数数量和低层参数；
5. 生成必要的 `copyout`，把后续调用还要引用的输出内存值保存到结果槽中。系统调用的直接返回值已经由第 4 步中的返回值槽保存，不需要再生成一条 `copyout`。

相关代码位于 `prog/encodingexec.go:93-130`、`228-249` 和 `305-320`。

这里写入的是 `Call.Meta.ID`，也就是当前 `Target` 中的 call ID。它不是直接等同于 Linux syscall number。目标端会用它索引生成的 `syscalls[]`，再取得真实系统调用号或伪调用函数。

### 3. 用 `openat → write → read → close` 理解降级

仓库中的 `sys/linux/test/file` 是一个很小的例子：

```text
r0 = openat(0xffffffffffffff9c, &AUTO='./file1\x00', 0x42, 0x1ff)
write(r0, &AUTO="01010101", 0x4)
read(r0, &AUTO=""/4, 0x4)
close(r0)
```

Host 端仍能理解：

- `openat` 返回的是 `fd` resource；
- 后三条调用的第一个参数引用同一个 resource；
- 三个 `&AUTO` 分别表示路径字符串、`write` 的输入缓冲区和 `read` 的输出缓冲区；
- 路径和写缓冲区必须在调用前准备内容，读缓冲区只需预留一块让内核写入的内存。

`SerializeForExec()` 要把这些类型和方向信息提前消解成 executor 能直接执行的动作。用 `A`、`B`、`C` 代表 Host 在 executor 数据区中已经选好的三个地址，实际解码结果可以简化为：

```text
copyin A <- "./file1\0"
call   openat(AT_FDCWD, A, 0x42, 0x1ff), return-slot=0

copyin B <- {0x01, 0x01, 0x01, 0x01}
call   write(result[0], B, 4), return-slot=none

call   read(result[0], C, 4), return-slot=none

call   close(result[0]), return-slot=none
EOF
```

这里的调用名称只是为了便于阅读；真实字节流中保存的是 call ID、参数编码和结果槽编号。

#### 第一步：路径为什么变成 `copyin + 地址 A`

高层 `Prog` 中，`&AUTO='./file1\x00'` 是一个 `PointerArg`，它指向保存字符串的 `DataArg`。Linux syscall 不能直接接收 Go 对象，因此 Host 先完成两件事：

1. 在 executor 预先映射的数据区中为字符串确定地址 `A`；
2. 生成 `copyin`，要求 executor 在调用前把 `"./file1\0"` 写到 `A`。

随后 `openat` 的第二个参数只需编码为地址 `A`。executor 先解释 `copyin` 准备内存，再发起 `openat(..., A, ...)`。

#### 第二步：`r0` 为什么变成 `result[0]`

Host 发现 `openat` 的返回值会被后续调用引用，于是给它分配结果槽 0，并把这个槽编号写进 `openat` 的 call 指令。`openat` 执行结束后，executor 把实际返回值保存到自己的 `results[0]`。

`write`、`read` 和 `close` 中的 `r0` 不再携带“这是 fd resource”的类型描述，而是编码成 `arg_result{index: 0}`。executor 的 `read_arg()` 看到这种参数时，从 `results[0]` 取出实际整数作为 syscall 参数。

因此，resource 依赖没有消失，只是从高层的对象引用：

```text
write.Args[0] ──► openat.Ret
```

降成了低层的结果槽引用：

```text
write.arg[0] ──► results[0]
```

executor 不需要再判断这个整数在 syzlang 中是不是 `fd`；这个合法依赖已经由 Host 在序列化前确认。

#### 第三步：为什么 `write` 有 `copyin`，`read` 没有

`write` 的缓冲区是输入参数。内核读取地址 `B` 前，其中必须已经存在四个 `0x01`，所以序列化结果包含一条 `copyin B`。

`read` 的缓冲区方向是输出。内核负责向地址 `C` 写数据，调用前不需要准备有效内容，因此 `writeCopyin()` 会跳过这个 `DirOut` 参数。地址 `C` 仍会作为普通地址参数传给 `read`。

这个程序后面既不引用 `read` 写入的四个字节，也不引用 `read` 的直接返回值，所以二者都不需要结果槽。

#### 第四步：这个例子为什么没有 `instr_copyout`

容易混淆的是，保存 syscall 的直接返回值与 `instr_copyout` 是两种机制：

| 情况 | 怎样保存 |
|---|---|
| `openat()` 通过 CPU 返回值返回 fd | call 指令携带 `return-slot=0`，调用结束后直接写入 `results[0]` |
| 某个 syscall 把 resource 或标量写入输出指针，并且后续调用还要使用它 | 调用后执行 `instr_copyout`，从数据区指定地址读取该值并写入某个 `results[]` 槽 |

例如 `pipe2()` 会把两个 fd 写进用户提供的数组。如果后续调用引用其中一个 fd，Host 就需要生成 `copyout`，把数组中的对应整数从 executor 数据区取到结果槽。这里的 `copyout` 只是“数据区内存 → executor 本地结果表”，不是把整个缓冲区通过 RPC 返回给 Host。

当前 `openat → write → read → close` 程序没有任何“由内核写入内存、又被后续调用引用”的值，所以没有单独的 `instr_copyout`。

上述规则分别对应 `prog/encodingexec.go:93-130` 的 call 与直接返回值槽、`228-249` 的 `writeCopyin()`、`305-320` 的 `writeCopyout()`，以及 `executor/executor.cc:1345-1375`、`1722-1752` 的结果保存和参数读取。

整个降级过程可以归纳为：

| Host 端高层信息 | executor 字节流中的低层表示 |
|---|---|
| 调用定义和名称 | call ID |
| 输入指针及其内容 | 数据区地址 + 调用前的 `copyin` |
| 只供内核写入的输出指针 | 数据区地址，通常没有调用前 `copyin` |
| 跨调用 resource 引用 | `results[]` 槽编号 |
| 直接返回值被后续使用 | call 指令自带的返回值槽 |
| 输出内存中的值被后续使用 | 调用后的 `instr_copyout` |

所以，“降级”不是简单地把 syz 文本翻译成 syscall 文本，而是 Host 提前完成地址分配、参数方向判断和 resource 依赖解析，只把内存准备、结果槽读写和 call ID 留给 executor 解释。

### 4. 封装成 FlatRPC 请求

`sendRequest()` 把执行字节流放入 `flatrpc.ExecRequest.Data`，同时加入：

- `Id`：用于把结果配回原请求；
- `Type`：普通程序为 `RequestTypeProgram`；
- `ExecOpts`：环境和本次执行选项；
- `Avoid`：目标端 proc 避让掩码；
- `AllSignal`：需要绕过目标端 `max_signal` 已见过滤的调用索引；
- `Flags`：是否返回进程输出或内部错误。

FlatRPC 的消息定义位于 `pkg/flatrpc/flatrpc.fbs:97-186`。`flatrpc.Send()` 在 `pkg/flatrpc/conn.go:119-134` 中先把消息编码成带长度前缀的 FlatBuffers 字节，再写入 TCP 连接；接收端从 TCP 字节流中按长度取出一条消息并解包。因此，图中的跨机器箭头既可以从传输层称为 TCP，也可以从应用消息层称为 FlatRPC，更完整的写法是“FlatRPC over TCP”。

发送前，Host 侧 runner 还会执行：

```go
runner.requests[id] = req
```

这张映射保留了“协议请求 ID → 原始 Go 执行工单”的关系：

```text
Host 内存
  runner.requests[42] ───► 原 queue.Request
                              └── Prog、回调、统计、等待通道……

网络
  ExecRequest{
      Id: 42,
      Data: SerializeForExec 产生的字节，
      ExecOpts / AllSignal / Flags: 从 Request 提取的控制信息，
  }
```

所以，`queue.Request` 本身没有跨过网络；跨过去的是从它提取并重新封装的 `ExecRequest`。结果以 `Id=42` 返回后，Host 才能重新找到同一张工单及其中没有放上网络的 `Prog`、回调和等待状态。

## 七、第三棒：目标机上的 runner、exec 和瞬态测试子进程

### 1. 外层 runner 维护网络连接

目标机由下面的命令启动网络 runner：

```text
syz-executor runner <vm-index> <manager-address> <manager-port>
```

这里开始讨论的是**目标端 C++ runner**，不是上一节的 Host 侧 `rpcserver.Runner`。入口位于 `executor/executor.cc:582-590` 和 `executor/executor_runner.h:964-1008`。它长期维护 FlatRPC 连接，并管理多个 `Proc`。`executor/executor_runner.h:610-659` 的循环从连接接收 `ExecRequest`，然后交给空闲 `Proc`；没有空闲执行槽时，请求先留在目标端 runner 的队列中。

`Proc` 不是一次测试的瞬态进程，也不只是一个 PID。它是 runner 中管理一个 `syz-executor exec` 子进程的持久**执行槽对象**，并负责：

- 启动或重启 `exec` 子进程；
- 管理请求和响应共享内存；
- 通过控制管道发送执行选项并接收完成状态；
- 监控超时和进程异常；
- 把共享内存中的结果封装成网络响应。

对应定义位于 `executor/executor_runner.h:109-158`。

目标端 runner 在握手后根据 manager 给出的 `procs` 数量创建同样数量的 `Proc`，见 `executor/executor_runner.h:553-571`。例如 `procs=4` 时，它可以让四个执行槽并行工作；每个槽分别保存自己的共享内存、控制管道和当前请求。

`Proc::Execute(msg)` 只有在状态为 `Started` 或 `Idle` 时才接收请求；接收后把状态推进到 `Handshaking` 或 `Executing`。如果执行子进程异常、超时，`Proc` 可以重启它，而不需要重建目标端的 FlatRPC 连接。

### 2. 执行前先发送 `ExecutingMessage`

这里先区分两个状态：

```text
Host 已把 ExecRequest 发到目标机
```

不等于：

```text
目标端已经开始执行这个程序
```

请求到达目标端后，可能仍在 runner 队列中等待空闲 `Proc`。如果 VM 此时因另一个程序崩溃，仅凭“请求已经发送”无法判断哪些请求真正开始过。

因此，一个 `Proc` 真正取得请求后，会在通知 `exec` 子进程之前先发送：

```text
ExecutingMessage{
    id:      请求 ID,
    proc_id: 当前执行槽 ID,
    try:     当前重试次数,
}
```

代码位于 `executor/executor_runner.h:396-443`。例如请求 ID 为 42 时，Host 发送阶段已经保存：

```text
runner.requests[42] ───► 原始 queue.Request
```

Host 收到 `ExecutingMessage{id=42, proc_id=1}` 后，`handleExecutingMessage()` 会：

1. 用 `id=42` 找到原始 `Request`；
2. 从 `req.Prog` 生成可读 syz 程序；
3. 把“proc 1 开始执行请求 42”写入 `lastExec`；
4. 把请求 42 标记到 `runner.executing`。

对应代码位于 `pkg/rpcserver/runner.go:383-423`。这个消息因而是一条**开始执行确认**，把 Host 的认识从“请求已下发”推进到“请求确实进入了执行阶段”。

如果内核随后崩溃，正常 `ExecResult` 往往来不及返回，但 VM monitor 仍会从 console、VM 进程状态或连接中断检测到崩溃。实例清理时，`Runner.Shutdown(crashed=true)` 会：

- 把已经标记为 `executing` 的请求完成为 `queue.Crashed`；
- 把只下发但尚未确认开始的请求完成为 `queue.Restarted`；
- 收集 `lastExec` 中最近开始的程序，附到 crash 报告中。

相关代码位于 `pkg/rpcserver/runner.go:582-611`、`pkg/rpcserver/last_executing.go:17-97` 和 `pkg/execbackend/rpc.go:109-125`。

所以两件事之间的因果关系是：

```text
目标端先确认“请求 42 已开始”
        │
        ▼
Host 端内存留下请求 42 的开始记录
        │
        ▼
目标内核崩溃，来不及返回正常结果
        │
        ▼
Host 仍能把请求 42 列为最近实际执行的候选
```

这并不绝对证明请求 42 就是根因：可能有多个 `Proc` 并行执行，也可能是先前操作延迟触发问题。因此 Host 保存的是最近执行程序的候选集合，最终仍要由 repro（崩溃复现）流程反复测试和简化，确定能够稳定触发问题的程序。

`pkg/flatrpc/flatrpc.fbs:201-211` 明确要求 `ExecutingMessage` 尽量小和快，就是为了提高它在内核崩溃前离开目标机、到达 Host 的概率。

随后：

- `msg.data` 中的执行字节流被复制到请求共享内存；
- `execute_req` 通过控制管道传给 `syz-executor exec`；
- `execute_req` 只保存请求 ID、类型、执行标志和 all-signal 位图，不重复携带大块程序数据。

### 3. `exec` 进程和 fork server

`syz-executor exec` 的入口仍在 `executor/executor.cc:582`。它映射输入和输出共享内存、接收握手、初始化 KCOV 和沙箱，然后进入目标对应的执行循环。

在 Linux 等启用 `SYZ_EXECUTOR_USES_FORK_SERVER` 的目标上，`executor/common.h:609-750` 中的 `loop()` 会对每个请求：

1. 创建单独的工作目录；
2. 调用 `receive_execute()` 从控制管道读取请求；
3. `fork()` 一个瞬态测试子进程；
4. 在子进程中调用 `execute_one()`；
5. 父进程等待并监控执行进度；
6. 超时则杀死子进程；
7. 回复执行状态并清理工作目录。

因此，当前 Linux 普通执行路径有三层：

```text
syz-executor runner                 长期维护网络连接
    └── syz-executor exec           由 Proc 管理，可重启，通常充当 fork server
            └── 测试子进程          执行一个程序后退出
```

不是所有目标都启用 fork server，snapshot 模式也有自己的路径。snapshot 模式会从预先保存的目标机状态恢复后执行测试，以获得更强的隔离和归因；本阶段讨论的是当前 Linux 的普通非 snapshot 路径。

## 八、第四棒：解释低层指令并发起调用

`receive_execute()` 和 `parse_execute()` 位于 `executor/executor.cc:853-885`，负责读取控制结构并设置本次执行标志。程序字节已位于 `input_data` 指向的共享内存中。

`execute_one()` 位于 `executor/executor.cc:933-1175`。它先读取调用总数，然后循环解释指令：

| 指令或值 | executor 的动作 |
|---|---|
| `instr_copyin` | 读取地址和参数类型，把常量、地址、资源结果、原始数据或校验和写入数据区 |
| `instr_copyout` | 跳过并记录相关位置，等前一调用完成后再从内存取结果 |
| `instr_setprops` | 设置下一次调用的异步、故障注入或重复等属性 |
| 普通 call ID | 索引 `syscalls[]`，读取参数，并交给 `schedule_call()` |
| `instr_eof` | 程序指令结束 |

普通调用的关键代码位于 `executor/executor.cc:1078-1127`：

```cpp
const call_t* call = &syscalls[call_num];
...
args[i] = read_arg(&input_pos);
...
schedule_call(...);
```

`call_t` 定义于 `executor/executor.cc:340-347`，保存调用名称、真实 syscall number、属性和可选伪调用函数。`execute_call()` 最终调用目标相关的 `execute_syscall()`。Linux 实现在 `executor/executor_linux.h:97-102`：

- `call->call` 非空时执行 syzkaller 的伪调用函数；
- 否则调用 `syscall(call->sys_nr, ...)` 发起真实系统调用。

调用完成后，`copyout_call_results()` 会保存返回值和指定输出内存，使后续调用的 `arg_result` 能引用它，见 `executor/executor.cc:1345-1375`。

这就是阶段 1 所说的边界：复杂类型和 resource 关系主要在 Go 端处理；executor 只解释已经降级的执行动作。但“只解释低层动作”不表示 executor 很简单，它仍要处理线程调度、沙箱、超时、故障注入、KCOV、共享内存和大量伪调用。这里只是不再重复一套完整 syzlang 类型系统。

## 九、第五棒：从 KCOV 原始记录到 signal、cover 和执行结果

### 1. KCOV 先提供每次调用经过的内核 PC

如果本次请求启用了覆盖率反馈，executor 会为执行调用的线程准备 KCOV 缓冲区。可以先把 KCOV 的输出理解为一串 PC（program counter，程序计数器）地址：这些地址表示执行期间经过了哪些内核代码位置。

executor 会尽量把反馈归到具体调用上。例如程序有三条调用，返回的 `ProgInfo.Calls[0]`、`Calls[1]` 和 `Calls[2]` 分别描述对应调用的执行状态与反馈；无法归到某一条调用的后台覆盖则放入 `ProgInfo.Extra`。这种对应关系使 Host 不仅知道“整个程序产生了新行为”，还知道主要是哪一条调用产生的。

调用开始前，executor 会重置并启用当前线程的 KCOV 缓冲区；调用完成后，`cover_collect()` 取得其中的记录，`write_call_output()` 再写出：

- 该调用是否真正执行、是否完成或阻塞；
- 返回的 `errno`；
- 按请求选项生成的 signal、cover 或 comparison 数据。

相关路径位于 `executor/executor.cc:1377-1442` 和 `1540-1597`。这些字段最后组成 FlatBuffers 的 `CallInfoRaw`；协议定义位于 `pkg/flatrpc/flatrpc.fbs:213-232`。

### 2. cover 与 signal 是同一批 PC 的两种用途

`cover` 和 `signal` 不是两个独立的内核采集机制。它们都以 KCOV 记录为基础，只是保留的信息和用途不同：

| 反馈 | executor 大致怎样产生 | Host 主要怎样使用 |
|---|---|---|
| `Cover` | 返回本次执行经过的 PC；请求也可要求先去重 | 查看和合并较完整的代码覆盖，记录有价值输入覆盖了哪些代码 |
| `Signal` | 当前实现根据 PC 形成紧凑的点或边标识，再过滤并去重 | 高频判断这次执行是否带来了此前没有见过的行为 |
| `Comps` | KCOV comparison 模式返回比较指令两侧的操作数 | 为 comparison hints 生成更有针对性的参数变异 |

当前普通 Linux 配置使用边反馈时，`write_signal()` 会把当前 PC 与前一个 PC 的部分信息组合成 signal。这里先把 signal 理解为“适合快速比较的新行为标识”即可；它的具体编码、优先级和集合运算留到阶段 5。

`CollectSignal` 和 `CollectCover` 分别决定本次请求是否写出这两类数据。两者可以同时设置，也可以只设置其中一个。`write_output()` 根据这些标志调用 `write_signal()` 或 `write_cover()`，见 `executor/executor.cc:1225-1279` 和 `1377-1404`。

### 3. 普通 fuzz 为什么通常只请求 signal

普通 fuzz 会持续执行大量程序，而绝大多数执行不会产生新覆盖。如果每一次都从目标机回传完整 PC 列表，会消耗更多共享内存、CPU 和 RPC 带宽。因此，普通生成或变异请求通常只设置：

```text
ExecFlagCollectSignal
```

一次普通执行的反馈路径可以概括为：

```text
queue.Request.ExecOpts 请求 CollectSignal
        │
        ▼
目标端解析为 flag_collect_signal
        │
        ▼
每条调用收集 KCOV PC
        │
        ▼
write_signal() 形成并去重 signal
        │
        ▼
CallInfo.Signal → ExecResult → Host
        │
        ▼
Host 与自己的 maxSignal 比较，判断是否有新 signal
```

这里的 `maxSignal` 是 Host 侧 fuzzer 保存的“到目前为止观察过的最大 signal 集合”，其中也包括后来可能被证明不稳定的 signal。`Cover.addRawMaxSignal()` 会把本次 signal 与该集合比较，只把差集作为潜在新 signal，同时立即把差集合并回 `maxSignal`。

### 4. 目标端的 `max_signal` 是 Host 集合的过滤副本

在当前普通、非 snapshot 路径中，manager 大约每半秒取走 Host 新增的 `maxSignal`，通过 `SignalUpdate` 增量同步给各目标端 runner。runner 把这些值加入共享的 `max_signal` 过滤器，各 `syz-executor exec` 进程可以访问这份过滤器。

于是 `write_signal()` 在普通模式下能够提前跳过目标端已经知道的 signal：

```text
Host：maxSignal（判新的权威集合）
          │ 周期性发送新增部分
          ▼
目标端：max_signal（用于减少回传的过滤副本）
```

这份目标端副本可能因为周期性同步而暂时落后，所以最终是否为新 signal，仍由 Host 的 `maxSignal` 判断。目标端过滤只是减少无用数据，不承担最终的判新结论。相关代码位于 `syz-manager/manager.go:1307-1318`、`pkg/rpcserver/rpcserver.go:617-621`、`executor/executor_runner.h:812-820` 和 `executor/executor.cc:1225-1258`。

### 5. triage 为什么需要 `ReturnAllSignal`

首次执行观察到潜在新 signal 后，`triageProgCall()` 已经立即把它加入 Host 的 `maxSignal`；它也可能很快被同步到目标端的 `max_signal`。但 triage（复查筛选）的下一步恰恰是重新执行原程序，检查这个 signal 是否还能出现。

如果 triage 仍按普通规则执行，目标端可能因为“这个 signal 已经在 `max_signal` 中”而不再返回它。Host 看到的将是一个被过滤后的结果，无法判断原 signal 是真的没有再次出现，还是出现了但被目标端省略了。

因此 triage 请求会这样设置：

```go
ExecOpts:        CollectSignal | CollectCover
ReturnAllSignal: 需要复查的调用索引
```

`ReturnAllSignal` 经 `ExecRequest.AllSignal` 传到目标端，再转换成 `all_call_signal` 位图。`write_signal(..., all=true)` 对指定调用绕过 `max_signal` 过滤，从而把这次执行实际得到的 signal 返回给 Host。

这里的“all”有严格边界：

- 它只表示不因 `max_signal` 已见集合而省略 signal；
- 它不会把 signal 变成 cover；完整 PC 仍由单独的 `CollectCover` 请求；
- 它也不会取消单次执行内部的去重、覆盖范围过滤等正常处理。

triage 同时请求 `CollectCover`，是因为一旦确认输入确实有稳定的新 signal，后续还要记录该输入覆盖了哪些 PC。两类请求的区别可以归纳为：

| 场景 | `CollectSignal` | `CollectCover` | `ReturnAllSignal` | 目的 |
|---|---:|---:|---:|---|
| 普通生成或变异 | 是 | 通常否 | 否 | 用较低成本发现潜在新行为 |
| triage 重执行 | 是 | 是 | 对关注调用设置 | 验证原 signal 是否稳定，并收集入库所需 cover |

这样，前文三个控制项就能放回同一条因果链中理解，而不必只靠变量名猜测。signal 的具体计算和稳定性集合运算属于阶段 5；KCOV 映射、缓冲区与线程采集细节属于阶段 6。

### 6. 形成 `ExecResult` 并回传

瞬态测试子进程把每个调用的结果片段写入响应共享内存。fork server 回复完成状态后，外层 `Proc::HandleCompletion()`：

1. 从原程序字节中读出调用数量；
2. 调用 `finish_output()` 组装 `ProgInfo`；
3. 把各调用反馈按调用索引放入 `ProgInfo.Calls`；
4. 把后台线程产生的额外覆盖放入 `ExtraRaw`；
5. 加入耗时、同一 `exec` 进程此前已执行的程序数（`freshness`）、是否无法正常结束（hang）和错误状态；
6. 形成 `ExecResult`，通过 FlatRPC 连接返回 Host。

相关代码位于 `executor/executor_runner.h:446-479` 和 `executor/executor.cc:1454-1493`。`ProgInfo` 与 `ExecResult` 的协议字段位于 `pkg/flatrpc/flatrpc.fbs:243-265`。

## 十、第六棒：Host 把网络结果交回 fuzzer

`rpcserver.Runner.handleExecResult()` 位于 `pkg/rpcserver/runner.go:426-495`。它先根据请求 ID 找到发送时保存的 `queue.Request`，再处理结果：

1. 补齐或裁剪调用结果数量，使其与原 `Prog.Calls` 一致；
2. 把目标机地址规范化到 Host 的模块视图；
3. 检查 signal 是否落在允许的内核地址范围，异常时丢弃整组 signal 和 cover；
4. 合并后台线程产生的 `ExtraRaw`；
5. 根据错误或挂起状态设置 `queue.Result.Status`；
6. 调用 `req.Done(result)`。

`queue.Result` 定义于 `pkg/fuzzer/queue/queue.go:181-203`，其中保存 `ProgInfo`、实际使用的 VM/proc、状态、进程输出和内部错误。

`Done()` 不只是关闭等待通道。`queue.Request.OnDone()` 可以提前安装完成回调，见 `pkg/fuzzer/queue/queue.go:68-108`。fuzzer 在请求发出前通过 `prepare()` 注册 `processResult()`；所以 `req.Done()` 会把结果重新送回反馈闭环，而不是只表示“RPC 已经结束”。

## 十一、第七棒：从潜在新 signal 到 corpus

### 1. 首次结果先完成判新，不直接入库

上一节的 `req.Done(result)` 会触发 fuzzer 事先注册的 `processResult()`。这个函数重新同时拿到原始 `Request` 和执行结果，因此既能访问 `req.Prog`，也能查看 `res.Info` 中各调用的 signal。`processResult()` 位于 `pkg/fuzzer/fuzzer.go:146-212`；普通收集 signal 的成功结果会逐个交给 `triageProgCall()`。

`triageProgCall()` 位于 `pkg/fuzzer/fuzzer.go:231-251`。它：

1. 根据调用结果计算 signal 优先级；
2. 调用 `Cover.addRawMaxSignal()`，求本次 signal 相对全局 `maxSignal` 的差集；
3. 没有差集就返回；
4. 有差集则记录“哪条调用产生了哪些潜在新 signal”，供 `triageJob` 处理。

`Cover.addRawMaxSignal()` 位于 `pkg/fuzzer/cover.go:27-36`。它会立即把新观察到的部分合并进 `maxSignal` 和待同步的 `newSignal`。

这里必须区分两个集合：

- `maxSignal`：所有曾观察到的最大 signal，包括之后可能被证明不稳定的 signal；
- corpus：经过稳定性验证并最小化后保留的程序集合。

因此，进入 `maxSignal` 只是“以后不必反复大量上报同一反馈”，不是入库证明。

### 2. triage（复查筛选）会再次走同一条执行链

如果至少一个调用存在潜在新 signal，`processResult()` 会克隆原 `Prog`，再把“程序、关注的调用、各调用首次发现的新 signal、首次使用的 executor”装入一个 `triageJob`。克隆是为了让后续最小化可以修改程序，而不改变仍由原请求持有的对象。

所以 triage 的输入和可能输出可以先概括为：

```text
输入：Prog 副本 + 需要复查的调用 + 首次发现的新 signal
              │
              ▼
     重复执行验证 → 最小化并重执行验证
              │
              ├── signal 不稳定：丢弃这次潜在发现
              └── signal 稳定：形成 corpus.NewInput 并保存
```

`triageJob.run()` 位于 `pkg/fuzzer/job.go:148-169`。它的第一步是 **deflake**，也就是通过重复执行排除只偶发出现的反馈。对普通非 snapshot 新程序，当前默认参数是：

- 需要 signal 至少在 3 次执行中共同出现；
- 最多观察 5 次执行；
- 一旦已经满足条件，或者已经不可能满足条件，可以提前停止。

常量和设计说明位于 `pkg/fuzzer/job.go:111-140`，实现位于 `228-347`。

每次重新执行仍然会产生新的 `queue.Request`，再次经过：

```text
队列 → SerializeForExec → FlatRPC → executor → ExecResult → queue.Result
```

triage 请求会同时设置 `CollectCover | CollectSignal`，并通过 `ReturnAllSignal` 要求关注调用的 signal 不被目标端 `max_signal` 已见集合省略，见 `pkg/fuzzer/job.go:250-256`。所以 triage 不是收到首次结果后在 Host 上做一次纯计算，而是一个会反复调用完整执行链的任务。

deflake 结束后：

```text
stableSignal    = 多次执行中足够稳定的 signal
newStableSignal = 首次发现的新 signal ∩ stableSignal
```

如果 `newStableSignal` 为空，这个程序不会因本次发现进入 corpus。

### 3. 最小化同样依赖反复执行

存在新稳定 signal 时，`triageJob.minimize()` 调用 `prog.Minimize()` 尝试删除调用或简化参数，见 `pkg/fuzzer/job.go:350-399`。每个候选修改都会重新执行；只有仍能保留全部目标 `newStableSignal` 的修改才会接受。

因此，最小化不是对程序文本做静态压缩，而是“提出更小程序 → 实际执行 → 验证目标 signal”的循环。

### 4. 保存到内存 corpus

验证和最小化通过后，`triageJob.handleCall()` 构造 `corpus.NewInput`：

```go
input := corpus.NewInput{
    Prog:     p,
    Call:     call,
    Signal:   info.stableSignal,
    Cover:    info.cover.Serialize(),
    RawCover: info.rawCover,
}
Corpus.Save(input)
```

源码位于 `pkg/fuzzer/job.go:171-225`。

`Corpus.Save()` 位于 `pkg/corpus/corpus.go:130-192`，它会：

1. 用 `Prog.Serialize()` 得到可读程序数据并计算哈希；
2. 如果哈希已存在，合并 signal 和 cover；
3. 如果是新程序，加入内存映射和按优先级选择的程序列表；
4. 合并整个 corpus 的 signal 和 cover；
5. 通过更新通道发送 `NewItemEvent`。

### 5. manager 持久化新程序

manager 在 `syz-manager/manager.go:991-1013` 的 `corpusInputHandler()` 接收更新：

- 已存在程序的 signal/cover 更新不重复写数据库；
- 新程序调用 `mgr.corpusDB.Save()` 并 `Flush()` 到 `workdir/corpus.db`。

这里持久化的是程序数据。运行时的稳定 signal 和 cover 保存在内存 corpus 中；manager 下次启动时会把数据库程序作为 candidate 重新执行和 triage。

### 6. 回到变异起点

新程序加入内存列表后，后续 `mutateProgRequest()` 可以再次通过 `Corpus.ChooseProgram()` 选择它，克隆并变异。闭环至此合上：

```text
新稳定 signal
      │
      ▼
最小化程序进入 corpus
      │
      ▼
成为后续变异的起点
      │
      ▼
探索新的内核状态和 signal
```

此外，新语料还可能触发 smash、comparison hints 和 fault injection 等强化任务。这些任务同样通过统一请求链执行，具体策略留到阶段 5。

## 十二、并非每个程序都会完整走到入库

“一个程序的一生”有多种终点：

| 执行结果 | 后续处理 |
|---|---|
| 成功执行，但没有新 signal | 普通 fuzz 程序通常在 `processResult()` 后结束，不进入 corpus |
| 首次出现新 signal，但重复执行后不稳定 | 停在 triage，不进入 corpus |
| 新 signal 稳定，但某个最小化修改丢失 signal | 拒绝该修改，继续尝试其他最小化；不是丢弃整个原程序 |
| 新 signal 稳定且最小化成功 | `Corpus.Save()`，并持久化新程序 |
| executor 返回 `Hanged` | 本轮不触发普通 triage；runner 和上层按挂起状态处理 |
| 目标内核崩溃 | 进入 crash 收集和复现支线，不把“崩溃”本身当作普通 corpus 入库条件 |
| `SerializeForExec()` 失败 | 在 Host 端形成 `ExecFailure`，请求不会作为程序消息发到目标机 |

启动时从 `corpus.db` 或 hub 取得的 candidate 还有自己的重试和重新 triage 规则。本文主线关注运行期间新生成或新变异的普通程序。

### 实验二：把 syz 程序转换为 C

先查看参数：

```bash

```

生成代码中的关键调用为：

```c
res = syscall(__NR_openat, ...);
```

## 十五、阶段 2 的概述版本

> 目标端出现空闲执行能力后，Host 依次查询 candidate triage、candidate、普通 triage 和 smash 工作源；这些工作源暂时都没有请求时，`genFuzz()` 才从零生成程序或从 corpus 选择程序变异。程序在 Host 内存中是类型化的 `*prog.Prog`，再被包装成携带执行策略、调度约束和完成回调的 `queue.Request`。Host 侧 RPC runner 取到请求后调用 `SerializeForExec()`，把 `Prog` 降为 copyin、call、copyout 等低层指令，并只把网络执行所需信息封装成 FlatRPC 的 `ExecRequest`；原 `Request` 仍按请求 ID 保留在 Host。目标端 executor runner 收到消息后选择一个 `Proc` 执行槽，先发送 `ExecutingMessage` 确认该请求已经开始，再通过共享内存和控制管道交给 `exec` 进程；Linux 普通路径由 fork server 启动瞬态测试子进程。子进程解释低层指令，用 call ID 查 `syscalls[]`，执行真实系统调用或伪调用，并从 KCOV 形成每个调用的 signal、cover 和状态。普通 fuzz 主要返回 signal，目标端 `max_signal` 只负责过滤 Host 已同步的旧 signal，最终仍由 Host 的 `maxSignal` 判新。结果以 `ExecResult` 回到 Host，RPC runner 根据 ID 找回原 `queue.Request` 并触发完成回调。没有新 signal 的普通程序到此结束；有潜在新 signal 的程序进入 triage，反复执行以排除偶发反馈，再通过实际重执行验证最小化。稳定且仍有新 signal 的程序加入内存 corpus，并由 manager 把新程序写入 `corpus.db`，之后可被再次选中和变异。
