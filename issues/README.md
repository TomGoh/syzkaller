# pKVM fuzzing — issue tracker

This directory tracks **things the fuzzing actually observed**. It is issue-keyed, so the primary question it answers is "what is the state of defect X on kernel Y", which no date-ordered note can express once the same defect set is re-run against a second kernel lineage.

`notes/` keeps its role: chronology, design records, and analysis. This directory records what was observed and what became of it.

## Scope — what belongs here

**In:** anything observable and abnormal that a fuzzing campaign produced, or that a targeted reproduction of such an observation produced. Kernel warnings, Oopses, panics, hung tasks, host lockups. Also campaign-level abnormalities: a stalled `exec total`, a manager that cannot recover a target, coverage that stops growing, a non-zero `LOST_IN_RING`.

**Out:** defects found by reading code or by diffing against upstream, which fuzzing has not exhibited. Those are analysis and belong in `notes/`. An `ISSUE.md` may *cite* such a note as a candidate mechanism for an observed symptom — code reading proposes, the tracker records only what fuzzing disposed.

The rule is chosen because it is falsifiable. "Present in code" is a claim that can be generated indefinitely by reading; this project's history records two confident code-derived mechanisms that were wrong. "Observed during fuzzing" is anchored to an artifact.

The tracker started empty on 2026-08-05. Findings from earlier campaigns on other kernel lineages were deliberately not imported. They enter only if a run on the current target observes them — which makes them predictions we can be wrong about, rather than inherited assertions.

## Layout

```
issues/
  README.md                        this file — the method
  INDEX.md                         GENERATED by tools/render-index.py — do not hand-edit
  tools/
    render-index.py                front-matter -> INDEX.md, and validation
    capture-run.sh                 snapshot a run's observability conditions
  runs/
    <run-id>.md                    one record per campaign or reproduction
    <run-id>/                      that run's bulky artifacts (config, logs, stats)
  NNN-<slug>/
    ISSUE.md                       front-matter + prose
    repro/                         reproducer source + build line, if one exists
    evidence/                      raw artifacts: stacks, dmesg, stdout
```

Issue IDs are three digits, allocated in order of first observation. They are never reused or renumbered.

## `ISSUE.md` front-matter

```yaml
---
id: 001
slug: pkvm-unmap-selfdeadlock
title: one line, states the defect
class: kernel-defect          # kernel-defect | instrumentation | operational
signature: the crash title or the observable symptom
hazard: none                  # none | wedges-target | destroys-data
diagnosis: symptom-only       # symptom-only | hypothesis | root-caused
disposition: open             # open | fix-proposed | fix-verified | not-a-defect
repro: repro/foo.c            # or: none
observations:
  - target: <kernel release, build number, tree @ commit>
    state: observed           # reproduced | observed | not-observed | unknown
    run: <run-id>
    evidence: evidence/<file>
---
```

Two front-matter conventions, both enforced by the renderer. **Quote any value containing `#`** — a build string like `6.6.103+ #3 @39ee...` is silently truncated at the `#` otherwise, and the record still parses, so the loss is invisible. For the same reason, **no inline `#` comments in front-matter**; put commentary in the prose below.

Run records use the same `---` fencing. They additionally carry `kind: campaign | reproduction`, and the two lists `observed:` / `not_observed:` of issue ids, which the renderer cross-checks against every issue that cites the run.

Prose sections follow, in this order: **Symptom** (the raw artifact) · **Mechanism** (confidence labelled) · **Trigger** · **Reproduction** · **Blast radius** · **Fix status** · **Residual hazard**.

`Residual hazard` is not decoration. It is where a partial mitigation records what it does *not* cover, so that a later reader does not see `mitigated` and believe it.

## State model

Three independent axes. Collapsing them is how a hypothesis becomes a root cause by accident.

**`state`** is per target — an issue carries one observation row per kernel build:

| value | meaning |
| --- | --- |
| `reproduced` | a standalone reproducer triggers it deterministically on this build |
| `observed` | seen in a run on this build, artifact attached |
| `not-observed` | a **qualifying** run completed without it |
| `unknown` | no qualifying run yet |

**`diagnosis`** — `symptom-only` → `hypothesis` (code reading, explicitly unconfirmed) → `root-caused` (trace or instrumentation showing actual values: pointers, PIDs, counts, states).

**`disposition`** — `open` → `fix-proposed` → `fix-verified` → `not-a-defect`.

Two rules keep this honest, and `render-index.py` enforces both:

1. **`not-observed` requires a linked run record**, and that run must have been *capable* of observing the signature — the filters in force must not match it, and the syscalls needed to reach it must have been enabled. Absent a qualifying run the state is `unknown`, not `not-observed`.
2. **`diagnosis: root-caused` requires evidence beyond source.** A mechanism inferred only from reading code is `hypothesis`, and must say so.

## Run records

Every campaign and every targeted reproduction gets `runs/<run-id>.md`. This is what makes a negative result usable: without the conditions, "we did not see it" is unfalsifiable.

The trap this exists to prevent is real and recent. On 2026-08-05 a campaign ran with `"ignores": []` in its config, which reads as "nothing filtered" — while the `syz-manager` binary it used had three ignores compiled into `pkg/report/linux.go`, two of them for pKVM KVM warnings. A run under those conditions can never license `not-observed` for either.

The filter set is derivable, not remembered. The manager binary embeds its own syzkaller revision:

```
strings bin/syz-manager | grep -oE '^[0-9a-f]{40}$'
```

Read `pkg/report/linux.go` at that revision for the ignores that were compiled in, and record them alongside the config's `ignores` list.

Record at minimum: board, kernel build string and source commit, manager revision, config (copied verbatim into `runs/<run-id>/`), both filter sets, enabled-syscall count, duration, final stats, EL2 ring counters, and the issue IDs observed and not-observed.

**A hung reproducer prints nothing — check `rc`, not output.** The reproducers here bound themselves with `alarm()` and `_exit(3)`, and `_exit()` does not flush stdio; piped output is block-buffered, so a program that hangs produces a **completely empty** result. That is visually identical to "the check passed and found nothing". On 2026-08-06 a verification run reported zeros across every column of its table and was nearly read as success — the kernel under test was actually livelocking every guest that enabled dirty logging. `stdbuf -o0` does not help, because nothing has been written yet. `rc=3` is the alarm; treat it as a failure, and make summary scripts print the exit status next to every result. See [runs/2026-08-06-fix-deploy-verify.md](runs/2026-08-06-fix-deploy-verify.md).

**`/tmp` on the boards is tmpfs and is wiped by a reboot.** Re-copy test binaries after every deploy, or a stale run reports `rc=127` that looks like a crash.

`LOST_IN_RING` belongs in every record. If the ring dropped PCs, "no new coverage" is an instrument artifact rather than a property of the target — the first methodology rule in `notes/pkvm/OPERATOR-RUNBOOK.md`.

## Reference trees — what may be compared against

We work on **klinux `klad-v11-next`**. When an issue needs "does this exist elsewhere / where did it come from", compare only against these:

| tree | what it is |
| --- | --- |
| `~/klinux` | the tree under test — the subject, not a reference |
| `~/common` | the original ACK checkout (whether or not it carries kcov/pKVM changes is irrelevant here) |
| `~/kernel-refs/ack` | **pure, unmodified ACK** — `android15-6.6`, `android16-6.12`, `android17-6.18`, fetched from `android.googlesource.com/kernel/common` and never committed to |
| `~/kernel-refs/linux` | **pure, unmodified upstream Linux** |

Both `~/kernel-refs` trees are deliberately left **with no checkout** — only `.git` is populated. A reference tree with no working files cannot be edited by accident, and it forces `git show <ref>:<path>`, which is the rule below. They are blobless (`--filter=blob:none`); blobs fetch on demand, and the two ACK branches beyond 6.6 are shallow, so file content is available but commit archaeology on them is not.

Snapshots as first fetched, 2026-08-05 — cite these when a claim depends on a moving branch:

| ref | tip |
| --- | --- |
| `aosp/android15-6.6` | `742616e` |
| `aosp/android16-6.12` | `f068f96` |
| `aosp/android17-6.18` | `42ab2c6` |
| `torvalds/master` | `c21bb4193` |
| `~/common` (`2030/bug930`) | `da966ce9a047` |

**Prefer a tag over a branch** for mainline claims. `master` moves: reading `arch/arm64/kvm/mmu.c` from two snapshots taken hours apart gave `account_locked_vm` at `1692`/`1741` and then at `1724`/`1773`. A line number cited against `master` is wrong by the next fetch.

**Do not compare against `~/common-stage2mvp`, `~/ksrc-pkvmfix` or `~/futlab-fixes`.** They are the `2030/bug930` lineage, which is not ours, and they carry local unpushed patches on top. Reasoning from them produced three false claims in one afternoon — that a fix had "landed on `2030/bug930`" when the branch is still unfixed, and that two ACK cherry-picks were on that branch when they are only on an unpushed local chain.

**Read refs, not working trees.** Always `git show <ref>:<path>`, never `cat <path>` in a checkout. The trap that caused the errors above was a checkout whose working tree contained an uncommitted fix while its branch did not — the file looks fixed, the branch is not. The same rule applies to a build: compare the build string embedded in the binary, not the file's mtime.

## Working an issue

Once an issue is filed, it goes through three steps in this order. Do not skip step 2 — shipping our own patch when an upstream fix already exists creates a divergence someone has to reconcile at every rebase, and the upstream version has been reviewed and tested by people with more context.

**1. Establish the cause, then have it reviewed.** Root-cause the defect, then hand the analysis to a reviewer whose brief is to *refute* it, not to agree. The reviewer reads complete function bodies against the actual tree and reports contradictions. This exists because the analysis being reviewed is usually the thing a fix will be built on, and this project has twice built on a confident mechanism that was wrong.

**2. Search AOSP and Linux upstream for an existing or related fix.** A fix from a different or newer kernel version still counts — it tells us the shape of the accepted solution even when it cannot be applied as-is.

The search has a trap that has already caught this project: in these repos the interesting upstream commits are frequently reachable **only from tags**, so searching branches returns nothing and wrongly concludes no fix exists. Always `git log --all --source`, which prints the ref each commit came from. Never rely on `git branch -r --contains`, which is slow and blind to tag-only commits. Search several angles — by function name, by `-S` on the code, and by the file's own history — because upstream subject lines rarely match our vocabulary. A subject that sounds right is a hypothesis; the diff is the evidence.

**3. Apply the fix.** Cherry-pick cleanly if possible, preserving the original author and `Change-Id`. If the tree has diverged so the patch must be adapted, record what changed and why. If nothing upstream exists, write it locally and say explicitly what was searched.

Record the outcome of all three in `ISSUE.md` under `Fix status`, including a negative result from step 2 — "we looked and found nothing" is worth writing down, because the next person will otherwise look again.

## Adding an issue

1. Allocate the next ID, create `NNN-<slug>/`.
2. Move the raw artifacts into `evidence/`. Prefer identity-tracked evidence — one PID, one handle, one object followed through its lifecycle — over aggregate counts.
3. Write `ISSUE.md`. Label every mechanism claim as verified or hypothesis. If the mechanism came only from reading code, `diagnosis` is `hypothesis`, whatever its plausibility.
4. Write or update the `runs/` record that observed it.
5. Run `python3 tools/render-index.py` and commit the regenerated `INDEX.md`.
