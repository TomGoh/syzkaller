Issue 005 — the one-line fix was tried on hardware and is WRONG
Date: 2026-08-06
Board: N90 (10.42.27.17), Kylin V11, kvm-arm.mode=protected
Kernels: #4  baseline (no fixes)
         #10 003-fix + 004-fix + 005-fix(pkvm_mkstate)          -> dirty logging LIVELOCKS
         #11 003-fix + 004-fix, 005 hunk reverted (bisect)      -> everything works
         #12 as #10 plus a relax_perms fallback on -EAGAIN      -> still LIVELOCKS
         #13 003-fix + 004-fix, 005 reverted with rationale     -> restored state

VERDICT: writing the page state back with pkvm_mkstate() at the existing
kvm_pgtable_stage2_map() call is not a fix. It converts issue 005's silent
corruption into an unrecoverable guest hang. 005 is back to `open`.


================================================================================
1. What was deployed and what happened
================================================================================

#10 carried the fix proposed in this issue:

  -   KVM_PGTABLE_PROT_RWX,
  +   pkvm_mkstate(KVM_PGTABLE_PROT_RWX, PKVM_PAGE_SHARED_BORROWED),

Every reproducer that enables dirty logging then hung. No output, no dmesg, no
Oops -- the process sat in state R inside KVM_RUN until its alarm() fired:

  mode[default] STUCK  state=R
    [<0>] kvm_release_pfn_clean+0x2c/0x100
    [<0>] kvm_handle_guest_abort+0x67c/0x1108
    ...
    [<0>] kvm_arch_vcpu_ioctl_run+0x884/0x8f8
  mode[nodirty] finished rc=0          <- the only mode without dirty logging
  mode[nohuge]  STUCK  state=R

Quantified with a kretprobe on kvm_handle_guest_abort:

  guest_abort events in 3 seconds: 39962
  return values: 39961 x ret=1, 1 x ret=0

ret=1 is "handled, resume the guest". So the fault was being accepted and
re-taken forever: an infinite stage-2 fault loop, not a deadlock.


================================================================================
2. Why -- the kernel documents this exact refusal
================================================================================

  /* arch/arm64/kvm/hyp/pgtable.c:961-975, stage2_map_walker_try_leaf() */
  old_is_counted = pte_ops->pte_is_counted_cb(ctx->old, ctx->level);
  if (old_is_counted) {
          /*
           * Skip updating a guest PTE if we are trying to recreate the
           * exact same mapping or change only the access permissions.
           * Instead, the vCPU will exit one more time from the guest if
           * still needed and then go through the path of relaxing
           * permissions. This applies only to guest PTEs; ...
           */
          if (!stage2_pte_needs_update(pgt, ctx->old, new))
                  return -EAGAIN;
  }

  /* pgtable.c:760-771 */
  static bool stage2_pte_needs_update(struct kvm_pgtable *pgt, kvm_pte_t old, kvm_pte_t new)
  {
          ...
          return ((old ^ new) & (~KVM_PTE_LEAF_ATTR_S2_PERMS));
  }

The discriminator is "do old and new differ ANYWHERE OUTSIDE the S2 permission
bits". The page-state bits live outside them, and stage2_set_prot_attr() carries
them through verbatim (`attr |= prot & KVM_PTE_LEAF_ATTR_HI_SW;`, pgtable.c:721).

  #4  (bare prot):  old SW = SHARED_BORROWED, new SW = 0
                    -> differ outside perms -> update proceeds -> "works"
  #10 (mkstate):    old SW = new SW = SHARED_BORROWED
                    -> differ ONLY in S2AP_W -> -EAGAIN -> nothing written

and the host converts that error into "retry":

  /* mmu.c, end of user_mem_abort() */
  return ret != -EAGAIN ? ret : 0;

0 means "resume the guest", the guest re-executes the same store, faults again,
and the logging branch calls the same hypercall again. Forever.

**So the dirty-log handler has only ever functioned because it corrupts the page
state.** The corruption is what makes the new PTE differ from the old one by
more than permissions, which is the only reason the mapping is ever installed.
Repairing the state without replacing the primitive removes the very thing that
was making the write land.

================================================================================
4. The obvious follow-up also fails
================================================================================

#12 kept pkvm_mkstate() and added what the kernel comment suggests -- fall back
to the relax_perms path when the map declines:

    if ret == -(EAGAIN as i32) {
        ret = kvm_pgtable_stage2_relax_perms(&vm->pgt, guest_addr,
                                             KVM_PGTABLE_PROT_RWX, 0);
    }

Still livelocks, identically.

RESOLVED (same day, by reading the walker rather than guessing). The fallback
never fires because `ret` is not -EAGAIN -- it is 0:

  /* pgtable.c:121-137 */
  static bool kvm_pgtable_walk_continue(const struct kvm_pgtable_walker *walker, int r)
  {
          /*
           * Visitor callbacks return EAGAIN when the conditions that led to a
           * fault are no longer reflected in the page tables due to a race ...
           * Ignore the return code altogether for walkers outside a fault
           * handler (e.g. write protecting a range of memory) ...
           */
          if (r == -EAGAIN)
                  return !(walker->flags & KVM_PGTABLE_WALK_HANDLE_FAULT);
          return !r;
  }

  /* pgtable.c:189-190, 205-209 -- __kvm_pgtable_visit() */
  if (!kvm_pgtable_walk_continue(data->walker, ret))
          goto out;
  ...
  out:
          if (kvm_pgtable_walk_continue(data->walker, ret))
                  return 0;              <<<< the -EAGAIN is swallowed here
          return ret;

-EAGAIN reaches the caller ONLY if the walker carries
KVM_PGTABLE_WALK_HANDLE_FAULT. __pkvm_host_dirty_log_guest() passes flags = 0,
so the walk returns 0. The hypercall reports success, the host resumes the
guest, and nothing was written. That is the livelock, exactly.

Note that simply adding KVM_PGTABLE_WALK_HANDLE_FAULT does NOT fix it either.
-EAGAIN there means "a race changed the tables under us, re-enter the guest and
try again", and user_mem_abort() implements it as such. Here the condition is
not a race and does not change on retry, so the loop just becomes visible
instead of silent. The primitive has to change.


================================================================================
5. What a real fix has to look like
================================================================================

The primitive is wrong, not the argument. A permissions-only change to a guest
PTE must go through kvm_pgtable_stage2_relax_perms(), which is a read-modify-
write of the existing leaf (sets S2AP_R/W, clears XN) and therefore preserves
the software bits by construction and is not subject to the needs-update filter.

But relax_perms cannot break a block, and dirty logging needs PAGE_SIZE
granularity -- relaxing a whole 2 MiB block would make 512 pages writable while
only one is marked dirty, which is the same class of silent loss this issue is
about.

So the correct shape is split-then-relax, which is exactly what upstream moved
to: ACK android16-6.12 does the job with __pkvm_host_split_guest() followed by
__pkvm_host_relax_perms_guest(), and deleted __pkvm_host_dirty_log_guest()
entirely (6e3ff69cb190). The split machinery klinux lacks is c8303029c094 +
024d995fb + b052adb82; its EL2 half is ~50 lines of C that would need
translating into Rust, its host half ~110 lines of C, plus a pgtable.c hunk that
is a straight cherry-pick.

That is a redesign, not a hunk, and it should be sized and scheduled as one.

7. SEQUEL — the fix that works (#15), and the last wrong assumption
================================================================================

Section 5 above said a real fix needs split-then-relax. That was right. It also
implied the upstream split series had to be ported first. That was wrong -- the
tree already has everything needed.

An intermediate attempt (#14) picked the primitive by granule: relax_perms when
the mapping is already PAGE_SIZE, stage2_map when it is a block. Result:

  005 criterion:  A=1 B=1  3/3   <- fixed
  003 criterion:  THP mode rc=3  <- REGRESSED, livelocked

So the block branch livelocked too, which falsified the assumption that the
post-split entry would be invalid. Reading stage2_map_prefault_block() from its
signature this time (it had been read from the middle before) shows why:

  /* pgtable.c:1026-1064 */
  static void stage2_map_prefault_block(..., const struct kvm_pgtable_visit_ctx *ctx,
                                        kvm_pte_t *ptep)
  {
          pa = kvm_pte_to_phys(block_pte);              /* physical */
          ...
          for (i = 0; i < PTRS_PER_PTE; ++i, ++ptep, pa += granule) {
                  ...
                  if ((ctx->level < (KVM_PGTABLE_LAST_LEVEL - 1)) ||
                                  (pa < ctx->addr) || (pa >= ctx->end)) {   /* IPA */
                          *ptep = pte;

The skip test compares a PHYSICAL address against ctx->addr / ctx->end, which
are IPAs. For a guest stage-2 those are different address spaces, so the target
page's entry is NOT skipped -- it is pre-populated as a valid, still
write-protected leaf carrying the block's software bits. The following leaf
visit is then a permissions-only change again, and lands in exactly the same
-EAGAIN-swallowed-into-0 hole.

Both branches hit the same wall, so the fix collapses to one rule: the mapping
call must never be what grants write access.

  if the IPA is still a block:
      stage2_map(PAGE_SIZE, pkvm_mkstate(RWX, SHARED_BORROWED))   -- to SPLIT only
  always:
      kvm_pgtable_stage2_relax_perms(RWX)                          -- the permission change

The state is still written explicitly on the split path, because the entries the
split creates are built from the prot handed in; a bare prot would reintroduce
issue 005 on every page a block covers.

#15, five runs, kretprobe on pkvm_call_hyp_nvhe_ppage and __stage2_wp_range:

  run1 round3[A=1 B=1]  reprotect: EPERM=0 ok=2  teardown-EPERM=0
  run2 round3[A=1 B=1]  reprotect: EPERM=0 ok=2  teardown-EPERM=0
  run3 round3[A=1 B=1]  reprotect: EPERM=0 ok=2  teardown-EPERM=0
  run4 round3[A=1 B=1]  reprotect: EPERM=0 ok=2  teardown-EPERM=0
  run5 round3[A=1 B=1]  reprotect: EPERM=0 ok=2  teardown-EPERM=0
  unmap WARN: 0    donation msgs: 0    any WARNING: 0

The re-write-protect that answered -EPERM now returns 0, twice per run (page A
and the control page B). The page written under dirty logging is reported dirty
where it used to be lost. The teardown unmap no longer fails and its WARNING is
gone. probe-dirtylog-thp passes in all three modes including THP, so the block
path did not regress.

Klinux commit cba248683e5c. Board left on #15.

Count of wrong designs for this one function before it worked: three (#10 state
write-back, #12 -EAGAIN fallback, #14 granule-selected primitive). Each was
defensible from the code as read at the time; each was falsified in about ten
minutes by the reproducer. Two of the three were wrong because a function had
been read from the middle rather than from its signature -- the rule at the top
of CLAUDE.md, and it cost three build-and-boot cycles to relearn.

8. Review corrections (2026-08-06, post-fix)
================================================================================

Two citation errors in the commit messages of this series, found in review and
recorded here because the commits are on an unpushed Gerrit branch and were not
rewritten for two nits:

  * 24714fe308bb cites pgtable.c:721 for `attr |= prot & KVM_PTE_LEAF_ATTR_HI_SW;`.
    The correct line is 723. (371 is the stage-1 equivalent, not this one.)

  * cba248683e5c justifies putting the state into the split's prot as "the
    entries a split creates are built from the prot handed in". Imprecise.
    stage2_map_prefault_block() derives the SIBLING entries from block_pte via
    kvm_init_valid_leaf_pte(), so their state comes from the block, not from
    prot. The TARGET entry is generated from prot by
    stage2_map_walker_try_leaf() -- but usually not written, because that write
    is what the needs-update filter declines. So carrying the state in prot is
    DEFENSIVE (it matters only if that write ever does land), not the mechanism
    the split path depends on. The code comment has been corrected to say this;
    the fix itself is unchanged and still correct.

Two code defects were also found in the same review and fixed:

  * c6c3a2503e4b -- 61173329e416 put the atomic64_add() after the error return,
    so a partial OOM inside topup_hyp_memcache() leaves pages donated but
    unaccounted and the counter goes negative again. __topup_hyp_memcache()
    pushes one page at a time and bails on the first failed allocation
    (kvm_host.h:126), keeping what it already pushed. Both pkvm_relax_perms()
    and pkvm_mem_abort() now account before propagating; handle_hyp_req_mem()
    already did, because upstream wrote it that way.

  * 22f8b90f89c7 -- cba248683e5c let every non-(-E2BIG) probe result fall
    through to relax_perms, so a -ENOENT from guest_get_valid_pte() would be
    reported as relax_perms' error instead of its own. The probe's error is now
    returned directly.

Re-verified on #16 after both: 005 gives A=1 B=1 5/5, 003 passes in all three
modes, and dmesg carries no WARNING at all.
